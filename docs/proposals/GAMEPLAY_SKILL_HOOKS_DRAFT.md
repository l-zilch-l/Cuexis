# Skill Hooks 与模块扩展性草案

状态：candidate（设计草案，未接受，未实施）

更新日期：2026-09-29

本文回应 [Gameplay Ruleset 设计讨论记录](GAMEPLAY_RULESET_DISCUSSION.md) 下一步工作 H：技能挂点
体系的覆盖范围。它回答的问题只有一个：**新增技能或角色，是否必须升级 Ruleset Interface**。
前置决定见该文 §2.6、§2.9、§2.10，以及
[Ruleset Fold Language 草案](GAMEPLAY_RULESET_FOLD_DRAFT.md) §4.4、§4.6、§4.7。

## 1. 结论

```text
新增技能或角色不需要升级 Ruleset Interface。
```

只要技能的改动没有让 L2 程序读到新的东西。这个条件在实践中几乎总成立，因为 L2 程序读取的
Hook 集合极小（见 §3），而技能绝大部分作用在折叠层内部。

以下三节说明这个结论为什么成立，以及残留的例外是哪一种。

## 2. 两个发现

### 2.1 Hook 分为两类

此前把 Hook 当作一类东西处理，因此得出"新增 Hook 需要 bump"的结论。这个结论过宽。真实的
区分是**谁读它**：

| | 谁读 | 声明位置 | 影响 L2 静态验证 |
| --- | --- | --- | --- |
| **程序可见 Hook** | L2 程序与模块 | Interface | 是（验证器需要静态取值范围） |
| **模块本地状态** | 只有本模块 | 模块自身 | 否 |

程序可见 Hook 的存在理由只有一个：**技能要改变 L2 程序读取的判定参数**。例如放宽窗口、
增加 Hold 宽限时间、加大接水果盘子的判定半宽。

而分数倍率、护盾次数、生命值、技能冷却、连击保底、准确率加成这些，**L2 程序从来不读**。
它们在折叠层内部流动。因此它们不是 Interface Hook，而是模块本地状态。

### 2.2 于是有两套扩展机制

```text
机制一  模块本地状态 + 数据化技能
        适用：已有机制的变体（倍率、护盾、生命、冷却、保底）
        代价：无。不碰 Interface，不碰 L2

机制二  模块代码（L3 可编程）
        适用：全新机制
        代价：写一个模块。仍然不碰 Interface，不碰 L2
```

原来的问题"挂点够不够用"预设了只有机制一。加上机制二之后，"挂点不够"几乎不再是死路，
因为一个新机制可以用代码表达。

**Interface bump 只剩一种触发条件**：某项改动要让 **L2 程序看到不同的东西**。而按
[Gameplay Identity 分层草案](GAMEPLAY_IDENTITY_DRAFT.md) §2.2，**新增一个 Hook 本身不 bump**，
因为既有内容不会引用一个当时还不存在的 Hook，所以对它不可见。

残留的例外是：技能改变的是**既有 Hook 的语义**，而不是新增 Hook。这一类很小，并且可以
精确刻画（§5）。

## 3. 什么可以成为程序可见 Hook

判据：**它必须是 L2 程序在守卫、定时器或参数表达式中需要读取的值，并且它的取值范围必须能在
prepare 时静态界定。**

按前面八个案例，L2 实际读到的程序可见 Hook 只有：

```text
窗口表（等级集合）的缩放或偏移   例如 win(set).grade.early / late
Hold 宽限时间                  holdGrace
接水果盘子的判定半宽             catchHalfWidth
```

共同特征：都是**判定相关的标量**，且都是"技能希望放宽或收紧判定"的产物。

反向清单（必须是模块本地状态，不能进 Interface）：

```text
分数倍率、准确率加成、连击保底次数      折叠内部量
护盾剩余次数、生命值、复活次数          折叠内部量
技能冷却、技能层数、持续时间            模块自身状态
任何只被表现层读取的值                 属于 L4 或导出字段
```

把后者放进 Interface 会同时造成两件事：无谓的 bump 压力，以及让 L2 验证器被迫了解与判定
无关的字段。

## 4. 模块本地状态与数据化技能

模块本地状态是模块自有的有界寄存器，按
[Ruleset Fold Language 草案](GAMEPLAY_RULESET_FOLD_DRAFT.md) §3 的类型系统声明。它参与快照与
Seek，但完全不进入 L2 的任何计算。

数据化技能的形式沿用讨论记录 §2.6：

```text
技能 = (触发, 条件, 目标, 数值, 时间窗口)
```

目标分为两类：

- **派生 Hook**：按 Fold 草案 §4.7 用合成算子并入贡献集合。
- **模块本地状态**：直接读写自己的寄存器。

## 5. 触发词汇表

数据化技能需要一组封闭的触发谓词。它们都是对确定性状态与事实流的只读条件：

```text
fact(category, outcome, grade?)      事实匹配
combo >= n                           连击阈值
counter(kind) >= n                   计数阈值（已判定数、Miss 数、某 category 计数）
time(at t | every ms | within(t0,t1)) 绝对时刻、周期或区间
accuracy >= x                        准确率阈值（整数分子分母比较）
life >= x                            生命阈值
signal(kind)                         另一模块发出的信号
```

补充规则：

- 周期触发（`every`）必须声明周期下限，并计入定时器预算。
- `signal` 的投递遵循 Fold 草案 §4.7 的下一 Tick 规则，因此信号不能在同一 Tick 内形成级联。
- 谓词里不能出现浮点、随机、墙钟或宿主状态。

## 6. 时间有界贡献

限时技能（例如"8 秒内分数 1.25 倍"）落在派生 Hook 已有的合成规则上：

```text
贡献 = {
  source: moduleId
  target: hookId
  value:  Int
  window: (from, to)     绝对 Tick 区间
}
```

合成对象是**当前 Tick 处于活跃期的贡献集合**，一次算完，与加入顺序无关。窗口到期由模块的
定时器关闭，或者由启用表直接声明固定区间。

因为合成是集合运算而不是逐项递推，同一个 Tick 内多个窗口同时开合不会产生顺序依赖。这与
Fold 草案 §4.7 的规则完全一致，不需要新机制。

## 7. Interface 投影：对 identity 的一处修正

"新增 Hook 不 bump"会留下一个不一致：Interface 版本号不变，而 Interface 的内容变了。于是
同一个版本号会对应两个不同的合同。

修法与前面几处一致，**再拆一层**：

```text
Interface 版本   兼容集合："哪些能力存在"。决定内容能否运行。
Interface 投影   use-based："内容与 Loadout 实际引用了哪些 Hook、窗口表、region、grade"。
```

`JudgementIdentity` 的 ruleset 分量只覆盖**被实际引用**的部分。

**投影的单位**（2026-10-01 补充，见
[Gameplay Identity 分层草案](GAMEPLAY_IDENTITY_DRAFT.md) §4.2）：不是 Hook 标识，
也不是判定域，而是 **(hookId, 贡献来源)**，且只覆盖"生效贡献集合"与该谱面实际读取的
Hook 集合的**交集**。理由与本文 §7 完全一致——判定读到的是合成后的**生效值**，
不是声明范围，所以记录 `windowScale: Int[750..1250]` 没有意义，
记录 `{core: 1000, skillA: +150}` 才有意义。

这个单位比逐 Hook 更细（更安全），但**不随谱面规模增长**：贡献集合的规模由 Loadout 决定，
与 requirement 数、小节数无关。线性于谱面的部分是 chart 分量，不是这里。

于是：

- 新增一个 Hook 且无人引用：版本不变，投影不变，没有 Replay 失效。
- 新增一个 Hook 且被某谱面引用：版本不变，只有该谱面的投影变化。其他谱面不受影响。

这与 Gameplay Identity 草案"只覆盖影响结果的字段"是同一条原则，只是从"字段"推进到
"实际使用"。现在回到 §2.2 的结论：新增 Hook 既不改版本，也不让已有 Replay 失效。

### 7.1 与 Fold Calculus 的接口

本文写作时间早于 [Bounded Fold Calculus 提案](GAMEPLAY_FOLD_CALCULUS_DRAFT.md)。术语对应：

| 本文 | Fold Calculus | 说明 |
| --- | --- | --- |
| 程序可见 Hook | 谓词读取集合中的 `hook` | calculus §5.6 把读取集合显式写出，`hook` 是其中之一 |
| L2 程序守卫读 Hook | Pattern 的 atom / instant 谓词读 `hook` | 同一能力，作者写作位置改变 |
| 窗口集 | 窗口表 / 等级集合 | Grading 用它把 Measure 映射到等级 |
| 模块本地状态 | Fold 的 State（per-session 寿命） | 同一机制，calculus 按寿命统一 |

**§1 的结论在 calculus 下更强**，因为 calculus 把 `hook` 明确列入谓词读取集合（§5.6），
于是"技能改变判定参数"这条路径在核心里有位置，不需要额外说明。

## 8. 禁止清单

以下四类在本次设计中**禁止**，不是推迟。

```text
禁止 1  模块或技能改变播放速度，或改变 Beat 与 chartTime 的映射
禁止 2  模块或技能变换谱面（改判定域映射、重排轨道、改锚点或区间）
禁止 3  运行期生成或删除 Requirement
禁止 4  非确定效果（读墙钟、随机数、宿主状态、外部 IO）
```

理由分别是：

1. 播放倍率会改变 TimingMap 的时间轴，而判定锚点是按该时间轴量化的。倍率一旦可变，
   Beat 与 Tick 的对应关系就成了运行期状态，与"锚点在 prepare 时量化一次"直接冲突，
   也会让 `TIMING_MODEL.md` 的确定性与三种时钟一致性规定失效。
2. 谱面变换会改变 requirement 的判定域或锚点，等价于改变谱面语义，但变换参数来自会话而不是
   谱面。这会让 `JudgementIdentity` 的 chart 分量不再是谱面的属性。
3. 运行期生成 requirement 破坏了 §9 节静态验证的全部前提：活动度预算、必然结算、单事件代价
   都依赖 requirement 集合在 prepare 时已知。
4. 非确定效果会让折叠不可复现，前面所有设计的前提一起失效。

**禁止 2 的一个后果需要明说**：MIRROR、RANDOM 这类"轨道重排"型玩法选项在当前设计中
**不存在**，不属于"本阶段不做"。将来若要恢复，它不是一条模块能力，而需要作为**会话级的
冻结声明**独立决策：在 prepare 前确定、进入 identity、并有自己的 capability 位。做成模块
会与禁止 2 直接冲突。

禁止 1 同样排除"练习模式变速"。若将来需要，正确做法是把它做成**独立的一次 prepare**，
以新的倍率重新准备会话，而不是在会话中途改变倍率。

## 9. 与 L2 静态验证的接口

本设计对 L2 验证器提出的要求只有一条，而且已经写在其草案里：

```text
验证器读取 Interface 声明的 Hook 及其静态取值范围，不读取 L3 的实现。
```

因此"模块可以自由扩展"与"L2 验证在 prepare 时完成"并不冲突：无论 Loadout 启用了多少模块，
L2 程序看到的 Hook 集合与取值范围始终由 Interface 决定，且与 Loadout 无关（Fold 草案 §4.6）。
唯一的例外是包级声明 `interfaceVariesWithLoadout = true`，那是已计价的逃生通道。
