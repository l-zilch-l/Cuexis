# 引擎冻结合同草案（定点表、缓动曲线、判定语义版本）

状态：candidate（设计草案，未接受，未实施）

更新日期：2026-10-01

本文回应四项已登记的待决项，它们的共同点是**随引擎冻结、并进入 identity 的 engine 分量**：

```text
Identity §10.2 / §13.4   判定语义版本的清单，以及它与 check_version_gate.py 的合并
Identity §11             定点表的统一登记点与版本管理
Program IR §10.7         定点表的集合与版本（与上一条同一问题）
Program IR §10.2         缓动（Ease）曲线的最终集合
```

分散的后果与预算文档当初的情形相同：每加一张表就多一处要记得写进身份，
漏一处就是 §2.1 意义上的静默分叉。

## 1. 一句话定位

```text
引擎冻结合同 = 一组"随引擎版本冻结、内容可引用、判定可读"的常量数据与语义版本标记。
它们全部进 JudgementIdentity 的 engine 分量。
```

判据来自身份草案 §2.1：**改了它会不会改变判定结果。** 下列四类都会，因此都进：

```text
定点表          角度表、缓动曲线、将来的 exp / sinusoid
量化单位        位置 1/1024 或更细、时间 1 微秒、角度 1/65536 圈
判定语义版本    一个只增不减的整数，标记"哪些规则算判定"
仲裁与折叠的求值顺序   t+1、同 Tick 内的固定顺序
```

最后一项容易被漏掉。它不是"数据"，但它改变结果，所以它与定点表同类：必须有一个版本标记，
且这个标记必须在代码改变时被人为提升。

## 2. 定点表的统一登记点

**裁决：一张表清单一处声明，表本身的版本不是一个可变的数字，而是名字的一部分。**

```text
tableRegistry := [TableEntry]

TableEntry {
  tableId      稳定标识。一旦发布，语义永久冻结
  kind         table | formula
  domain       该表服务的量化域与单位（角度 1/65536 圈、位置、无量纲 0..1）
  resolution   若 kind = table：采样点数与插值方式
  errorBound   该表逼近其名义函数的最大误差，以量化单位表示
  vectors      一致性测试向量集合的引用
  capability   引擎缺少该表时，引用它的内容稳定拒绝
}
```

`vectors` 不是可选项。整份设计的立足点是跨平台逐位一致，而定点表是唯一"由人写下的数字"
参与判定的地方。没有一致性向量，就无法区分"引擎实现正确"与"实现不同但看起来对"。
每个条目必须带一组覆盖定义域端点与拐点的向量。

## 3. 表的身份是语义内容，不是可变版本

Identity §11 留了一个问题："同一张表是否允许多版本并存，还是永久冻结、只能新增。"

**裁决：这个问题被消解，而不是被回答。** 一条表目的 `tableId` 就是它的语义内容，
改进不是"新版本"，是"新条目"。

```text
错误做法   angle.v1 -> angle.v2，版本号提升，引用 v1 的内容需要迁移
正确做法   angle.unit65536 与 angle.unit65536.approx 是两个条目，永久并存
```

三条理由：

```text
1  并存的必然性   优化过的表与原来的表可能永远都需要：老内容要保持逐位可复现，
                  新内容可能想要更高的精度。二者不是替代关系，是共存关系。
2  失效的不可接受 若改进使版本提升，全部角度相关 Replay 立即失效。
                  而"换一张更准的三角函数表"不该让玩家昨天的成绩作废。
3  能力位的自然性 capability 按 tableId 声明，天然是"引擎有没有这张表"，
                  而不是"引擎的这张表是不是这个版本"。
```

由此得到一条**代价声明**：引擎的表集合只增不减，每一张表都要永久维护、永久测试。
这是可控的，因为表的规模本来就有上界（§6）。

**内容如何引用**：按 §表 的 `tableId` 引用，不引用"版本"。因为 id 即语义，不需要第二个轴。

## 4. 缓动曲线的裁决（回应 Program IR §10.2）

Program IR §5.4 列了线性、二次、三次、回退、弹性五类作为起点，待决项问最终集合。
裁决分两步：先定**准入判据**，再定**起始集合**。

**准入判据**：

```text
一条缓动曲线可以进入引擎，当且仅当它有一条闭式整数求值，
其误差可静态界定，且不调用宿主数学库。
```

这直接排除 `elastic`（衰减正弦，需要 `sinusoid` 表）与任何"看起来平滑"的分段样条。
被排除的曲线不是永久禁止，而是**等它的表到达**：`sinusoid` 一旦进入 §2 的登记表，
`elastic` 就可以作为引用该表的条目加入。

**起始集合：九条，全部是多项式或有界常数。**

```text
linear
quadIn      quadOut      quadInOut
cubicIn     cubicOut     cubicInOut
backIn      backOut
```

`inOut` 是既有的派生形式（前半段用 in、后半段用 out），因此九条里只有七条是独立实现。

**`back` 需要一处显式规定**：它的过冲常数（常见的 1.70158）必须以定点字面量写入登记表，
不能由实现自行选取。选一个数就是选定了一条曲线。

**求值规则**（与 §5.5 的"量化一次"一致）：

```text
输入      归一化进度 p ∈ [0, 1]，以 1/65536 为单位的整数
输出      同一单位的整数
取整      向偶舍入，只做一次
禁止      在同一表达式里串联多次缓动
```

最后一条与 D6（几何运算取整）的处置同形：串联两次缓动会让误差叠加，而"叠加多少"取决于
实现。要更复杂的曲线，就写一条新的闭式曲线，而不是把两条串起来。

**缓动曲线同时是 `Ease` 分段类型与 `frame` 的摆放曲线**，两处共用同一个登记表条目。

## 5. 判定语义版本的清单（回应 Identity §10.1）

Identity §10 要求"一份什么算判定语义的清单"。裁定如下，范围是**参与折叠且结果可见**的部分：

```text
在清单内（改动需要提升判定语义版本）
  窗口比较与等级判定的边界规则
  锚点量化（Beat -> chartTimeMs -> Tick 的换算与舍入方向）
  仲裁：候选集计算、排序键、lock 与 fanout 的语义
  fold 求值：处理器顺序、同 Tick 内的推进顺序、信号的下一 Tick 投递
  谓词读取集合的语义（本 requirement / ctrl / level / hook 各自读到什么）
  采样语义：`every` 的相位锚定规则、两套格点的相位关系
  定点表：全部条目（§2）
  缓动与 frame 求值：量化点与取整规则
  连续量重采样：格点定义与插值方式
  数值模型的量化单位与舍入模式

不在清单内（引擎升级不影响判定语义）
  渲染后端、着色器、呈现路径
  音频输出、解码、按键音播放时机
  日志、诊断、错误信息文本
  prepare 的容量与代价门限（见预算草案 §5：收紧是兼容性破坏，不是 identity 变化）
  宿主适配器的实现（它只影响 L1 的输入形状，而 Replay 记录规范化之后的流）
```

最后一条与身份草案 §6 一致，但要写清它有一个例外边界：**适配器可以改变判定结果，
如果它改变了归一化后的事件流。** 那不叫"适配器实现差异"，叫"输入映射变化"，
按 §6 属于信息性元数据，不进校验门。两者必须分清楚，否则"L1 不进 identity"会被误用为
"L1 怎么改都行"。

## 6. 门禁与放行开关的传递路径（回应 Identity §13.4）

Identity §10 已指出正确的机制原型：`tools/check_version_gate.py` 对 SDK API 版本采用
"一经变更即需显式放行"的模式。判定语义版本照此办理。但该脚本有一处**已知的 Stage 7A 阻塞**
必须一并解决：

```text
症状      开关没有工作流传入，而检查器从 base commit 取出运行，候选分支无法自行开启
```

**正确做法是一条三来源原则**：

```text
执行器   从 base commit 取        防止候选分支修改检查器来自我放行
声明     从 candidate commit 取    变更声明必须出现在 PR diff 里，可被审查
放行     从 workflow 事件取        标签、环境或人工批准，不来自候选分支的代码
```

三者分开，缺一不可：

```text
只做前两条   候选分支写一句"我改了判定语义"，门禁就通过 —— 等于没有门禁
只做一、三条 声明不在 diff 里，审查者看不到改了什么
只做二、三条 候选分支可以改检查器，或改判定语义而不声明
```

**声明的形式**：一个提交在候选树里的机器可读文件，逐条列出本次改动属于 §5 清单的哪一项。
它同时是 PR 审查清单的人工入口：

```text
judgementSemantics {
  version          提升后的版本号
  changes          [ { item: <§5 清单项>, note } ]
  allowToken       由 workflow 注入，不写在文件里
}
```

**放行的粒度**：按"本次变更声明的清单项"放行，而不是一个全局布尔。全局布尔会让声明
退化成形式；按项放行使"改了采样语义但只声明了窗口比较"这类错误在门禁处暴露。

这条设计同时解决讨论记录里记录的另一个同类问题：**Stage 7A 的开关传递路径需要先修好，
再让判定语义版本搭同一班车**，否则会把同一个坑复制一次。

## 7. 与 identity 的关系

```text
engine 分量  = 判定语义版本 + 全部定点表条目的 (tableId) 集合中**被实际引用**的部分
```

"被实际引用"沿用 Interface 投影的 use-based 口径（身份草案 §4.1、Skill Hooks §7）。
理由是 D8 已经裁决的同一件事：**声明范围不进投影，实际生效的值进投影。**

因此：引擎新增一张表且无人引用 → 版本不变、投影不变、无 Replay 失效。
引擎新增一张表且被某谱面引用 → 版本不变、只有该谱面的投影变化。

这与"表的身份是语义内容"（§3）是同一条原则的两个侧面。

## 8. 待决

1. ~~`judgementSemantics.version` 的初值与提升粒度~~ 已裁决：**全局一个数字，加逐项变更
   声明**。初值 `1`。理由是分量已经足够细（engine / ruleset / chart / session），再按清单项
   各自编号会让比对逻辑膨胀到"变更矩阵"的量级，而矩阵的每一格都不会单独带来诊断价值。
   逐项声明（§6）已经承担了"变更了什么"这个问题。

2. ~~一致性测试向量是否随引擎发行~~ 已裁决：**随测试工程发行，不进入运行期**。
   理由：向量用于证明"这张表的这份实现是正确的"，而这类证明属于 CI，不属于运行时自检。
   运行期自检能做的只是比较 tableId，而 tableId 已经是身份的一部分（§7），重复检查没有收益。
   代价写在明处：**发行包不含向量，因此终端用户的引擎无法自证表实现正确**。这可以接受，
   因为表在 CI 里被验证过，而运行期无法修复一张错的表。

3. `back` 的过冲常数与 `sinusoid` 表的采样点数需要具体数值，属实测范畴。**保持不变。**

4. ~~§5 清单里"仲裁与折叠的求值顺序"的归属~~ 已对齐，分界是**谁声明的顺序**：

   ```text
   ruleset 分量   包内的处理器顺序、模块顺序、折叠表覆盖关系
                  —— 由包清单声明，包的内容 hash 覆盖它（Ruleset Fold 草案 §4.7）
   engine 分量    同 Tick 内四个阶段的推进顺序（激活 / 定时器 / 输入 / 折叠）、
                  信号的下一个 Tick 投递、Hook 快照的生效时点
                  —— 由引擎定义，任何包都不能声明或覆盖
   ```

   分界判据正是"内容能不能声明它"：**包的作者能改的进 ruleset，改不了的进 engine。**
   这条判据同时解释了为什么包的顺序要进包 hash 而引擎的顺序不要——后者对所有内容一致，
   改它就改了一切。

5. ~~判定语义版本的提升是否需要同时提升 SDK API 版本~~ 已裁决：**不需要，但两者有一条
   单向关联**。

   ```text
   SDK API 版本      覆盖公开头文件与安装包暴露的表面。改它需要 --allow-sdk-api-change
   判定语义版本      覆盖结果产出行为。改它需要 §6 的三来源放行
   两者独立          一次纯粹的判定语义修改（例如修正锚点量化）通常不动任何公开头文件
   ```

   单向关联是**流程上的而不是版本号上的**：判定语义的提升必须是一次**发行事件**，
   不得发生在同 SHA 的复验里，也不得混在"仅文档"或"仅 CI"的变更中。
   理由直白：判定语义变更会让已有 Replay 失效，玩家需要事先知道，因此它必须出现在
   发行说明里，而不能是某次复验顺手带上的一行。

   **反例（用来验证这条不会被误用）**：若某次修改既改了判定语义又改了公开头文件
   （例如为了暴露新的诊断码而改了头），它需要**两次放行**，两次的审查内容不同——
   前者看"结果变了多少"，后者看"表面变了多少"。把两者合并成一次放行会让其中一个
   失去审查。
