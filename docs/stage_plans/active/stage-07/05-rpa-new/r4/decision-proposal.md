## 1. 目标与推荐组合

本方案把技术实施交给代理连续完成，把产品范围、机器使用、预算接受与退出决定集中交给 owner。
owner 选定组合后，常规检查、修复、构建、工具登记、获准测量与报告不逐步请求确认。
完成一轮工作包括如实交付超界或缺证据结论；不承诺通过所有门，也不自动放宽门槛。

推荐组合：**D1-B、D2-A、D3-B、D4-B、D5-B、D6-A、D7-A**。
若机器不能连续占用，只把 D2 改为 B。接受本组合后仍保留两次集中接受点：
正式运行前的新增具体预算/生产参数表，以及证据齐备后的最终退出决定；需要实体操作的项目集中安排。
若 SDK Version Gate 要求绑定最终 SHA 的 owner 评论，则在该 SHA 确定后单独提供准确内容。

## 3. D1：本轮独立交付范围

| 选项 | 交付与优点 | 成本与限制 |
| --- | --- | --- |
| A：只做准备 | 缺口清单、集成方案、工具与注册草案、功能回归；机器占用低 | 正式性能、设备和内存结论仍缺失，后续还要再次授权运行 |
| **B：完成全部可自动执行的 R4 工作（推荐）** | 合同内必要集成/缺陷修复、工具、适用本地矩阵、P0–P7 reference 单元、新身份 P8、分域内存、自动设备验证与完整接受包；适合连续推进 | 新预算须先接受；人工设备观察和最终退出仍独立；无法取得的门保持缺证据 |
| C：本轮同时追求完整生产接受 | 在 B 上补齐生产 Scheduling/Tail/容量等 profile、实际用户设备及故障/AV 同步验证；覆盖最完整 | 产品决定与设备配合更多，可能需要额外硬件/测量手段；不能仅凭本机 reference 关闭生产门 |

D1-B 的运行清单由代理从已接受 P0–P8 矩阵展开，记录每项适用性、对照、内容、规模与预算来源。
P0–P7 沿用原对应负载，不用新小夹具替代原矩阵。P8 是新源码/工具/fixture 绑定下的
40K low/high 各一次完整规模单侧取证，不重跑或覆盖旧 invocation，不改成九对，不要求 40K 达到 240 FPS。
缺少合法 A、profile 或工具门的单元先补齐；不能重建 A 时披露阻断，不能用 R3/Q4 替代共同 A。
普通性能使用 Release STATIC、candidate ON、普通 allocator；诊断计时及内存观察另建树/另进程。
自动构建/功能测试与性能采样分时执行，避免本机后台构建污染采样。

R4 默认不新增性能机制。必要的协议集成与缺陷修复由代理处理；若必须新增 owner/线程、
公共契约或性能架构才能达标，先提交最小独立变更方案及原始失败证据，不能默认为 D1-B 已接受。

## 4. D2：设备、时段与人工参与

| 选项 | 优点 | 成本与限制 |
| --- | --- | --- |
| **A：本机连续专用窗口（推荐）** | owner 接受后，在本次持续任务期间允许 CPU/GPU/声卡长时使用和前台测试；排程简单，干扰较少 | 采样时用户需暂停操作、接交流电并保持端点稳定；会出现窗口和声音 |
| B：仅夜间设备窗口 | Asia/Shanghai 每日 00:00–08:00 允许前台 GPU/audio；其余时段只做实施和普通构建回归，对日常使用影响较小 | 总工期延长；不能赶在窗口结束前缩短正式组，需估算完整单元后再启动 |
| C：仅 CPU/headless 自动推进 | 不占前台或音频，实施和 CPU 证据可先完成 | GPU/audio、完整设备验证和相关最终接受保持缺口 |

设备 reference 优先沿用已接受的 **RTX 4060 Laptop、1280×720 窗口、VSync ON、
240 Hz、固定 Senary Audio 端点、gain 0.35**；当前桌面分辨率无需改成 720p。
1080p/VSync OFF 容量诊断另列 profile，不混入本组，也不因本方案自动重开容量扫描。
正式进程启动前再次确认实际 GPU、驱动、刷新率与端点；当前电源方案保持并冻结，
CPU 亲和性按既有拓扑策略，不能按已测快慢挑核。供电、前台或端点条件不成立时停止启动该组。

代理可自动执行软件故障注入、窗口/焦点脚本、设备 API 检查和 GPU/audio 遥测；
实体 DFJK/Hold、听音、物理拔插与精确 AV 同步按合同逐项判别所需人工/仪器，集中形成一次操作清单。
脚本事件与软件模拟不替代相应的实体证据；没有该证据则如实留空。
夜间选项由本次活跃任务排程；若任务不在运行，不能保证届时自动启动。
未完成单元不因跨日自动获得新样本身份。

每个独立排程的 A/B 单元仅机器热身与两个最小窗间隔已需
18 × 30 s + 2 × 600 s = **29 min**，还不含实际采样、会话预热、构建和准备。
代理完成单元清单后再给总时间估算，不用九对总数估算整张矩阵。

## 5. D3：内存 caps 与生产参数怎样接受

| 选项 | 优点 | 成本与限制 |
| --- | --- | --- |
| A：仅验已有正式 profile | 直接沿用已接受数值，新增预算决定最少 | B0 仅有 1/200/201 参考规模；64/2048/40K 和未覆盖域不能据此通过，完整 R4 留缺口 |
| **B：先完成静态推导，再一次接受具体表（推荐）** | 代理核对容量、真实类型尺寸、别名/生命周期及超限行为，提交每域 count/bytes/age 和总范围；依据可审查 | 正式新增 profile 运行前需要一次集中裁定；超出已接受表须形成新版本，不能事后调高 |
| C：owner 先定产品总预算，再反向设计 | 能把内存目标与产品设备规格直接绑定 | 目前尚缺完整构成和目标硬件分布；较紧总额可能要求新设计并扩大范围，较松总额不能证明各域有界 |

D3-B 先产出全表，包含 World/current/candidate/scratch/index、payload/attempt、
journal/receipt/command/history、prepare-only、decoded heap、CPU owning 结果、GPU/audio、
保留代数、各域 age、active/Close 后持有旧 handle/最终释放三阶段和各类排除项。
CPU requested/storage、进程 commit/working set、GPU 实占分开；未知项标记缺证据而非 0。
同时列出 Scheduling/TailProfile、时钟误差、容量与超限行为中仍需生产决定的参数，集中裁定。

推导来源是声明的容量、实际结构与明确设计余量；有限诊断可用于核对计数/覆盖和开销，
但不能由观测峰值倒填 caps，不能给缺乏上限的 profile 启动正式采样。
B0 冻结文件保留，新 profile/caps 单独版本化。

以下只是沿用 B0 系数的**部分域算术示例**，不是本方案请求接受的完整 caps：
state 部分 = 13,312 × N + 327,680 B；host 已覆盖非 state 域合计为 67,208,192 B。

| N | state 部分 / B | 加 host 已覆盖域 / B | 再加原 1/8 声明余量 / B |
| --- | ---: | ---: | ---: |
| 64 | 1,179,648 | 68,387,840 | 76,936,320 |
| 2,048 | 27,590,656 | 94,798,848 | 106,648,704 |
| 40,000 | 532,807,680 | 600,015,872 | 675,017,856 |

这些数不覆盖完整 prepare/decoded/GPU/audio 等成本，当前布局和容量适用性也尚待审计。
因此既不能把约 644 MiB 当作 40K 总上限，也不能凭“128 MiB 已取消”自动选择 512 MiB 或 1 GiB。
选择 B 是授权推导和有限诊断，不是预先接受未知数字；表齐备前其他不依赖新增 caps 的工作继续。

## 6. D4：失败后的独立处理范围

| 选项 | 优点 | 成本与限制 |
| --- | --- | --- |
| A：每个正式失败都回来裁定 | owner 掌握每次后续动作 | 中断频繁，工具/环境缺陷也会阻塞进度 |
| **B：有限修复后新登记（推荐，需本次显式接受）** | 代理自行定位并修复合同内代码/工具缺陷，运行必要回归；有可验证修复时可启动一次全新正式单元 | 需要严格控制身份和样本；旧失败永久保留，第二次仍失败则提交处置包 |
| C：只完成固定测量并交付结论 | 测量成本与次数最可控 | 发现可修复问题也留待下一轮，通常无法一次完成接受包 |

D4-B 的新增授权不是“补跑一个失败进程”：

1. 身份/执行/语义错误按现行规则立即停止受影响单元；性能超界完成固定组后裁定；
   环境噪声记 inconclusive。缺字段、身份错和性能超界不能事后改名为 invalid-process。
2. 可独立修复合同内缺陷；针对同一问题最多安排两轮有限诊断，每轮先登记问题、组数、
   时间上限和停止条件。普通正确性回归按修复需要执行，不属于补充性能样本。
3. 每个受影响正式单元最多一次新的完整登记，须有可验证的代码/工具/环境处置、
   全新 binding、冻结样本与顺序；不与旧结果合并，不择优选旧/新样本。
   每个单元的额度跨版本累计，不通过改名称重置。
   此额度仅用于对应的 A/B 或 B-only 固定组；P8 仍是 low/high 各一次，额外 P8 运行另行裁定。
4. 没有修复或明确环境变化的 inconclusive/性能超界不自动重开；原单元的慢值保留。
   不改变 1.10、15%、20 ms 等阈值，不复活 R3c，不新增性能机制作为隐含救场。
5. 产品行为/限额发生变化后重建最终候选身份，重跑受影响门；最后本地/hosted 验证仍绑定
   共同候选 SHA。需要第三轮正式单元、改变合同或新硬件时才集中提交后续裁定。

有限 pilot 在对应工具与 profile 准入后按原协议登记，pilot 样本不进入正式组。
ETW、新设备和新增负载类别不由本方案默认扩大授权。

## 7. D5：提交、远端与 CI

| 选项 | 优点 | 成本与限制 |
| --- | --- | --- |
| A：本地修改与提交 | 远端不受影响，可完成本地证据 | 无法完成新的 hosted 门；最后还需推送授权 |

| C：更新既有 Stage 7 PR | 保持一个总 PR，可沿已有审查路径推进 | 混合 R3/R4，旧批准可能失效，影响已有审查与候选身份；须先核实当前远端与 PR 状态 |

本地工作流源码显示 Linux Quality、Windows MSVC、Windows MinGW 支持任意分支 push，
因此 D5-B 可先获得 hosted 证据，无须立即更改 PR #32 或推送 master。远端 PR 当前状态本次未查询。
推送前核对远端祖先关系；本地基线已含前轮收尾提交，推送新分支会一并使其在远端可达。
R4 审查差异以记录的 R3 基线为起点；面向 master 的 PR 必须明确其是否已包含该基线。

D5-B 授权正常提交、推送新分支和运行/读取 CI；不包括 force-push、合并、发行、删除
archive tag 或替 owner 发布批准。现有 archive tag 保留，不列为 R4 开工前置。
SDK API 仍为 0.9.1 不能保证无需新评论：实际 PR base/head 的版本差异和精确 SHA 决定
Version Gate；需批准时由代理生成完整记录，owner 明确授权后按既有机制发布。

## 8. D6：同 SHA 与报告提交策略

| 选项 | 优点 | 成本与限制 |
| --- | --- | --- |
| **A：沿用同 SHA（推荐）** | 不修改现行规则；产品、工具、版本/profile 稳定后冻结 C，本地矩阵与 hosted 均验证 C | 冻结后变更会增加重验；报告的后继提交必须明确证据仍针对 C |
| B：预先允许纯报告 delta | 允许 C 后追加白名单报告/证据而不重跑产品门，减少纯记录改动的成本 | 属于新 owner 例外；须逐文件/hash证明无产品、工具、配置、fixture、profile、版本或门禁变化，不能借用 R3 先例 |
| C：允许含平台修复的受控 delta | 遇跨平台修复可少跑部分本地矩阵 | 语义等价判断成本大，易重复 R3 争议；R4 身份证明更弱，不推荐 |

D6-A 下先做平台预检，再冻结最终 C 并跑正式本地/hosted。结果可归档到后继报告提交 E，
但证据只能声明验证 C；若将 E 作为新的最终接受/合并候选，必须按现行规则重新冻结和验证，
不能默认“文档变更已豁免”。发布与合并不在本轮推荐授权内。
SDK Version Gate 的批准记录由实际候选 SHA/tree/base/日期约束，不能提前填未知值或复用旧批准。
