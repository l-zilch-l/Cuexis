## 3. 路线选择与未选替代

选择一条 Player 执行线，是因为既有产品边界已把 Player 与 Studio 定位为 Playback 的宿主，
且禁止两者各自建立私有 Chart → Runtime 路径（ADR 0027）。代码已有 `PlaybackSession::commit`，
候选执行提交也能在校验宿主证明后复用该入口；正式帧交付已有 `submit` / `present`。
这些接缝可承载收敛方向，同时保留普通播放与实时游玩的模式差异。

以下替代没有选作长期路线，记录其取舍供继续讨论：

- **长期保留独立实验宿主**：短期可保留执行试验的边界；代价是继续维护两套会话控制、时钟和交付协调，
  与 Player 承接实时判定的方向不一致。现有分离可作为过渡事实，不能据此推定最终边界。
- **由实验宿主取代 Player**：可直接沿用实验执行协议；代价是把候选执行入口变成普通产品入口，
  混合普通播放与 test-only 玩法适配的生命周期。长期产品宿主仍是 Player。

以上是路线讨论依据，不是具体 API 决定或实施批准。

## 5. 一次性结构代价与验收方向

一次性代价需要在后续设计中逐项盘清，不在此给出工期或实施批次：

- 归并 Player 的会话生命周期与播放控制接线，同时保留 `PlaybackSession` 的 prepare/commit 校验和失败原子性。
- 将音源位置、设备校正、Chart offset 与 chart time/tick 的映射收口到 Playback，避免各宿主重复换算。
- 将实时输入、时钟过期、帧交付回执、seek/replay 状态接到共同执行骨架，并保留失败恢复边界。
- 处理旧渲染兼容入口与 `submit` / `present` 正式交付路径的关系。
- 共享播放行为每次改变时，分别验证普通播放和实时游玩。

验收方向至少覆盖：

- 非零 offset 与设备校正同时存在时，source position、chart time 和 judgement tick 的映射一致，校正不重复应用。
- 按 D-21 验证正负半 tick 取偶、溢出和量化后无效窗口被拒绝。用四拍内从 120 线性变速至 240 BPM 的案例：
  第 2 拍约为 `810930.216 μs`，把该拍用作离散表现和判定的共同边界，验证两侧均在 tick `810930` 生效，
  不因反查拍位仍小于 2 而推迟。另覆盖停顿边界、旧成品按原基准复现，以及作者编译器与运行时内核在构建图中的实际分离。
- 暂停/恢复不推进暂停期间的判定时间，也不重放已消费输入；seek 不伪造目标之前或未来的输入历史。
- 帧丢失、未交付或交付过期时，不因重试/重放帧重复判定；帧交付回执与实际 `submit` / `present` 结果一致。
- 按 D-24 验证输出准备失败时判定状态未推进。无输入跨过窗口终点时，当次 `advance` 交付一次 `Miss`；
  在交付后注入表现或渲染提交失败，确认判定和计分不重算，下一次推进后宿主持有的结果仍有效，同一事件不再次交付。
- Reload 按 D-13 验证成功切换前保留旧内容与已准备音频；分别记录准备、设备接入、提交及切换后故障，
  不把数据保留描述成恢复了旧局进度或设备状态。
- 纯播放可正常准备、更新、渲染和 seek，且不创建或启动 Judgement。
- 实时游玩保留输入采集、时钟有效性校验、判定与恢复行为；两种用途都覆盖共享改动。

## 6. 已接受的行为边界与候选合同入口

下列共识是本轮技术细化的边界。一次采用的候选输入见[运行与时间合同](contracts/runtime-timing.md)、[渲染、Player 与写回合同](contracts/render-player-writer.md)和[后继成品合同](contracts/prepared-artifact.md)。

Packed、CXT v2、Chart v5 的正式发行组合仍由 Stage 8 在原范围决定。CXC v1 已接入；Chart v1/v2/v3 Reader 与显式 v1/v2/v3→v4 迁移继续受 ADR 0041 保护。

- **Studio 预览与实机游玩（未来边界共识）**：Studio 预览是纯播放，不创建实时 `Judgement`，不记录成绩或连击。首版实机从头判定；新谱须重新载入并从头开局。未来可在同一实机路径从指定点开始或跳过中段：被跳过的未决音符按普通 `Miss` 结算并正常计分、影响连击；音符起点早于跳转目标，且音符跨越该目标的未决长按，也直接判 `Miss`；已完成结果不改写。防止谱面失败只作为未来选项，不改变上述 `Miss` 语义。以上是未来边界共识，不是实施批准；Retry/Reload 见 D-13。

### 会话控制串行化（D-09：已确认目标与验收场景，非现状或实施授权）

D-09 确认每个会话由一个执行线程串行推进播放与可选实时判定；普通播放不创建或推进 `Judgement`，实时游玩由同一执行线程推进 Playback 与 `Judgement`。`judgement` 不向 Player 反向发起控制。UI、窗口、渲染、I/O 与音频设备不强制共用该线程，相关操作仍遵守各自既有 owner。技术部署与迁移见[会话控制合同](contracts/render-player-writer.md#所有权暂停与收尾)，验收见[会话任务](tasks/T-14.md)。

以下是目标验收场景，不是已实现行为：

- **用途与串行推进**：普通播放即使内容可玩也不启动判定；显式请求且校验通过的实时游玩才启动判定，Playback 与判定在该会话执行线程上串行推进。共享改动分别检查两种用途。
- **并发 Pause**：运行中的会话同时收到两个 Pause 请求时，共享一次冻结、一个判定边界和同一结果；第二个请求若在操作完成前到达，则等待并共享该结果。各自来源仍单独登记。所有必要参与方确认成功后才可报告成功；任一参与方失败时不得报告成功。
- **重复与独立暂停原因**：Pause、Resume 是明确命令，不是 Toggle。已暂停时再收 Pause，不改变时间、输入或挂起判定；同一来源重复 Pause 不叠加。玩家手动暂停、设备中断等独立持久原因分别解除；仍有另一原因时，解除其中一项不得恢复播放。
- **恢复后的迟到操作**：Resume 后，旧 Pause 操作及旧会话回执均不能重新暂停或改变结果；Resume 后真正发起的新 Pause 请求仍可暂停会话。回执只确认既有操作，不构成新的暂停意图。

### ADR 0046 的候选部署（与 D-09 目标分开）

[ADR 0046「决定」第 1、3 条](../../../adr/0046-realtime-playback-coordination.md)记录了 B 职责边界及初始 P-B 部署：主线程承载 D1 捕获、D5 GL 与 D6 协调，Playback worker 共置 D2 执行和 D3 表现，audio worker 独立。该 ADR 标注当前分支为 candidate 实施、尚未发行；这项候选现状不证明 D-09 已实现，也不裁定 D-09 所留的未来部署与迁移顺序。

现有 [`ExecutionHost::pause`](../../../../app/player/src/execution_host_frame.cpp) 在非 running 或操作冲突时会拒绝请求；这是代码现状，不能据此把上面的幂等、合并与共享结果目标描述为已实现。

### 可复用会话控制与 Player 外壳（D-10：未来验收目标，非现状或实施授权）

D-10 要求将可复用的会话控制实现与 Player 外壳分开；Player 和测试必须使用同一份实现，不设测试专用控制实现。该实现须能脱离窗口、CLI 解析与 SDL 主循环独立编译，运行时判定内核 `judgement` 仅依赖 `core`。未来合并时，构建约束与以下行为测试都是必跑门槛。

- 测试直接提供内存可玩谱面，驱动 Player 实际使用的同一份会话实现；不创建窗口、不解析 CLI、不模拟按键，并可替代外部设备。
- 普通播放完整经过播放、Pause、Resume，不创建也不推进判定；显式请求且校验通过的游玩使用相同 Pause/Resume 规则，并运行判定。

以上是 D-10 的未来验收目标，尚未实现或运行验证。不扩大 D-05、不新建共享库、不冻结 Studio 公共 API。D-10 当时未裁定 `ExecutionHost` 是否退役或故障恢复；后续共识分别见 D-11、D-12、D-13，不回写扩大 D-10。

以下 D-11 至 D-15 均为未来目标，不是已运行验证，也不改变 D-05。

### Retry、Reload 与失败（D-13：2026-11-19 owner 已确认的未来设计）

**目标按键（已确认，拟实施）。** Player 的 `R` 触发 Retry。Reload 键位和启动来源、条目选择边界见 [Player 命令与启动](contracts/render-player-writer.md#命令与启动)。D-13 不改变 D-05 或实施授权。

**源码现状。** 普通 Player 的窗口 `R` 映射为 `Reload`：重新读取启动配置所确定的当前来源并执行 `RestartAtZero`；尚无独立的 Retry 按键。启动来源由 `--chart`、`--project`、`--cxc` 之一确定，均未指定时使用默认工程（[选项解析](../../../../app/player/src/player_options.cpp)、[启动默认值与来源端口](../../../../app/player/src/player_app.cpp)）；当前 `R` 接线见[按键绑定](../../../../app/player/src/player_assembly.cpp)、[命令映射](../../../../app/player/src/player_control.cpp)及[来源解析与重载](../../../../app/player/src/player_control_transaction.cpp)。内部 [`PlayerCommand`](../../../../app/player/src/player_control.hpp) 可携带显式 `PlaybackSource`；这不意味着窗口支持选谱或无谱空会话已接受 Reload。

**2026-11-20 续议（owner 已接受，实现未开始）。** 会话按 D-15 跨局保留当前已解析的不可变内容和已准备且健康的音频。Owner 接受这部分局间内存开销，优先让 Retry 免于重复加载。本续议不改变 D-05 或实施授权。

**Retry** 复用当前已解析版本和健康的已准备资源，初始化新局，从零即播；Playing、Paused、Stop 或自然结束后均适用。对仍可复用的内容不重读、不重解析、不重解码，也不建立源字节快照缓存。Retry 与 Reload 共用新局初始化逻辑，重置播放游标，不继承旧局输入历史、成绩、连击或判定进度。设备或其他必要条件未就绪时不播放、不先行推进判定；必要时恢复或重新接入设备。普通播放始终不创建或推进 `Judgement`。

**Reload** 每次都重新读取同一启动来源，即使内容未变。同一会话串行处理 Reload，同一时刻只允许一轮进行。必须遵守以下顺序：

1. 停止旧局播放、音频输出和判定推进，保留当前版本 A 的不可变内容及已准备音频。
2. 独立准备 B：校验内容和该模式的玩法要求，加载必需资源并准备音频（需要时解码），完成该模式的判定初始化和必要的设备接入确认。普通播放无 `Judgement`。检查每一步的 `Result`；资源不足时报告失败，禁止提前卸载 A 来腾空间。
3. 只有 B 验证、加载和必要设备接入均成功后，唯一会话控制者才切换当前版本为 B。B 从零暂停、无声且不推进判定，等待显式 Play。旧操作不再引用 A 后释放 A，不积累历史版本。
4. 成功切换前任何失败均报告实际原因及阶段，只清理本次 B 尝试，保留 A 的不可变内容及已准备音频，保持停播和停止判定；不得自动续旧局或把 B 显示为就绪。显式 Retry A 仍以设备就绪为条件；设备受影响时须恢复或重新接入。保留 A 的数据不保证旧局进度或设备状态回滚。成功切换后发生故障，报告实际阶段并停止播放和判定推进；按实际当前版本处理，不承诺撤销已完成的切换。没有可用版本时保持无谱、停播；这不表示已实现空会话 Reload。

- 纯渲染资源 rebuild 按 D-14 恢复当前已加载版本和本局状态。首版命令、失败处理和会话部署见[候选 Player 合同](contracts/render-player-writer.md#p4player-生命周期)。

以下场景用于未来验收，不表示已实现：

- **Retry 已加载版本**：分别从 Playing、Paused、Stop 和自然结束后的 A 按 `R` 发起 Retry，同时把来源改为 B；验证复用 A 的已解析内容和健康音频，不读、解析或解码可复用资源。必要条件就绪时直接从零播放，无需 Play，也不带入旧局进度；条件未就绪时不启动播放、不推进判定。
- **改谱重载**：正在播放或暂停 A 时，同一来源改为有效的 B；先确认 A 停止推进和输出，保持 A 数据存活。发起重叠 Reload，确认同一时刻只有一轮准备。B 的校验、资源加载、模式初始化和必要设备接入均成功后才切换；B 在零点暂停、无声且不推进判定，直到显式 Play。旧操作不再引用 A 后释放 A；B 不继承 A 的局状态。
- **来源未变重载**：正在播放或暂停 A 且来源仍为 A；Reload 仍重读、解析并校验来源，成功后同样以该版本开从零、暂停、无声的新局，不推进判定，直到显式 Play。
- **Reload 失败**：分别在 B 的解析、校验、资源不足、解码、判定初始化与设备接入阶段注入失败；验证只清理 B 尝试，保留 A 的不可变内容和已准备音频，报告实际阶段并保持停播，不自动续局。设备受影响时，确认只有恢复或重新接入设备后才允许显式 Retry A；不依赖旧局进度或设备状态回滚。另在成功切换后注入故障，验证按实际当前版本停止和报告，不声称撤销了切换。

现有 Player 对照证据显示，解码准备失败会保留旧 bundle，且当前实际状态仍为 `Playing`（L299）；设备激活失败会保留旧 bundle 但进入 `Failed`（L319）。L299 的继续播放是当前现状证据，与 D-13 未来“Reload 失败即停播”的设计不同；D-13 尚未实现，不能把该测试描述为已满足未来目标。这些测试只说明资源事务现状，不证明 gameplay 状态可整局回滚：[`player_control_load_tests.cpp`（准备失败）](../../../../tests/player/player_control_load_tests.cpp#L299)、[（激活失败）](../../../../tests/player/player_control_load_tests.cpp#L319)。D-13 也不改变未来在同一实机路径内从指定点开始或跳段时的 `Miss` 语义。

### 纯渲染资源重建（D-14：2026-11-19 owner 共识，边界确认，非实现或授权）

D-14 只覆盖纯渲染资源重建：重建后的画面应来自当前已加载的谱面版本，并保留本局位置、判定、输入/连击及其他进度；不重读谱面来源，不换谱、清分或重开，也不要求在任何时刻一律冻结或倒带。例：正在游玩已加载版本 A 时，磁盘上的同一来源已改为 B，纯画面重建仍呈现 A 和当前局面；只有显式 Reload 才读取并采纳该来源的新版本。

**2026-11-19 续议：**渲染器只报告带当前会话身份的画面可显示事实，不直接发 Pause/Resume；唯一会话控制者只解除当前会话的“画面不可用”暂停原因，不触碰其他原因。纯画面重建若没有因画面不可用而实际暂停播放，不额外发 Pause/Resume，也不倒带。

普通播放确实因画面中断暂停时，控制者仅在中断前正在播放、恢复时仍为同一会话和同一局，且解除画面不可用原因后没有其他暂停原因，才自动续播。玩家手动暂停（包括中断期间新到的）保持为独立原因，不能被画面恢复回执解除；Reload 成功建立的零点暂停新局继续等待显式 Play。旧会话的迟到画面回执不得改变当前会话状态或带起播放。

实时游玩若因画面中断暂停，须先显示冻结画面，再等待玩家显式 Resume；用于继续的那次按键不得同时进入游玩判定，恢复前播放位置和判定均不推进。若音频也中断，恢复还须满足 D-12 的安全续局条件。首版不设时长阈值、倒计时或配置项。以上续议不扩大 D-05，不改变 API 或线程，也不构成实现授权。

现状对照：[`player_control_transaction.cpp` 的 `runRebuild`](../../../../app/player/src/player_control_transaction.cpp#L156) 比纯画面恢复更广，会重建 renderer、处理 audio seat、读取来源，并调用 `prepareReload(..., KeepChartTime)`。当尚无 bundle 且处于 `Failed` 时，该路径还会转入 `runLoad`。因此 D-14 不适用于所有 `Rebuild` 或 `Failed` 恢复；现有接线也不表示 D-14 已实现。

以下为未来验收方向，不表示已实现或验证：

- **纯画面重建未造成暂停**：A 正在播放时执行纯渲染资源重建，播放没有因画面不可用而暂停；重建不额外发 Pause/Resume、不倒带，位置连续向前，且不重读来源、不换谱、不清分或重开。若来源已改为 B，画面和状态仍对应已加载版本 A；只有显式 Reload 才采纳 B。
- **普通播放自动续播**：A 因画面不可显示而实际暂停；此前正在播放，恢复回执属于当前会话和同一局，且没有其他暂停原因。控制者只解除画面不可用原因并从冻结位置自动续播，不倒带。
- **手动暂停阻止自动续播**：分别覆盖画面中断前已有手动暂停，以及暂停期间新到手动 Pause；恢复时只解除画面不可用原因，手动原因仍在，播放保持暂停，须由玩家显式 Resume。
- **Reload 与旧局迟到回执**：画面中断期间 Reload 成功建立新局，新局从零暂停并等待显式 Play；新局的画面可显示回执不启动播放。随后到达的旧会话回执也不得改变新局或启动播放。
- **实时游玩显式恢复**：实时游玩因画面中断暂停后，先确认冻结画面已显示，再接受玩家显式 Resume；用于 Resume 的按键不命中音符，恢复前播放位置与判定 tick 均不推进。若同时注入音频中断，另验证 D-12 的同局、音频位置及已结算输入边界安全条件。
- **无时间策略配置**：首版验收不设置中断时长阈值、恢复倒计时或相关配置项；纯渲染重建不新增 API 或线程要求，也不改变 D-05 范围。

### 主动 Stop 与自然结束的统一完成处理（D-15：2026-11-19 owner 已确认的未来设计）

以下是 owner 2026-11-19 的决定及 2026-11-20 续议。续议接受多局会话和局间内容保留，取代原先每局结束就卸载的安排。以下均为未来设计，实现未开始，不改变 D-05，也不授权实施。

**自然结束。** 普通有音轨播放由播放路径报告本局 EOF，不创建或推进 `judgement`。有音轨实时游玩须分别取得带本局身份的两项事实：播放路径确认音频自然播完；判定执行路径确认依原规则应处理的输入与判定尾段已实际执行完成。唯一会话控制者仅在两项事实都成立后结束本局。EOF 不代替输入/尾段完成：合法输入窗口仍有效，未处理到期判定须实际处理，不能因 EOF 批量判 Miss；队列为空或时刻已到也不证明尾段已执行。尾段先完成则继续播放至 EOF；EOF 先到则保持本局并继续所需输入/尾段处理。候选 RPA 或 test-only 尾段参数不能作为生产默认来制造完成事实。无音轨自然终点的技术规则见 [Player 收尾合同](contracts/render-player-writer.md#所有权暂停与收尾)。

**Stop 截止。** 唯一会话控制者按本局输入顺序确定 Stop 的截止边界。只结算截止前已接收、且按既有规则应在截止前生效或到期的输入/判定，包括已接收但调度较晚、规则生效时间仍在截止前的命中；截止后才接收的输入不计。不得用 UI 时间、末帧分数或空队列代替该顺序与结算结果。Stop 不等曲终；截止时尚未到达的音符不补 Miss，尚未到期的长按尾不预判。结算遇到故障时保留并报告故障证据，不把未证实结果伪装为完成。

**成绩与局清理。** Stop 和自然结束共用同一流程：已开玩的实机局先按实际成绩结算并将独立有效的结果交给宿主，包括暂停中的局和真实零分；随后清理本局判定、输入、计分和播放状态。仅装载或 Reload 后尚未开玩就 Stop 不交付成绩，普通播放始终没有判定成绩。结果交付后独立于本局和已保留的谱面；不要求写文件，也不规定展示或持久化方式。

每局只执行一次结束处理。Stop 和曲终同时到达不重复结算或交付；旧局的迟到通知不能结束新局。如果成绩已经交付而局清理失败，只处理余下的清理工作，不重算也不再次交付。

**会话与内容。** 一个 Player 会话可包含多局。Stop 或自然结束只清理本局状态，保留当前已加载的不可变内容和已准备且健康的音频，按 D-13 显式 Retry，无需再加载。会话结束时释放当前版本；成功替换后按 D-13 释放被替换版本。故障暂缓与 Reload 失败不进入正常局结束流程，分别遵循 D-12 与 D-13。`judgement` 不感知音频、Player 或卸载；Player 不重算判定窗口。D-15 不新增结束管理器、API、固定等待或谱面字段。

候选规则参考：[RPA 执行合同 §7](../../../formats/rpa-execution-contract.md#7-需要测量的后续门禁)描述候选 profile 的 EOF 尾段路径及生产测量门槛；该合同仍为 candidate，不代表通用生产语义或已实现，也不裁定无音轨自然终点。

现状对照：普通音频 `Ended` 只使应用进入 `Stopped`（[会话测试](../../../../tests/player/player_control_session_tests.cpp#L141)）。候选玩法的 [`runStop`](../../../../app/player/src/player_control_transaction.cpp#L262) 调用 `GameplayControl::Stop` 后会重置适配器；该控制本身还会[替换判定会话](../../../../engine/playback/src/playback_session_realtime.cpp#L481)。因此不能先走旧 Stop 再查询本局成绩。[候选结果对象](../../../../engine/playback/include/cuexis/playback/gameplay_candidate.hpp#L230)可以独立持有取出的结果，但目前尚无 D-15 的统一结算、交付与局清理流程。

未来验收方向（不表示已实现或验证）：

- **自然结束顺序**：用可分别控制 EOF 与判定完成时点的有音轨实时局，分别先发 EOF、先完成尾段；前者在输入窗口及应执行尾段完成前不得结束或批量 Miss，后者须播放至 EOF。额外让队列为空、时钟到达尾段时刻但尾段尚未实际执行，确认仍不结束；确认生产路径不依赖 test-only 尾段默认值。普通有音轨播放自然结束后保留当前内容和健康音频，且始终无 `judgement`。
- **Stop 截止与成绩**：安排一项截止前已接收、有效时间在截止前但调度较晚的命中，一项截止后输入、一个未到达音符和一个未到期长按尾；让 UI 时间与会话顺序冲突、末帧分数滞后且队列暂空后发 Stop。核对只按会话顺序结算应在界内生效/到期的项目，后到输入被排除，未到达音符和未到期长按尾不补 Miss，Stop 不等 EOF；注入结算故障时仍能观察到原故障证据。
- **开局与交付**：成功 Reload 后未 Play 即 Stop，断言仍保留当前版本且无成绩交付；实际开玩后暂停并以零分 Stop，断言交付真实零分，清理局状态、Retry 开新局及会话卸载后仍可读取原结果。确认会话结束时释放当前内容和音频。普通播放全过程不创建/推进 `Judgement`。
- **竞合与清理**：让 Stop 与自然完成及重复通知竞合，断言只收束、交付一次；新局开始后再送旧局 EOF/Stop 通知，断言新局不结束。结果交付后注入局清理失败并重试清理，断言不重算、不重复交付。边界审查确认没有新增结束管理器/API 或 `judgement` 对音频、Player 的依赖。无音轨终点按 [Player 收尾合同](contracts/render-player-writer.md#所有权暂停与收尾)取证。

### D-16 普通启动与无资源窗口

D-16 是 2026-11-19 owner 确认的 RR 后续 Player 目标，实施须另行授权。独立参考播放器可通过启动参数指定谱面来源；只有显式请求判定且满足 D-07 校验时才启用判定。播放器不提供内置 GUI 选谱、设置或菜单。

启动占位和无来源状态的窗口画面由 Player 窗口外壳负责绘制；这类画面不要求创建谱面快照，也不计作当前谱面帧已呈现。普通启动未指定内容来源时（无参普通启动是典型例）应显示一个可关闭的播放窗口，窗口文字为「无资源」；不加载或回退到阶段测试谱，不开始播放或判定。此规则不改变显式测试或工具命令的行为。明确指定的内容加载失败时，须报告实际失败的文件或来源及失败原因，不得伪装成无资源状态或回退样例；报错渠道按下节已接受共识。

显式调试/测试入口保留；显式测试请求可使用约定样例。此行为设计不构成源码依赖限制，不要求改用 v4 演示或移除旧 Reader，也不改变 D-05。当前未指定来源时仍采用默认工程，见 D-13 的源码现状。

以下是未来可实测场景，不表示今天已实现或验证：

- **无源普通启动**：普通无参启动后窗口显示「无资源」且可关闭；未加载阶段测试谱，不播放、不判定。
- **有源成功**：明确指定有效来源后，确认加载的是该来源；未显式请求判定时不启动判定。
- **有源无效**：明确指定无效来源后，报告对应文件或来源及实际失败原因；不显示成无资源空态，也不回退样例。
- **显式测试**：显式进入调试/测试后可使用约定样例；该样例不成为普通无参启动的默认内容。

#### 外部行为（2026-11-21 owner 已接受，拟实施）

参数语法错误（缺值、多来源或不相容请求等）不创建窗口，向 stderr 输出诊断并非零退出；`--help` 正常输出帮助并以 0 退出。无参普通启动显示上述可关闭的「无资源」窗口。语法正确且拼写受支持的请求若能力不足，保留具体能力诊断，不当作未知参数。

参数合法但来源文件缺失、坏谱、缺资源或合法内容不受支持时，保留可关闭的错误窗口，停止播放，窗口显示简短的实际原因，详细诊断写 stderr。缺能力不报包损坏，不降级。修复后可显式 Reload；成功仍按 D-13 在零点暂停、静音，等待 Play。

退出码取决于关闭时是否仍有未恢复的加载或运行故障。正常关闭为 0，包括无资源、Stop 和自然结束后的关闭；Stop 和自然结束不强制关闭窗口。发生过错误但已恢复时正常关闭为 0；尚有未恢复失败时非零，即使此前曾成功加载。语法错误或致命外壳错误非零退出。普通被拒控制命令不自动记作未恢复运行故障。

日志、FPS、性能统计等仅观察功能可与普通播放、正式 `--judge` 组合；取消 `--judge` 与全部开发参数一概互斥的限制。手工时间、输入注入和玩法覆盖只允许显式测试入口，共用会话实现且不绕过准入。原有不相容测试请求继续拒绝，不自动放行所有旧开发开关。

离线迁移、编译、打包工具按一次命令完成后退出，明确输入和输出，成功 0、失败非零，`--help` 正常帮助退出 0；沿用各工具现有诊断码、路径和各自已有错误分类，迁移工具保留现有具体 1/2 分类。迁移工具现有单独 `--help` 会作为参数错误退出，须随本设计更新。迁移发现损失须报告并失败，不交付有损成品；沿用已有提交保护与恢复机制，不承诺所有文件系统故障下绝对回滚。工具落点见 [P5 工具外部行为](contracts/render-player-writer.md#工具外部行为)，Writer 与编辑器职责见 [D-19](#d-19-sdk-示例与宿主试用)。本节只记录已接受设计，不授权生产实施。

### D-17 格式版本与发行兼容

D-17 是 2026-11-19 owner 确认的兼容决策原则，不是格式合同修订、已发行组合声明或实现状态。Player 维持一条执行主线；Chart 表示与玩法语义可独立演进，Chart v5 是路线节点而非最终版本，不按代际绑定格式版本与玩法语义版本。

Chart、CXT、CXC、Packed、Capsule 与 Graph 的接受版本及必需能力，只在直接读取、嵌入、解释或实际语义依赖的边界规定。格式合同（schema/Spec）决定表示是否合法；这不自动构成 Player 的发行支持。Player 每次发行只对实际具名且验证过的组合，分别承诺普通播放与显式判定。无需要求这些格式同号，不建立全排列兼容表，也不另设全局第七个版本号。

遇到对应请求所必需但不支持的能力时，须给出诊断并拒绝依赖该能力的请求；不得静默忽略或降级，也不得借此改变判定规则、让旧谱按新规则得分。若新表示影响判定语义，须跨层验证从成品表示读取、语义解释到判定结果的路径。

回归样例应保留正式承诺对应的当时实际交付输入：承诺直接读取源谱就保留源谱，承诺编译发行就保留已编译成品。验证旧成品不以重新取得源工程或重新编译为前提；这不授权删除源工程，也不改变其既有保留要求。对正式承诺的判定路径固定输入及预期结果，并为不支持路径保留能证明诊断与拒绝的反例。只验证 schema 或单层解析，不足以证明判定兼容。

候选 schema 约束示例：[`cuexis.gameplay-graph.v1.schema.json`](../../../../schemas/cuexis.gameplay-graph.v1.schema.json) 当前将 `graphFormatRevision` 固定为 1、`capsuleRevision` 固定为 3；这是现有候选约束，不是发行声明。另一个发行入口示例见 [ROADMAP CXC 路线](../../../ROADMAP.md#cxc-路线)：Stage 8 规划在 CXC v1 下发行经验证的 Packed playback entry 或独立 gameplay-graph entry；这是阶段规划，不表示入口已发行。两者分属现有约束与未来发行规划，不构成已发布的格式组合，也不规定特定二进制嵌套；Graph 不因此仅供调试。示例不预选发行载体、未来版本组合或治理工具实现。

已接受的 [ADR 0041](../../../adr/0041-legacy-format-exit-policy.md) 继续约束旧格式读取、显式迁移与兼容路径退出条件，D-17 不变更这些决定；也不扩大 D-05、排期或实施授权。

### D-18 按用途编译 Player

D-18 是 2026-11-19 owner 接受的设计目标，归入 D-05 的 R1，不扩大阶段范围或实施授权。默认构建、显式实验构建与打包工具按实际消费者划分；两种 Player 构建共用同一套 Player 源码、会话、时钟和渲染路径。

纯候选播放读取器只编入显式实验构建。两种 Player 构建都执行正式 CXC 合同要求的整包校验，即使选择正式入口。校验 ZIP CRC、清单 SHA-256、条目存在性和闭包时可以读取候选条目的原始字节及清单记录；这一层不解码候选谱面内容。候选内容的语义解码只在显式候选播放入口或验证工具中执行；打包专用写入留给打包工具。

共同启动参数在两种构建中含义一致：对同一受支持正式谱和相同请求，两者须产生相同播放行为。实验构建可额外接受显式开发参数；包中同时有正式与候选条目时，混合 CXC 的普通 `--cxc` 始终走既定正式入口，实验构建须显式选择候选条目，`--candidate-entry` 是已支持相应条目的现行示例。默认构建拒绝显式实验请求。

不同编码表达相同谱面和玩法时，播放器共用执行路径；新增玩法还须提供对应 Judgement 能力。编译结果决定构建可用能力，运行时仍须显式请求判定并通过校验。普通播放所需能力齐全时允许正常播放；缺少本次请求所需的格式或玩法能力时，按 D-17 诊断并拒绝。

后续验收方向包括：核对默认构建的实际编译源和传递链接依赖，确认纯候选播放读取器已隔离。同一受支持正式输入在两种构建中的播放行为一致，包括合法混合包的正式入口；候选条目原始字节损坏时，即使走正式入口也须拒绝该包。仅实验构建可显式进入受支持的候选条目，默认构建拒绝实验请求。此处记录的是设计目标，未表示已经实现或完成编译验证。具体源文件、构建 target 与 SDK 安装面/ABI 不由 D-18 裁定，发行组合由 Stage 8 决定。

**共享公开类的窄迁移（设计已接受）。** 承接 [D-24](#d-24-sdk-判定接入与实验扩展) 的跨构建类定义一致目标，R1 先隔离候选源码和链接依赖；RR-4 的窄迁移仅处理 `PlaybackSession`、`PlaybackSource` 的宏控候选声明，由独立实验头和窄扩展入口承接，并改接具名消费者。两种构建均保留通用显式 entry 工厂，默认构建仍拒绝候选请求。用同一普通宿主源码分别从两套安装树构建并验证相同的普通行为；另用具名实验宿主验证候选行为。

窄迁移前先核对实际安装面、源码与 ABI 兼容性。若涉及既有源码不兼容、删除已装符号或改变布局，须先按现行合同和版本规则裁定迁移与 SDK 版本。本条不授权实施、不改变 D-05，也不重启延期的 R2。`PlaybackSession` 与 `PlaybackSource` 的具体 API 和安装清单见 [RR-4 逐符号兼容迁移](contracts/runtime-timing.md#rr-4-逐符号兼容迁移)及[安装与窗口](contracts/runtime-timing.md#安装与窗口)。

**API 分组迁移与稳定性（2026-11-21，owner 已接受）。** 已对外发布的旧 API 按功能组逐步替代，各组分别发布替代入口、公告弃用并安排退出，不要求一个版本替代或删除全部旧 API。每组至少经过一个实际发布的过渡版本；这是最低迁移机会，旧入口仍须持续保留到对应新入口稳定，不能因达到预定版本号而自动删除。

稳定性依据已有证据确认：替代入口已发布并实际接入参考应用和独立 SDK 消费者，承诺的使用场景、错误行为及适用回归通过，且没有未解决的阻断迁移问题。各组的替代、弃用、稳定性证据及删除裁定记在现有迁移表和采用记录中；通过后按现行版本规则在获准的不兼容变更版本退出，未稳定的组继续保留。不另设固定观察天数或用户数量门槛，也不以所有第三方迁完为前提。

行为等价时新旧入口共用实现；需要保留旧语义时明确其兼容路径。真正仓内私有接口在调用迁移和验证完成后可清理；涉及已安装公共类的布局、虚表或 ABI 时仍执行公开兼容门禁。共享类型和支撑实现须等仍受支持的入口不再依赖后才可移除。此规则不要求长期维护独立的旧 SDK 发行分支，也不改变旧格式支持合同。Judgement 晋升默认 SDK 按成熟度独立评审，具体版本随发布裁定，不预排固定版本。

D-17 管理格式兼容关系，SDK 接口按宿主用例单独评估。RR 后续核定安装清单，Stage 8 决定具体发行组合。

### D-20 旧谱判定兼容

长期维护同一套 `judgement`。对仍正式支持的判定组合，使用发行时交付的同一份谱面，从相同初始状态，按相同的判定和计分设置提交同一组带时间和顺序的标准化输入，须复现已发布规则约定的逐音符结果与结算。遇到未支持的规则，Player 按 D-17 给出诊断并拒绝该判定请求。

发行时保留按承诺交付的源谱或编译成品、输入和独立确定的预期结果。每套正式规则保留少量能区分边界的用例，逐项核对判定与结算。仓库的长按内部测试采用尾判窗口 `[990, 1000)`。第 999 个 tick 松手应判 Hit，第 1000 个 tick 松手应判 Miss。[长按尾判测试](../../../../tests/judgement/execution_kernel_phase_tests.cpp#L418)

当时发布的规则与验收样例明确且一致，某个构建却给出不同结果时，按原规则修正实现。发行说明列出受影响的构建和触发条件。已保存的成绩保留当局原值，修正版重算产生的差异可据此解释。

主动调整判定行为，或当年的规则说明与验收证据冲突时，按规则变更审阅，明确区分新旧行为。仍支持旧规则时沿用其原有判定窗口。同一个内核只在新旧规则确有差异处分别处理。不同 Chart 版本沿用同一玩法语义时，可复用同一组边界用例。[D-17 格式版本与发行兼容](#d-17-格式版本与发行兼容)

### D-21 谱面表现与判定共用拍位换算

**已接受设计（2026-11-20，拟实施）。** 新建独立的谱面时间库，只依赖 `core`。新库维护现有 Chart 作者拍位（`RationalBeat`）的语义，负责在连续 BPM 变化与停顿下，由拍位求逻辑谱面时刻，也能由逻辑谱面时刻反查拍位。Chart 负责解释源谱的节奏数据，并提供本次换算的权威谱面上下文。

新内容的逻辑谱面时间与判定 tick 固定采用有符号 64 位整数微秒，`1 tick = 1 μs`。作者落点用精确 `RationalBeat` 表示并保留供 Studio 编辑，判定窗口仍以带符号毫秒偏移声明。编译按最近整数微秒量化，恰好位于两个 tick 正中时取偶数 tick。拍位在完成节奏积分与停顿累计后量化。

**窗口端点（2026-11-21，已接受）。** 设 `t` 为量化前的目标时刻，`δ` 为相对窗口端点偏移，两者均以微秒表示。以 `R` 表示上述量化，目标 tick 为 `R(t)`，每个绝对窗口端点为 `R(t) + R(δ)`。同一等级表复用到不同目标 tick 时，相对端点和窗口宽度保持不变。量化结果转换为 `int64` 前须检查范围，端点加法须检查溢出。遇到非法或非有限值、转换或加法溢出、量化后 `start >= end` 时，编译拒绝，不自动扩窗。

Chart 表现侧与玩法作者编译器依赖该时间库，共用 `RationalBeat` 与换算实现。编译器只换算新增的显式拍位输入；其 Chart 上下文缺失或与玩法时间基准不匹配时，应报错，不用默认节奏推算。

同一离散边界只量化一次，Chart 表现与判定消费同一次编译所得的 tick。连续变速段中的阶跃事件和停顿起止等离散边界，也按整数 tick 比较，不用反查拍位决定何时越过边界。反查拍位只供连续表现插值；按编译所得的 tick 选定区段，反查值只是近似采样值，不能用来复原作者拍位。

**新映射的 Stop。** D-21 沿用 [Chart Stop](../../../../schemas/cuexis.chart.v4.schema.json) 的单一作者 Beat 加正时长语义：Stop 占用谱面时间区间，整个区间固定在该 Beat。以 Beat 0 归零时，仅扣 `stop.beat < 0` 的 Stop 累计时长；Beat 0 自身的 Stop 从零时刻开始，其时长照常累加到后续拍位。旧 [Judgement `TimebaseProfile`](../../../../engine/judgement/include/cuexis/judgement/timebase_profile.hpp) 则在 `[startBeat, endBeat)` 内冻结 Beat→tick 累计，在 `endBeat` 加时长。旧模型的 `endBeat`、跨零 Beat 区间和 [Gameplay Spec 的集合／区间反查约束](../../../formats/GAMEPLAY_V2_SPEC.md) 留在旧模型范围内。

**停顿反查（已接受）。** 时间库的反查结果包含 Beat、是否位于 Stop 内以及 Stop progress；该结果类型属于时间库，不依赖 Chart 类型。Stop 的时间区间为 `[S, E)`：在区间内返回 Stop Beat、`inStop=true` 和 `[0, 1)` 的 progress；恰在结束 tick `E` 时返回同一 Beat、`inStop=false`，不返回 progress `1`。

新作者 Stop 的碰撞规则见[谱面时间合同](contracts/runtime-timing.md#谱面时间-api)，诊断和旧接受集合对照见[稳定诊断与迁移](contracts/runtime-timing.md#稳定诊断与迁移)。

运行时判定内核 `judgement` 消费编译好的 tick，只依赖 `core`。玩法作者编译器须与运行时内核拆为独立的构建 target，前者依赖时间库，后者不链接时间库。当前 [Judgement 构建](../../../../engine/judgement/CMakeLists.txt)仍将部分 `gameplay_assembler` 源码列入同一 target；若直接为该 target 加入时间库，整个 target 就会依赖时间库。具体类型、构建及旧 codec 拆分见[运行合同](contracts/runtime-timing.md)。

Playback 负责设备观测、音源位置和输入时间的会话换算，以及谱面 offset、设备校正、输入补偿和显示提前。上述会话校正不改变拍位对应的逻辑谱面时刻。已有 tick 输入、旧编译成品和旧回放沿用原校验、时间基准、判定规则及窗口边界，不按新映射统一重算，不改写现有 wire 或 identity；旧普通 seek 继续遵循 [ADR 0042](../../../adr/0042-stage-6-productization-boundaries.md)。旧谱复现见 [D-20](#d-20-旧谱判定兼容)。

**现状与精度边界。** 现有 [Chart TimingMap](../../../../engine/chart/src/timing_map.cpp)对连续 BPM 使用浮点积分。一次最近舍入相对其输入值的误差至多 `0.5 μs`；目标与偏移各量化一次，绝对窗口端点相对未量化的计算值 `t + δ` 的量化误差至多 `1 μs`，不含浮点 BPM 积分误差。跨平台重编译在半 tick 附近可能得到不同 tick，不承诺浮点积分结果位级一致。读取同一成品时，离散表现与判定沿用已编译边界，不从浮点映射重算。输入设备和声画呈现的实际精度不因 tick 单位改变。

**候选格式。** [作者版本、Stop、比例和最小多等级](contracts/runtime-timing.md#作者版本stop比例和最小多等级)已写明字段、版本和规则；保持候选状态。

### D-22 谱师自定义判定等级

**已确认的目标。** 下一版判定内核须允许谱师决定档数、每档的等级标识，以及相对目标时刻的带符号时间误差区间，不限定三级或内建名称。`Outcome` 继续表示 `Hit` 或 `Miss`，可选的 `grade` 另行记录精度等级。玩法作者编译器使用 [D-21 的谱面时间库](#d-21-谱面表现与判定共用拍位换算)换算落点和毫秒窗口；运行时判定内核接受编译好的 tick 与等级表，仅依赖 `core`，负责按已验证的表评档。

相邻档共用同一个量化端点；按半开区间 `[a, b)`、`[b, c)` 评档，公共端点 `b` 归后一档。验证配置要求评档的误差范围内没有空档或重叠，最后一窗的 `Miss` 结算仍按下文规则。

**等级表引用（拟实施）。** 不同音符类型可引用不同判定等级表，单个音符也可引用不同的表。此处确认引用能力，具体表示和校验见[候选作者合同](contracts/runtime-timing.md#作者版本stop比例和最小多等级)。

**计分与连击（2026-11-21 owner 已接受，拟实施）。** 等级、分值和连击的具体规则由谱师定义，SDK 提供稳定、确定的计算方式。同一谱面、规则和标准化输入须得到相同结果。旧谱兼容继续遵循 [D-20](#d-20-旧谱判定兼容)。固定满分模式将等级积分与连击积分分别归一化，再合成总分。总分、两部分占比、等级权重和连击规则属于可跨谱复用的同一模式配置。玩法编译器根据具体谱面计算各自的满积分基数。同一模式用于 200 或 1000 个计分单元时，模式配置的满分及两部分占比保持一致。

设累计等级积分为 `J`、累计连击积分为 `C`，整谱的满积分基数为 `Jmax`、`Cmax`，模式给两部分分配的满分为 `Mj`、`Mc`，采用 `S = Mj * (J / Jmax) + Mc * (C / Cmax)`。总分 `1000000 = 900000 等级分 + 100000 连击分` 只是模式配置示例，不硬编码这些数值。内部保留累计积分与精确比例，统一在输出时取整，避免逐音符截断累积丢分。现有 `maximum` 截断仅约束算术范围，不能替代归一化。

连击积分的一种模式是每次符合条件的判定先按作者规则更新 combo，再累加更新后的 combo。从 0 开始、同一可达全连序列的 `N` 个单元均使 combo 加一时，连击满积分为 `N(N+1)/2`。长按哪些阶段计入由模式定义。模式若采用封顶或分段连击奖励，编译和运行按同一规则求值。Stop 沿用整谱分母。计分单元、编译基数及上界、取整和零分母规则见[归一化计分合同](contracts/runtime-timing.md#归一化计分与-prepared-记录)。

**结果误差与方向（2026-11-21 owner 已接受，拟实施）。** 返回等级、可选的实际带符号输入误差，以及可选的 `Early/Exact/Late` 方向。误差沿用输入观测时刻减本 phase 目标时刻的语义。方向与 grade 独立，例如 `Great + Exact + 8 ms` 有效。

Exact 由作者在判定表中配置为非零宽、包含 0、可非对称的半开区间 `[a,b)`；作者毫秒值经共享时间库量化为 tick 后比较。以 `[-10,+15) ms` 为例：`error < a` 为 Early，`a <= error < b` 为 Exact，`error >= b` 为 Late。不能以 `error == 0` 代替 Exact 区间。

没有实际输入误差的 timer Miss、hold 自动阶段保持误差和方向为空。带真实误差的 release Miss 可以有方向。Exact 的字段、缺失配置的处理和旧谱兼容见[作者合同](contracts/runtime-timing.md#作者版本stop比例和最小多等级)。成品计分与误差记录见[玩法准备行](contracts/prepared-artifact.md#jpr1-玩法准备行)。

**Player 的选择边界（拟实施）。** Player 只能按谱面允许的选择调整玩法规则，不可任意覆盖。CXC 或工程内有多张难度谱面时，允许从中选择一张播放；所选对象是一张难度谱面。

**输入映射（2026-11-21 owner 已接受，拟实施）。** 谱面定义逻辑通道与操作要求；Player 负责可配置的物理键位映射，玩家可通过启动参数指定键位配置改键；SDK 消费标准化逻辑输入，玩法、窗口和计分继续按谱面。相同已支持键盘输入语义的 4/6/7 等通道配置，经完整性、冲突和容量校验即可使用，增加通道数共用同一 Player 实现。D/F/J/K 四键仅为验收样例，不构成正式格式或 Player 整体的四键限制。

鼠标、触摸、旋钮等需要对应宿主适配能力。启动参数、键位配置、默认映射和改键边界见 [Player 命令与启动](contracts/render-player-writer.md#命令与启动)。

**普通单击的最后窗口（拟实施）。** 最后一个可命中窗口左闭右开，取 `[start, end)`。以 `[1.000, 1.100)` 秒为例：逻辑时间推进到或越过终点时，先处理此前已提交且时间戳落在窗口内的有效输入；仍未命中且尚无结果的音符只结算一次 `Miss`，发生时间记为窗口终点 `1.100 s`。即使跨帧才越过终点，宿主也从该次 `advance` 取得结果，无需操作系统恰在终点回调。当次结果交付按 [D-24](#d-24-sdk-判定接入与实验扩展)；既有摘要、回放与留存规则不变。

**现有基础。** 候选[作者编译器](../../../../tools/gameplay/gameplay_assembler/src/gameplay_author.cpp#L106)和[成品的 Measure 声明](../../../../engine/gameplay_packed/src/gameplay_capsule_model_internal.hpp#L204)只传递等级标识，未携带各档的误差区间。[内核](../../../../engine/judgement/src/execution_kernel_impl_fold.cpp#L272)在已有等级表且本次判定有时间误差时，按带符号区间选中一档，将其标识与 `Outcome` 一起写入结果。[候选宿主的成绩汇总](../../../../engine/playback/include/cuexis/playback/gameplay_candidate.hpp#L226)列出分数、连击和 Hit/Miss 数量，没有等级明细。

**未来验收方向。** 作者声明的标识和区间须能经编译成品传到准备阶段。准备时检查区间上下界和标识引用，并验证在声明要评档的误差范围内，每个误差恰好对应一档。用区间重叠、应评档处有空档或引用未声明标识的反例，验证开局前即给出诊断并拒绝该表。

用一份两档谱和一份五档谱，各自声明等级标识和区间。分别编译、重新载入成品、准备并运行，让每一档都实际命中；从宿主结果逐项核对 `Outcome` 和谱师声明的 `grade`。输入覆盖早到、晚到、零误差、共享端点及其相邻 tick；将含半 tick 偏移的同一等级表用于奇数和偶数目标 tick，核对相对端点和窗口宽度一致。另用未声明等级表的旧谱回放既有输入：`grade` 应为空，不补默认等级，逐音符 Hit/Miss 与结算按 [D-20](#d-20-旧谱判定兼容) 复现。

分别让不同音符类型和单个音符引用不同表，核对各自等级结果。按谱师声明的规则重复运行相同输入，核对等级、分值和连击一致。验证 Player 只接受谱面允许的玩法选择，并能从多难度 CXC 或工程中选择一张谱面播放。

**候选细节。** 数据结构、载体、资源限制与校验见[运行与时间合同](contracts/runtime-timing.md)；本条保持目标状态，不承诺 SDK 发布。

### D-23 谱面画面比例与宿主尺寸

**桌面 Player 共识（2026-11-21 owner 已接受，拟实施）。** 桌面 Player 优先按谱面选定比例创建窗口；默认不旋转，通过启动参数显式选择 0/90/180/270 度整幅画面旋转。旋转选择、默认值、启动参数与窗口尺寸均属 Player 职责。不得根据屏幕利用率自动旋转，不得把用户旋转选择变为 Chart 作者字段。画面等比显示，禁止非等比拉伸，剩余区域留边。

**多比例画幅共识（2026-11-21 owner 已接受，拟实施）。** 同一 Chart 声明多种比例，各比例是同一台相机的画幅配置；每比例静态画幅参数仅为宽高比与取景范围大小，保持居中。所有比例共享相机的位置、朝向、运动轨迹、变焦和同一时间轴，共用场景、对象动画和玩法。作者分别设置取景范围大小，谱师负责场景构图差异并为每个声明比例检查构图。

多比例适配不得通过引用不同相机或另建相机运动轨迹实现。该约束仅适用于多比例适配。不新增中心偏移、画幅专属动画或额外适配规则。取景范围大小的数值表达、默认值与合法值域见[作者画幅](contracts/render-player-writer.md#作者画幅)。取景与 FOV、共同变焦的组合及比例选择见[内存与布局](contracts/render-player-writer.md#内存与布局)。

**已确认的需求方向（拟实施）。** 作者用宽、高两个正整数按宽:高表示每个声明比例，例如 9:16 为竖屏、16:9 为横屏。这两个整数表示比例，不固定像素分辨率。画面在选定构图内按对应比例等比适配。Player 按基准短边推算初始窗口：横屏取基准为高度，竖屏取基准为宽度。初始目标超出可用区域时同时约束宽、高，等比缩小；可用区域更大时仍用初始目标尺寸。

**现有数据与窗口入口。** [Chart schema](../../../../schemas/cuexis.chart.v4.schema.json)和 [ChartDocument / CameraData](../../../../engine/chart/include/cuexis/chart/chart_document.hpp)没有声明画面比例、视口或画布的专用字段；`metadata` 是不透明数据。[createPlayerWindow](../../../../app/player/src/player_assembly.cpp)按用户宽高创建窗口，并开启高 DPI；[SdlWindow::drawableSize](../../../../engine/platform/src/sdl_window.cpp)读取实际绘图区像素。当前 Player 与平台窗口封装尚无可用显示区域查询。

**现有投影与输入接线。** [Player 帧循环](../../../../app/player/src/player_control_frame_loop.cpp)把整个绘图区尺寸交给 `extractFrame`；[fillCamera](../../../../engine/playback/src/presentation_materializer.cpp)据此计算透视投影的宽高比，[OpenGL 绘制](../../../../engine/render_opengl/src/open_gl_presentation_frame.cpp)从原点使用该视口。窗口比例变化会改变相机横向可见范围，单改初始窗口大小不足以保证构图。[SdlWindow::pollEvents](../../../../engine/platform/src/sdl_window.cpp)当前只接入键盘作为游玩输入，没有窗口位置到谱面坐标的转换。

**初始渲染尺寸与高 DPI。** `720 px` 是设置初始渲染分辨率的短边示例。Player 按实际像素计算短边基准与可用绘图区的宽、高，并据此求目标尺寸。若平台只接受逻辑坐标，宿主在请求建窗时把像素目标换成窗口系统单位。建窗后及尺寸变化时，宿主读回实际 drawable 像素尺寸，再交给 SDK 适配，无需新增配置。取整和换算规则见[内存与布局](contracts/render-player-writer.md#内存与布局)。

**SDK 接线（2026-11-20 owner 已接受，拟实施）。** 比例适配放进现有 SDK 呈现层。宿主提供呈现目标内的实际像素矩形，包含位置与尺寸；SDK 按谱面比例计算区域内的内容矩形 `x, y, w, h`，随帧传递。相机投影遵循作者比例。渲染适配器只清宿主矩形，再以内容矩形设置视口并裁剪谱面绘制，留边使用清屏色。窗口、全屏和 Studio 嵌入共用这条接线。具体布局算法见[渲染合同](contracts/render-player-writer.md#内存与布局)。

正式谱面帧沿用 `submit` / `present`；嵌入目标的最终呈现由宿主负责，适配器绘制后归还借用的图形状态。宿主矩形或内容矩形为空时跳过该谱面帧，不计为已呈现。启动占位由应用外壳绘制，不创建谱面帧，也不计为已呈现谱面帧。

宿主负责窗口尺寸、可用屏幕查询与高 DPI 尺寸换算，交给 SDK 的区域统一使用实际像素。未来接入位置输入时，复用内容矩形与已有坐标、相机变换，不另造作者画布坐标系；当前键盘输入不要求新增位置 API。运行时 `judgement` 仍只依赖 `core`，不依赖窗口或设备。

渲染资源沿用 [ADR 0037](../../../adr/0037-stage-3-portable-presentation-contracts.md) 的所有权规则。内容成功切换或会话结束后，适配器按既有设备归属释放已无操作使用的退役资源。宿主若要在旧内容退役后继续绘制旧帧，须持有此前取得的拥有型资源；会话不承诺重新解析尚未取得的旧资源。D-13／D-15 的局间内容和音频保留规则不变。

**旧谱兼容（已接受）。** 未声明比例的旧谱沿用当前随视口宽高比变化的投影行为，不补固定 16:9，也不修改原文件。采用新比例语义的谱须显式声明比例；由所采用的内容语义确定行为，不另设兼容模式选择器。

**候选呈现接线。** [渲染合同](contracts/render-player-writer.md#p2同提交布局与呈现)维护取整、高 DPI、宿主桥、资源身份与正反向量；保护入口的历史安装取证仍按 D-25。旧谱判定继续遵循 [D-20](#d-20-旧谱判定兼容)。

### D-24 SDK 判定接入与实验扩展

**已接受设计（2026-11-20，拟实施）。** Judgement 保持独立，成熟后按 [D-19](#d-19-sdk-示例与宿主试用) 的流程公开。运行时内核仅依赖 `core`；玩法作者编译器与时间库的构建关系按 [D-21](#d-21-谱面表现与判定共用拍位换算)。Playback 在现有会话中可选接入判定，普通播放不创建或推进 Judgement。

判定接入职责收敛到准备、提交输入、推进并直接交付本次结果。`advance` 直接交付本次新增的零到多条结算事件，包括没有按键时到期产生的 `Miss`。推进前准备足以容纳本批新增事件（含到期 `Miss`）的输出空间并确认容量；容量不足或输出准备失败时不推进判定状态。判定状态提交后，结果交付不再分配，也不以普通失败掩盖本次事件。普通单击的最后窗口及返回等级、实际输入误差和可选方向的语义见 [D-22](#d-22-谱师自定义判定等级)。具体输出容量和故障返回见[候选推进合同](contracts/runtime-timing.md#prepared-与当次推进)。

宿主先收到事件，再提交该帧表现。结果由宿主持有，不因下一次推进失效。后续表现或渲染失败按既有会话故障路径处理，不丢弃已交付事件，也不重新执行已完成的判定或计分。这里保证当次结果输出，不承诺任意内部故障下整次推进可回滚，也不代替宿主持久保存结果；不增加结果有效期、消费确认或跨调用待取队列。

暂停、恢复、设备控制与故障处理沿用既有会话责任。复用现有 candidate 入口与适配层承接这些职责，不增加完整游玩会话层、第二会话或调度者、通用插件框架，也不建立新的长期 SDK 产品线。

默认与实验构建中的共享公开类保持同一定义。新增未成熟能力先经独立实验头和窄扩展入口试用，不再向既有公开类的宏分支添加方法。实验包按 D-19 显式选用、独立安装；接口成熟与实验名称晋升按现行版本机制处理。既有通用显式 entry 工厂在两种构建中保留，默认构建遇到候选请求仍拒绝，遵循 [ADR 0042](../../../adr/0042-stage-6-productization-boundaries.md)。

**现状与候选迁移。** 已有 Playback 公开类仍存在候选宏声明差异，旧推进也未直接返回当次新增事件。[运行合同](contracts/runtime-timing.md)给出迁移表、安装集与兼容窗口；[RR-4](tasks/T-08.md)与[后继运行内核](tasks/T-10.md)各按计划授权执行。

### D-25 兼容入口与格式合同收敛

**旧渲染入口（已接受方向，拟实施）。** 先替代启动占位、像素与摘要探针，再逐项退出 `renderFrame` 与 `renderPresentationFrame`；兼容包装只用于过渡。`RenderFrame` / `renderFrame` 是 [ADR 0041](../../../adr/0041-legacy-format-exit-policy.md#兼容路径按版本退出) 列明的保护项，须单列迁移说明、外部消费者门禁和 SDK/API 版本目标，并保留 ADR 原有验收门禁和适用的 hosted consumer 证据。

按历史发布合同裁定安装消费是否适用。若发布曾支持从安装包使用该入口，由一个覆盖受影响能力的代表性仓外宿主验证迁移；这项验证不替代 ADR 的其他门禁。若证实只支持源码消费，记录安装宿主门禁不适用的依据，仍保留保护项的版本和退出裁定。历史安装面尚未核实；仅迁完仓内调用或检查当前安装导出均不足以裁定历史合同，无需证明没有未知外部用户。`renderPresentationFrame` 若证实为纯内部入口，可在替代用例验证通过后单独删除。

**Packed CRC（合同已更正）。** owner 选择现行 Reader/Writer 的前 92 字节算法，[Packed §5.1](../../../formats/PACKED_CHART_FORMAT.md#51-fixed-header96-bytes) 已对齐。Header 总长仍为 96 字节，末尾 4 字节存放 CRC；Reader 将重算值与保存值比较，因此 CRC 字段损坏仍可被检查。现有工具生成的文件、CRC 和 artifact identity 无需改写。按旧文档的完整 Header 置零算法生成的外部文件仍与现有 Reader 不兼容；真实外部消费者尚未核实，需要保留此类文件时另行明确迁移及哈希更新。此次更正沿用候选状态，不提升为生产格式。

**CXC 条目（合同已对齐）。** [CXC](../../../formats/CXC_FORMAT.md) 与 [Chart Entry](../../../formats/CHART_ENTRY_V1_FORMAT.md) 按具名 profile 固定 playback encoding：`candidate.static-tap-lanes4-v1` 必须为 `packed-chart`，`candidate.behavior-v2-v1` 必须为 `source-json`。候选条目须显式选取，默认入口继续沿用既有内容合同；整包校验与候选解码边界见 [D-18](#d-18-按用途编译-player)。正式化时按实际不兼容程度裁定是否新增 entry revision 及所需迁移；发行遵循 [D-17](#d-17-格式版本与发行兼容) 的具名支持组合，不由本次合同更正改变发行范围。

本次完成格式文字更正，未改变读取实现或现有 wire。渲染迁移仍是目标设计，沿用 D-05 范围及实施门禁。当前验收仅覆盖文档一致性；外部工具互操作与渲染替代测试另行取证。

#### 后继成品与 CXC 源包

**已接受的能力方向（2026-11-21，owner）。** 源谱编译与成品解码交付同一种拥有型准备内容，包含场景、可运行表现、玩法和按 [D-21](#d-21-谱面表现与判定共用拍位换算)共享的时间数据，随后复用同一会话、求值与渲染路径。成品完整保留该发布支持的能力，保存准备后的曲线、绑定和程序等数据。动画循环、混合与交互响应仍由运行时求值；不逐帧烘焙，不落盘 C++ 对象或会话状态。旧静态成品保留原有能力、编码和接受集。

**CXC 的打包选择。** 为减小包体，CXC 可以省略编译运行产物，保留源内容及所需资源；不要求同时存两份。按所选包形态检查清单、引用和资源闭包。合法源包不因没有编译产物而被视为损坏；清单或条目实际引用的缺失文件仍属错误。没有相应源内容也没有成品的包不因此获得可播放能力。

**Player 的支持选择。** 容器合法性与可播放能力分别判断。各 Player 开发者自行决定是否接受源包，可提供加载时编译，也可明确报告不支持。此决定不要求加载时编译或自动回退，不要求参考 Player 支持源包，也不承诺替各 Player 实现或维护。

**技术合同入口。** 准备内容、动态表现与时序见[拥有关系与入口](contracts/prepared-artifact.md#拥有关系与入口)、[场景与动态表现](contracts/prepared-artifact.md#场景与动态表现)和[共享时间与运行时边界](contracts/prepared-artifact.md#共享时间与运行时边界)。身份校验、资源闭包和源包派发见[资源闭包与完整身份](contracts/prepared-artifact.md#资源闭包与完整身份)及 [CXC 条目、源包及派发](contracts/prepared-artifact.md#cxc-条目源包及派发)。设计复验进度见[Astra 修订与复验](../../../stage_reports/stages/stage-07-rr/2026-11-22-astra-review-resolution.md)，等价验证见 [T-13](tasks/T-13.md)。
