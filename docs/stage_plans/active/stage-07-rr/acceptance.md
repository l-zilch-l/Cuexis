## 交叉验证

四组冷启动与原审查者差量复验的当期结果保留在[首轮设计报告](../../../stage_reports/stages/stage-07-rr/2026-11-22-design-readiness-review.md)。九项修订见[Astra 报告](../../../stage_reports/stages/stage-07-rr/2026-11-22-astra-review-resolution.md#结果与证据)，后续独立 checkout 缺口及可随仓复核的续审回执见[当前处置](../../../stage_reports/stages/stage-07-rr/2026-11-22-checkout-review-resolution.md)。A-01 仍须单独取得阶段 owner 的采用/接受记录；产品运行与发布条件须在实施后取证。

主代理按任务卡复跑当前获准执行的门禁。独立冷启动使用任务卡、链接输入和采用记录，抽查 R1、R5 帧桥及一个 `NEXT` 包，确认首改位置、可复现用例、正反期望和停止条件。在隔离副本运行对应已存在门禁的一项阴性对照，核对实际失败原因。标注四类记录的证据类型和 revision，分别登记设计冷启动、文档门禁、实施正反例和发布迁移。未采用的卡检查设计与命令可达性，产品运行随实施取证。

## 证据清单

- 每卡保留 SHA、合同修订和未提交输入哈希、preset/平台、命令、退出码、fixture、预期与实测、负例及回滚点。阶段索引注明退出基线与较早证据所用基线的差异。受影响的结论附重跑记录。批次报告按[模板](../../../templates/report.md)归档并用规定的四档结论。
- 独立 checkout 必需的复审回执与短门禁输出放进对应报告的 `evidence/`，随修订提交；写清审查 revision、范围、具体裁定及未执行项。`out/` 可留大日志和临时快照，不能作为唯一可取得的设计通过证据。历史回执或日志确实未交付时按缺失记录，重新验证当前修订，不回填过去的“原始”记录。
- 汇总合同变更、安装面、删并清单、受影响消费者与发现处置。适用的跨平台、hosted、GPU、设备或性能结果附环境和日志。目标未建、用例未执行、运行环境缺失分别记录在证据状态。
- 四组审查的最终封存见 `out/review/stage-07-rr/T-01/final-20261122/`，已有调度阴性按原快照读取。本次 Astra 修订另用 `out/review/stage-07-rr/astra-resolution-20261122/`，实得结果见[修订报告](../../../stage_reports/stages/stage-07-rr/2026-11-22-astra-review-resolution.md#执行记录)。两批文档证据均与产品运行分开。

## 发布与迁移门禁

旧 API 逐组记录兼容新增、弃用、实际过渡发布、代表性消费者、替代稳定性及退役裁定。该组至少有一个已发布的过渡版本，替代入口通过宿主和独立安装消费者的正反用例并获准退役后，才核验旧声明与符号退出。其他组的现有入口随各自窗口保留。RR-4 的新旧对照、R5 渲染入口和 Judgement 晋升各按自身门槛取证。实施采用在[计划](plan.md#唯一派单授权入口)，各组与向量见[运行合同](contracts/runtime-timing.md#rr-4-逐符号兼容迁移)和[呈现合同](contracts/render-player-writer.md#兼容目标及向量)。本阶段不发布（计划 §13），A-04 只核验兼容新增、迁移计划与目标版本；需要已发布过渡版本或仓外宿主的退役核验随稳定 C ABI 移交 Stage 14，不以未发布判失败。

## 延后记录

`NEXT` 按[授权入口](plan.md#唯一派单授权入口)移交候选合同。A-05 仅核验本阶段范围。阶段内的延后须逐项链接任务/发现 ID、原始失败或缺证据、原因、目的阶段与责任、恢复门槛和 owner 接受记录。技术合同、当前证据结论与延后处置各按其原始时点记录。
