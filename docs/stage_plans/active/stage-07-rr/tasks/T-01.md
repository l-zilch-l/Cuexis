## 目标

## 写域

本卡证据目录和派单清单。基线登记差异交集成者回写 findings，调度反例在临时副本运行。

## 步骤

1. 从仓库根运行 `git rev-parse HEAD`、`git rev-parse 'HEAD^{tree}'`、`git status --short`，把完整 SHA/tree 记入派单清单。`<BASE_SHA>` 取计划采用记录绑定的合同提交；首次接卡尚未绑定时取本次读出的完整 HEAD，并在清单固定后继续。运行 `git diff --name-status <BASE_SHA> --`，对变化项保留 `git diff --binary <BASE_SHA> -- <列出的路径>`。`9623efa3` 是旧研究对照，`8599c83a` 是首次实施交接提交，均不自动替代接卡时已采用的修订。用 `git ls-files --others --exclude-standard` 清点整个仓库的未跟踪文件，从中明确列出本次派单所需的设计、报告、回执及 fixture 输入，不能只扫描 RR 计划目录。未提交的已跟踪差异随上述补丁交付，相关未跟踪文件另保留原文与相对路径；哈希清单不能代替文件内容。接手者若使用独立 checkout，须先应用这份补丁并取得这些文件，再逐项核对哈希；同工作树接手也须核对它们尚在。对所有派单输入逐文件计算原字节哈希，统一使用下面的 Python 命令，Windows 和 Linux 相同。以任务 ID 列出合同、CMake/安装、源码、schema、fixture、复跑命令和回滚基线。历史证据依其记录的 revision 解释，当前变化对象重取证。
2. 从本轮设计基线或已登记采用记录绑定合同 revision、任务 scope 与阶段。每次派单按验收页交付卡片、链接输入、该卡的基线和命令。独立回执需标卡内首改路径、测试目标、正反结果与触发的停止条件。

3. 按 [D-20](../architecture-design.md#d-20-旧谱判定兼容)在现有基线清单绑定仍承诺支持的具名旧组合、原始交付源谱或成品及哈希、初始状态、判定/计分设置、带时间和顺序的标准输入、独立确定的逐音符与结算预期，以及各自的合同/发布证据。正式交付语料与内部候选夹具分开标记，不把当前实现输出反写成历史预期。没有发布身份或原始预期证据时如实列缺口，保留现有兼容行为，不新增正式支持承诺；规则与证据冲突的具体条目按 D-20 提交裁定。T-10/T-13 消费同一清单，不另建语料管理框架。取证从[格式矩阵](../../../../formats/README.md)、[格式退出政策](../../../../adr/0041-legacy-format-exit-policy.md)、`tests/fixtures/chart_format_update/golden/README.md` 及 `tests/judgement/` 现有兼容测试开始，再追溯相应交付记录；内部金样的存在不证明正式发行身份。对确无正式发布承诺的组合，记录所查发布/合同依据并标明正式发行回归不适用，仍执行既有候选兼容回归；不能仅因未找到文件就判不适用。对已确认承诺但缺资料的具体组合，T-01 如实交接缺口，保留旧路并继续不受影响的工作；需要改变承诺或在缺证据下退出时由 owner 单独接受，T-09 不可按通过关闭。

```text
python -c "import hashlib,pathlib,sys; print(hashlib.sha256(pathlib.Path(sys.argv[1]).read_bytes()).hexdigest())" "<路径>"
```

独立 checkout 不依赖未提交的 `out/`。仓内报告和可提交回执用于复核历史设计；历史原始日志未随仓交付时标记为当前不可取得，重新执行本卡短检查并生成本次证据，不补造历史通过。任务卡中标为本卡新增的 target、schema 和验收用例先检查其创建责任与前置，交付后才执行对应产品测试。

## 任务级验收

- `python -B tools/verification/check_plan_schedule.py` 和 `python -B tools/verification/test_check_plan_schedule.py` 退出 0。复制阶段目录到本卡证据目录的独立临时子目录，先用 `python -B tools/verification/check_plan_schedule.py --stage-dir <副本路径>` 确认退出 0；仅在副本中把 T-05 的前置加上 T-06，再运行同一命令，应退出 1。唯一错误须精确对应 T-05 行的 `prerequisite T-06 must be in an earlier wave`。保存前后哈希、命令、stdout/stderr、退出码、单行差异和回执，确认正本 schedule.md 哈希未变、副本其他文件未变。
- `python -B tools/check_docs.py` 与 `git diff --check` 退出 0。抽查派单清单中的合同哈希和输入路径可重现，冷启动回执覆盖[交叉验证](../acceptance.md#交叉验证)指定的卡。发现不存在的入口、未给定的合同选择或无法说明预期诊断时，该卡回到设计复核。
- 在另一个独立副本删除 T-05 的 `## 停止条件`，调度检查须退出 1 并明确报告任务卡七段结构错误；将该标题放进代码块或注释也不得通过。检查器分别列出 active 与 candidate 卡，active 不得依赖 candidate。当前 T-01–T-17 均为 active，表示纳入本轮安排；实际派单仍须绑定本次基线与范围。技术合同的 candidate 标记不改变任务状态，也不表示已实现或已发布。

- D-20 清单的每个正式支持组合均能回溯到交付身份及独立规则/结果；不能取得的材料标为缺失，内部夹具不得冒充正式语料。T-10/T-13 的验证输入和预期必须引用清单中的同一对象。
