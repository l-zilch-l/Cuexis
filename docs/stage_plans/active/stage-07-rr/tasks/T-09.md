## 步骤

1. 按 A-01–A-09 建证据索引。每行绑定任务/发现 ID、T-01 的 SHA 和合同修订、卡级报告路径、适用 preset/平台、fixture、正反例日志和回滚点。对较早批次记录取证 SHA 到退出基线的变更，涉及已验对象时附重跑结果。核对 T-07 删并清单、T-08 实际消费者/导出与逐组退役记录。
2. 对 P0/P1 逐条链接满足条件的修复、限制或已接受延后，按[登记册 §24](../findings.md#24-统一实施前设计裁定2026-11-23)的当前处置逐条核对；§22 保留上一轮承接快照。区分实际修复、原判断不成立或过宽、保留现状、兼容条件未满足和已接受后继处理，不把无卡项自动延期。RR-F401 的保存保留修复随 [T-16](T-16.md) 采用（其写域已含 `engine/chart/src/chart_writer.cpp` 与图表 round-trip 测试）；RR-F420 按 owner 已选择的方案 D，按 [T-14](T-14.md#任务级验收) 已列的完整、单条缺失、未知来源与计数饱和分支在采用后验证；旧路径恒 false 作为保守下界，T-09 只登记承接，不再重写或细化判据。RR-F401 与 RR-F420 随 T-16/T-14 纳入本轮实际运行验收；本卡以证据核对，不能再整体具名延期。D-20 按既有兼容原则由 T-01 绑定旧组合及实际交付语料/独立预期，T-10 验旧规则逐音符与结算，T-13 验旧成品无需源工程或重编译即可重放；本卡核对同一清单的证据。不得把 D-20 整体延期或以内部夹具代替正式发布语料；无法取得的具体材料保留缺口，由 owner 对该条处置单独接受。v3 实验金样与未来正式发行实际交付文件分开标记。RR-F510 的新 seek 仍按运行合同的既有延期边界处理；T-10/T-14 实验完成不等于默认 SDK 晋升。由 T-08 汇集逐组安装消费者和替代证据，SDK 接口组维护者按 D-19 的实际过渡发布与成熟度条件提交晋升/退出接受；F306、F405 分别记录各自窗口，不能一并自动关闭。P2 延后写明责任、进入条件与恢复门槛。按模板生成退出报告供 owner 接受，记录接受人、日期和接受的范围。阶段受限退出仍引用原失败或缺证据。
3. 获得退出接受后同步状态和路由。CURRENT_STATUS 链接报告、已接受范围和遗留。HANDOFF 写明现行任务、下一步、阻塞和验证状态，保留已有 Plan 拆分规则。Stage 7.5 入场引用这份退出报告与接手项，Stage 8 继续引用独立的 Stage 7.5 退出门槛。归档时把已接受阶段计划移至 `docs/stage_plans/completed/stage-07-rr/`，更新活动指针和硬编码门禁路径，按文档政策为旧入口留跳转，历史报告与 manifest 保持原位置。`NEXT` 已完成范围按实验实现及其证据交接；正式发行和旧公共接口退出条件继续具名保留，不把未完成实施包装为候选设计移交。

## 任务级验收

- 在退出快照执行 `python -B tools/verification/gen_docs_map.py`，再执行 `python -B tools/check_docs.py`、`python -B tools/verification/check_plan_schedule.py --stage-dir docs/stage_plans/completed/stage-07-rr`、`python -B tools/verification/gen_docs_map.py --check`、`python -B tools/verification/check_docs_facts.py --list` 和 `git diff --check`，均退出 0。接受前核对时，调度命令使用当前阶段目录。索引的每项通过须回溯至与对象一致的 SHA、证据与接受记录。
- 在退出证据的隔离副本分别拿掉一项必需负例日志、一个具名延后的接受记录。按 A-05 复核时分别判该项缺证据和延期未接受，均保持 active。恢复两份记录后再核对 Stage 7.5 链接的接受范围和报告一致。人工核对结论及缺证据原因，文档链接检查单独记账。
