## 步骤

本卡引入 `engine/timing` 和 `beat_us_compile` 新源，并为 `cuexis_judgement_compile` 增加 `timing` 链接边；运行目标 `cuexis_judgement` 的依赖不变。

按 [F302 Chart 源表](../contracts/runtime-timing.md#chart-源表与安装隔离rr-f302)，本卡首创 `engine/chart/internal/cuexis/chart/compiled_chart_timing.hpp` 与 `engine/chart/src/compiled_chart_timing.cpp`，仅编入已有 `cuexis_chart_codec`，其 BUILD_INTERFACE 提供该内部根；不放回基础 Chart 作者头链。基础 Chart 的旧时间适配和 codec 各加 `timing` PUBLIC/ALLOWED，默认 static 安装按基础边补 `InternalTiming`。从 T-11 源值取得时间声明的 Chart 适配编入 `chart_tools`，通过 codec 的 `CompiledChartTiming` 交付；不在本卡提前创建 T-13 v5/CXT2 Animation adapter。

本卡唯一首创 `compiled_gameplay_context.hpp` 和 `compiled_gameplay_rows.hpp`：context 只迁 `CompileCapabilityContext`、`ContentProfileLimits` 并完成旧头转引，直接包含 T-10 的 `prepared_identity.hpp`；四个身份类型及 `StableDeclarationId` 的定义保持在 T-10 运行头。T-13 只消费两共享头。按合同配置拓扑把 `timing` 子目录放到 `chart` 前，保留 `judgement → judgement_compile → gameplay_packed`；不创建 Reader/Source target。

按合同实施编译、反查与同源锚点；旧入口用旧换算。`compileBeatGameplay` 先 `matchesSource` 验证完整源声明，随后逐窗校验 `BeatWindow.phase`：先用完整 `PhaseDeclaration`（kind、declarationOrdinal）与本 requirement 声明全等匹配，成功后才以 kind 查 phase target。再用保存的锚和相对端点量化，解析实例表和计分分组，调用 T-10 的共用 `deriveScoreBasis`。`BeatGameplaySourceView` 的 `PatternDeclaration` 和 `BeatMeasureDefinition` 两个 span 随 stable merge 输入，定义体和具名声明双向校验。产出未终结 owning `BeatGameplayProduct`（运行数组、canonical rows、beat keys），GPH0 ruleset 镜像取 `scoreMode.id`、GPD0 保留完整定义（包括未用项），Measure 声明等级保持空。仅对合同明确规范顺序的 `gradeTables`、intervals、rules 及由 scoring 派生的 units 在拒绝重复键后排序；phase 的 `declarationOrdinal`、Pattern/Measure 声明和其 stable merge 身份顺序保持原语义，不据此重排或拒绝。共享 `compiled_gameplay_rows.hpp` 和 `compiled_gameplay_context.hpp` 在 `engine/judgement/internal/cuexis/judgement/`，Reader 独立包含、不链接编译目标。T-13 才做 digest → identity → 最终 `prepareCompiledGameplay`；本卡不实现 wire 或终结器。

RR-F133 核对仓内 `BehaviorSystem::evaluate` 调用：需要 event/step 拍位的路径传已有完整 `BehaviorSample`，由该内容所属的既有 TimingMap 提供 beat/inStop/stopProgress，不由缺省值猜拍位、不把新 v3 时钟套给旧内容。当前 `runtime_session.cpp` 已传完整 sample，保留；未发现其他受影响生产调用时记录证据，不制造迁移。
