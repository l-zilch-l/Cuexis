# Gameplay Fold Spike：预算实测与确定性检查

状态：dated evidence（研究性 spike，不是实施；2026-10-01 快照）

更新日期：2026-10-01

本报告记录对 [Gameplay 预算与规模上界草案](../../../proposals/GAMEPLAY_BUDGET_AND_SCALE_DRAFT.md)
的第一次实测。被测对象是一个**独立的研究性 spike**，位于 `tools/research/gameplay_fold_spike/`：
不进产品构建、无 CMake target、不链接任何 Cuexis 库，也不是 Stage 7A 的实施。它的唯一用途是
给候选预算表填上第一批数字，并检验设计中的三条确定性声明。

当前状态仍以 [CURRENT_STATUS.md](../../../CURRENT_STATUS.md) 为准；本报告不改变任何阶段状态。

## 1. 被测内容与边界

```text
pattern.*   Pattern -> NFA -> 子集构造 -> 最小化；补在完整 DFA 上取；状态预算指出失败子表达式
runtime.*   Tap / Hold / Bomb / Roll 四种标准条目
            同 Tick 四阶段顺序（激活 / 定时器 / 输入 / 折叠）
            按 claimKey 仲裁、fanout 1、bomb 走 observe 边
            every(period) 采样，格点锚定在 arm（D1 的修法）
            派生 Hook windowScale，只在折叠阶段写，t+1 生效
            L3 折叠 + 一个限时模块（每 100 连击窗口放宽 10%，持续 5 s）
            规范化快照 / Seek
main.cpp    合成谱面与合成玩家，五个 profile
```

**不覆盖**：内联 Pattern 的运行时执行（运行时按标准条目直接实现，Pattern 编译只用于测状态规模）。
多接触点与差分见 §7–§8，几何、frame 与输入重采样见 §9。

**合成数据的局限**：谱面与玩家都是程序生成的。数字代表"这套执行模型在这些负载形状下的
代价"，不代表任何真实游戏的谱面分布。

## 4. 发现

### 4.1 新缺陷 D11：同 Tick 内 Fact 的折叠顺序依赖实例枚举顺序

**现象**：mixed-40k 在正向与反向枚举实例时结果摘要不同。定位到第一处差异：同一次按下在
同一 Tick 内引爆了同一轨道上的两个炸弹（requirement 32 与 40），两条 `Detonated` Fact 的
发出顺序随枚举顺序互换。

```text
正向   2280405 req=32 Detonated / 2280405 req=40 Detonated
反向   2280405 req=40 Detonated / 2280405 req=32 Detonated
```

**根因**：[Ruleset Fold Language 草案](../../../proposals/GAMEPLAY_RULESET_FOLD_DRAFT.md) §2.1
第 4 步规定"按发出顺序折叠本 Tick 产生的 Fact"。L7 的结构性保证只覆盖 **Hook 读取**
（同 Tick 内所有实例读到同一份 Hook），不覆盖 **Fact 发出顺序**——后者在 observe 边会让
一次输入同时结算多条 requirement 时，取决于实现遍历实例的顺序。

**后果**：本例中计分是可交换的，最终分数相同，只是 Fact 流（以及 Replay 可见的事件序列）
不同。但 L3 是可分发内容，任何对顺序敏感的处理器（"本 Tick 第一条 Fact 触发技能"、
按序累计的状态机）都会让同一输入得到不同结果。这与 D4 是同一类错误：一条没写死的顺序规则。

**修法（spike 已验证）**：折叠前把本 Tick 的 Fact 按 `(requirementId, phase, outcome)` 排序。
`requirementId` 已随 Fact 暴露（讨论记录第 47 条），因此这条规则不需要新字段。开启后五个
profile 正反枚举全部一致；关闭时 mixed-40k 复现差异。D11 的这一对照在 spike 报告的 B2 节
自动重跑。

**为什么之前没发现**：34 项案例与封闭性验证都是**逐条 requirement** 检查的，而 D11 只在
"一次输入、多条结算"时出现——它是跨实体的，正落在 Fold Calculus §2.1 说的核心边界之外。
这再一次说明跨实体语义需要按类检查，而不是逐案例检查。

### 4.2 预算草案 §7.5 的签名要求得到证实，且后果比预计更具体

预算草案只说"扫描线必须接收 Loadout 的窗口缩放取值"。实测表明后果不是"活动度估低"，而是
**判定结果改变**：若 `arm` 用基础缩放计算，实例在放宽窗口的前沿尚未激活，提前按下找不到
候选，变成 stray，音符随后 Miss。结论应写得更直接：**`arm` 是判定语义，不只是预算输入。**

### 4.3 活动度与 40,000 的关系：数量级成立

预算草案 §3.1 估计 40,000 条要求的平均活动度约 27。实测：

```text
tap-40k     实测最大存活 27，静态扫描峰值 36
mixed-40k   33 / 50
burst-40k   52 / 91（327 音符/s，远超常规谱面）
```

"整曲计数与瞬时计数相差约两个数量级"成立。静态扫描峰值是实测值的 1.3–1.8 倍，作为
保守上界可用。

### 4.4 稳态代价不是瓶颈

在本模型的计数下，最重的 profile（burst-40k）单 Tick 最多 94 次运算，每秒 14,021 次；
完整五分钟曲目单线程 11–30 ms 跑完。**以本 spike 的执行模型，L2 + L3 的稳态代价比渲染
低数个数量级**，`eventBudget` 的瓶颈不会在判定侧。

### 4.5 周期采样是稳态里唯一随长条线性增长的项

`samples/s` 列显示：Tap-only 为 0，长条比例越高越大（long-hold-4k 达 3,324/s，是该 profile
运算量的主要来源）。与压测 L3 的判断一致，但量级比"1.2e10"那个最坏估计低得多，
因为同时处于采样态的实例数实测只有 10–20 个。

### 4.6 快照极小，Seek 延迟与间隔近似线性

单快照约 1.2 KiB（只存存活实例、待触发定时器与折叠状态）。60 s 间隔下最坏 Seek 6 ms。
预算草案 §4.4 的不等式在本规模下**远未逼近边界**，因此"第一版只做全量快照"的裁决
（预算草案 §7.3）得到支持。

### 4.7 补的规模：常规条目远离预算，对抗输入被正确拒绝

标准条目的最小 DFA 在 8–122 状态之间；补出现在 Hold 与 Bomb 中，操作数最大 32。
对抗性 `¬(any* · press · any{n})` 在 n=10 处超过 4,096 预算，被拒绝且诊断指向子表达式。
这证实"补进预算、不进 capability"（预算草案 §3.3）在实践中可行：规模门能挡住指数爆炸，
同时不误伤常规条目。

**一处次要发现**：Tap 的 NFA 规模随窗口线性增长（窗口 120 时 2,166），主要来自
`repeat(any, 0, w)` 的展开。最小化后只剩 122。编译器若在构造中途检查规模，应检查
**确定化后**的状态数，而不是 NFA 规模，否则会误伤宽窗口条目。

## 6. 局限

1. 合成谱面与合成玩家，不代表真实分布。
2. 只测了四种标准条目；内联 Pattern 的运行时执行与 Controller 未覆盖（多接触点见 §7，
   几何与重采样见 §9）。
3. 运行时按条目手写，而不是执行编译出的自动机。§8 的差分测试部分补上了这一项：短轨迹穷举
   与长轨迹随机化两轮下，编译产物与参考谓词一致，但运行时仍然不执行自动机，因此
   "运行时行为"与"编译产物"之间仍是两套实现。
4. 两个编译器都在 Windows x86-64 上；跨 OS 与跨架构的逐位一致尚未验证。**这一条现在比
   写下的更重要**：§9.7 的 D12 正是"两个编译器不一致"，说明这一项不是可选的加强项，
   而是必需项。
5. 耗时为单次运行，仅作量级参考。

## 7. 多接触点场景（第二轮）

第一轮只覆盖单轨道的单次按下，因此 §4.5 的归属、可见性与换手规则没有被测。第二轮补上：
多接触点模型 + 十一个定向场景，每个场景先写下设计文档的预期，不一致即失败。

| 场景 | 预期来源 | 结果 |
| --- | --- | --- |
| S1 同轨两个 Tap，相隔 30 ms | 仲裁取 `claimKey` 最近者 | 两个分别被就近的按下命中 |
| S2 一次按下、两条同锚点 Tap | 默认 fanout 1 | 只结算一条，另一条 Miss |
| S2b 同上，fanout = all on equal anchor | Ruleset 声明 | 两条都结算 |
| S3 sticky Hold 被第二个接触点中途按下 | §4.5 第 3 条 | 不换手，主体 `Broken` |
| S3b 同上，`strayWhen = noCandidate` | D10 精化后的定义 | 该按下被考虑过并拒绝，不是 stray |
| S4 handoff Hold 在宽限内换手 | §4.5 第 3 条 | 换手成功，主体 `Hit` |
| S5 炸弹（observe）与 Hold（claim）同按 | §4.5 第 2 条 | 都看见，只有 Hold 拥有 |
| S6 比 good 窗口晚 130 ms 按下 | 无候选 | Miss + stray |
| S6b 同上，`strayWhen = noCandidate` | D10 | 没有任何实例考虑过，是 stray |
| S7 槽位复用，原持有者接触点已终止 | D9 的修法 | 隐式替换，两个都命中 |
| S7b 同槽位，原持有者接触点未终止 | D9 的修法 | 活着的归属挡住第二个 |

### 7.1 由这批场景精化的两条规则

**D10 的 `noCandidate` 定义。** 原写法是"完全没有任何实例监听该输入"，实测发现它与
`consumeEmpty` 的区别不在"监听"，而在"**考虑过但拒绝**"。三种拒绝原因（接触点被独占、
窗口不匹配、实例已结算）都算考虑过。S3 正是第一种：sticky Hold 的边看过第二支手并因归属
拒绝，所以它不该算 stray。定义已改为"没有任何实例考虑过"，并写回压测文档。

**换手是一次消费。** spike 最初把 handoff 写成边上的无条件接管，S4 通过但 S3 失败——
因为"接管"绕过了候选集，于是 `sticky` 与 `handoff` 的差别被实现成了别的东西。正确形式是：
换手的边与同一按下上的其他 `consume` 边一起参加 `claimKey` 比较。这条已写回 Program IR
§4.5：`handoff` 的宽限窗口是**边上的谓词**，进候选集计算，而不是先于候选集判断。

### 7.2 Hold 的头部与主体是两条独立 Fact

S3 与 S5 的输出显示：中途断开时头部已经发出 `Hit(head)`，主体再发 `Broken(body)`，
两条事实同时存在。这不是 bug，而是 V2 修补（允许多分量 Measure）的直接结果，但原文档
没有说明它们的关系。裁决是**不做互相撤销**：是否把断开的 Hold 的头部命中计入连击由 L3 的
折叠规则决定。已写回 Program IR §4.5。

## 8. 差分测试：编译产物与手写条目是否同义（第二轮）

第一轮局限 3 指出：运行时按条目手写，没有证明"编译后的 Pattern 与手写语义等价"。
第二轮补上：为四种条目各写一个**独立于 Pattern 构造的参考谓词**，在字母表
{press, release, held, not-held, idle} 上枚举长度 0–5 的全部 3,906 条轨迹逐一比对。

| 条目 | 轨迹数 | 结果 |
| --- | --- | --- |
| Tap，窗口 3 | 3,906 | 一致 |
| Hold 主体，grace 0 / 1 / 2 | 3,906 × 3 | 一致 |
| Bomb，窗口 3 / 1 | 3,906 × 2 | 一致 |
| Roll，2 / 3 次 | 3,906 × 2 | 一致 |

八项全部一致，即 **31,248 条轨迹零反例**。这不能证明对所有长度成立（枚举只到 5 步），
但它排除了最常见的构造错误：`hole` 与 `gap` 的混淆、补的方向、`repeat` 的边界偏移。
grace=0/1/2 三档覆盖了"阈值为 0"这个容易出错的边界。

### 8.1 长轨迹：随机化补测（0–400 步，100 万条）

穷举在长度上是指数增长的（5 个符号、长度 5 已是 3,906 条），因此长端改用随机化。
长度在 1–400 之间均匀抽取而不是固定取上界：反例通常由一个短后缀就能到达，均匀长度
在同等试验次数下更容易命中。五个条目各 200,000 条，种子互不相同。

| 条目 | 最大长度 | 轨迹数 | 结果 |
| --- | --- | --- | --- |
| Tap，窗口 40 | 400 | 200,000 | 一致 |
| Hold 主体，grace 3 | 400 | 200,000 | 一致 |
| Hold 主体，grace 0 | 400 | 200,000 | 一致 |
| Bomb，窗口 40 | 400 | 200,000 | 一致 |
| Roll，6 次按下 | 400 | 200,000 | 一致 |

**100 万条随机长轨迹零反例。** 与 §8 的穷举合起来，两端的覆盖都到了：短端穷举到 5 步，
长端随机到 400 步，窗口也从 1–3 采样扩到 40 采样、grace 扩到 3、Roll 扩到 6 次。

**这仍然不是证明。** 随机化给出的是"在均匀分布下没有找到反例"，它对**稀疏反例**无力：
若某个不一致只发生在形如 `notHeld{4}·press` 这样概率极低的特定子串上，20 万次抽样很可能
测不到。真正的完备手段是符号方法（把编译产物与参考谓词都化成自动机，判语言相等），
这属后续 spike。当前结论的准确表述是：**在两类覆盖下零反例，等价性达到"高度可信"而非
"已证明"**——差异测试通常停在这一档。

## 9. 几何、frame 与量化（第三轮）

补上 §4.3 的几何原语、§5.4 的 frame 与 §5.5 的数值模型。裁决侧的算术全部是整数；
报告里唯一的浮点用于算参考值以量误差。

**读这张表之前先看 §9.7**：Segment 的平方比较曾发生 int64 溢出（缺陷 D12），现已修复并
经 GCC/clang 逐行复测一致。

| 项目 | 结果 |
| --- | --- |
| 定点表误差（1/65536 圈，Q16 值） | 0 单位（表本身就是"最接近的整数"这一语义） |
| 四分之一圈 ×4 回到原点 | 精确，零漂移 |
| 一次旋转的误差（1/1024 px 单位） | 1.489 |
| 串联两次旋转的误差 | 2.305，即一次旋转的 1.5 倍 |
| frame 求值（64 分段） | 每次 7 次比较，log₂64 = 6，符合 O(log N) |
| 区域命中代价 | Disc 5 次运算 / Rect 4 / Strip 9 / Segment 8，均为常数 |
| 反变换往返 | 误差 ≤ 1 单位 |

### 9.1 D6 的取整规则得到验证

**"仿射变换是单次量化运算"这条规则有实测依据。** 串联两次旋转的误差是一次旋转的 1.5 倍
（1.489 → 2.305 个 1/1024 px 单位），而且误差方向不可预测。这与 §5.5 的"禁止在同一表达式里
串联多次旋转"一致：串联不只是"多一点误差"，而是让误差随串联层数累积并失去简单上界。

**四分之一圈可精确表示**这一点值得单独记录。它是四类常见角度（0、90、180、270 度）中的全部，
因此**标准正交的判定线旋转不产生任何漂移**，只有任意角度才产生上表中的 1.5 单位误差。

### 9.2 区域形状的边界约定

四种形状的边界都是**含**的（`<=`），包括半宽为 0 的 Segment。这必须写进规范，否则
"正好在边界上"会在实现之间分叉。命中代价是常数，`contains` 不进 O(log N)，只有 frame
求值是 O(log N)。

### 9.3 输入重采样的样本量（回应预算草案 §5.2 的附带成本）

| 接触点 | 周期 | 域时长 | 样本数 | 每秒 |
| --- | --- | --- | --- | --- |
| 1 | 4 ms | 300 s | 75,000 | 250 |
| 10 | 4 ms | 300 s | 750,000 | 2,500 |
| 10 | 8 ms | 300 s | 375,000 | 1,250 |
| 10 | 4 ms | 600 s | 1,500,000 | 2,500 |

预算草案 §5.2 原估"5 分钟、4 ms、10 个接触点约 750,000 个样本"——实测完全一致。
**每秒 2,500 个样本与每秒 14,021 次运算的最重 profile 相比是同一量级**，因此重采样样本
必须计入每事件代价，不能当成免费的归一化。一小时 @1 ms 无溢出。

### 9.4 D1 的格点相位

格点锚定在 requirement 自己的 `arm`：同一 requirement 两次求值给出同一组采样时刻，
锚点平移 1 ms 则时刻集合改变。这正是 D1 的修法，且它使"采样时刻与前序输入无关"可测。

**两套格点的关系也测了**（见 §9.6），因此压测 L1 的这条要求不再是未验交叉。

### 9.5 重建误差随上报率下降，但不到零

同一条平滑运动，以三种上报率取样，再按 §5.2 的线性插值在 4 ms 规范格点上求值，
与精确位置的偏差（1/1024 px 单位）：

| 设备上报间隔 | 1 秒内原始事件数 | 格点样本数 | 格点上最大位置误差 |
| --- | --- | --- | --- |
| 1 ms | 2,001 | 250 | 1 |
| 4 ms | 501 | 250 | 1 |
| 8 ms | 251 | 250 | 98 |

**格点样本数完全相同（250），这与设备无关；误差不同，这无法与设备无关。** 这正是方案 A
承诺的边界：统一的是表示与求值时刻，不是信息。8 ms 设备的重建轨迹比 1 ms 粗两个数量级。

### 9.6 电平变化的检出延迟有一个周期的上界

电平谓词只在唤醒时刻被求值，因此"谓词在两次唤醒之间改变"最多迟到**一个采样周期**。
实测：4 ms 周期下，在周期内均匀取多个偏移，最坏检出延迟 3,863 us，未超过 4,000 us 的周期。

这条与 §9.4 的格点相位合起来回答了压测 L1 的问题：**重采样格点决定"何时被唤醒"，
`every` 格点也决定"何时被唤醒"，两者的相位都锚定在声明过的时刻，因此延迟有上界且可预知。**
不过两者仍是两套相位——重采样格点由域声明，`every` 格点由 `arm` 决定——所以"相位关系必须
一并定死"这条要求**成立但尚未合并**：本次验证了各自的相位是确定的，没有验证两者叠加后的
联合最坏延迟。这属真正的 L1 实现。

### 9.7 D12 修复与跨编译器复测（2026-10-01）

原始第三轮逐行比对发现，除耗时列外只有一行不同：

```text
GCC    | Segment | <= half width | 8.0 | 11.3% |
clang  | Segment | <= half width | 8.0 |  0.1% |
```

手算该形状的容忍率约 0.0625%，即 **clang 一侧接近预期，GCC 一侧受溢出影响**。

**根因**：`Segment::contains` 的判定式用了平方比较

```text
cross = dx * py - dy * px              // Segment 长度为 100 显示像素、采样点纵坐标最大 200 px
命中  <=>  cross * cross <= halfWidth * halfWidth * len2
```

以 1/1024 px 为单位时 `dx = 102400`，`|py|` 最大 `204800`，于是 `cross ≈ 2.1e10`，
`cross² ≈ 4.4e20`，**远超 `int64` 上限 9.22e18**。有符号整数溢出在 C++ 里是未定义行为，
两个编译器各自选了一条分支，于是同一份输入给出不同的判定结果。

**这与 §5.5 的整条论证直接相关。** §5.5 主张"决策侧只看一次性量化投影"，本次是它的第一次
跨编译器实测，结果是：**整数本身不保证确定，必须同时证明每一项都在量程内。** 声称"整数运算
逐位可复现"之前，必须先给出坐标量程、形状尺寸与乘加次数的显式上界，并据此证明判定不等式
的每一项不溢出；否则两个编译器可以合法地给出不同答案。

**为什么这一条比一个 bug 更重要**：它是"设计已收敛"之后第二次由实测发现问题（第一次是
§4.1 的 D11），而且两次都属于同一类——**文档写下了性质，却没有写下使该性质成立的条件**。
D11 缺的是"事实顺序"，本条缺的是"量程"。这类缺口逐案例推演查不出来，只能靠**跨实现对照**
（跨编译器、跨枚举顺序）暴露。

**修复**：spike 的 `Segment`、`Strip` 与 `Corridor` 统一使用有符号/无符号宽整数中间值，
并对平方、乘法和加法做显式范围检查；超出声明量程时显式拒绝，而不是执行有符号溢出。
这保持了含边界的原判定关系，并覆盖了同类平方比较路径。

**复测**：重新构建 GCC 16.1.0 与 clang 22.1.8（MSVC ABI），两个二进制均通过 spike 自检。
逐行比较两份完整报告，除运行耗时列外无差异；五个 profile 摘要和 §9.2 的 Segment 行均一致，
Segment 容忍率均为 0.1%。因此 D12 的 spike 实现缺陷已处置，判定域量程规则仍作为设计约束保留。

## 10. 连续音符断连宽限压测（2026-10-01）

本轮新增的被测对象仍是 `tools/research/gameplay_fold_spike/` 内的独立 spike，未进入产品
构建。最小模型只增加一个隔离的 `continuity.*`：

```text
handoff Hold       Follow -> Gap(releasedAt) -> Follow，复用 holdGrace
连续 Slider        同一条 Gap 路径，保留 seg、移动进度和已发出的 head Fact
sticky             不允许重新 claim；仍由宽限计时器产生一次 Break
恢复按下           参加普通 consume 候选集，不无条件抢占新音符
持续结果           宽限内断开按有效连续区间归一化，不增加 reconnect Fact
```

### 10.1 定向案例

| 案例 | 验证内容 | 结果 |
| --- | --- | --- |
| C1 | Hold 全程按住基线 | `HeadHit + BodyHit` |
| C2 | 一次宽限内松开/重按 | 与 C1 判定摘要相同 |
| C3 | 多次宽限内断开 | 与 C1 判定摘要相同 |
| C4 | `releasedAt + holdGrace` 的严格边界 | 不恢复，产生一次 `Break` |
| C5 | 超过宽限后再次按下 | 不重复 `Break`，后续按下为 stray |
| C6 | Slider 断开恢复 | `seg` 保持，路径进度不回退，只有一个 head |
| C7 | Gap 恢复与新头部竞争 | 恢复按下走普通仲裁，新头部可获胜 |
| C8 | sticky 连续音符 | 不恢复，产生一次 `Break` |
| C9 | 在 Gap 中做快照/恢复 | 与连续运行的判定和 `seg` 摘要相同 |

9 个定向案例全部通过。C2/C3/C6/C9 使用判定摘要（Fact 与 stray）对比基线；C6 另外检查
最终 `seg=4` 且 `HeadHit` 计数为 1。

### 10.2 并发压力

压力谱面包含 2,048 条 handoff Hold，每条包含 6 次宽限内断开/恢复，共 26,624 个输入事件。
为了只测连续性状态，256 个 lane 的相邻头部窗口互不重叠。结果为：

| 编译器 | heads | bodies | breaks | strays | 运行时间 |
| --- | ---: | ---: | ---: | ---: | ---: |
| GCC 16.1.0 `-O2` | 2,048 | 2,048 | 0 | 0 | 123.96 ms |
| clang 22.1.8 MSVC target `-O2` | 2,048 | 2,048 | 0 | 0 | 99.86 ms |

连续性章节的定向输出与状态摘要在两个编译器之间逐行一致；仅压力运行时间不同。既有五个
profile 的摘要仍为 `63ff9cebc811ee9a`、`c862befbe096f01c`、`357c381fdd3a4744`、
`f07c2f59c8b62dd4`、`0de3815ce79887d8`。

### 10.3 C10-C14 prepared grace 矩阵

第二轮把统一的 `holdGrace` 扩展为最小的 prepare 模型：每条 requirement 解析自己的最终
`effectiveGrace`，并记录 `graceResolutionPolicy = 1`。运行时只读取冻结值；来源
`explicit` / `inherited` 保留在内容与诊断摘要。GCC 与 clang 的结果逐行一致：

| 案例 | 验证内容 | 结果 |
| --- | --- | --- |
| C10 | 同一谱面短宽限与长宽限并存 | 短值断开，长值恢复 |
| C11 | `grace = 0`、最小值、最大值 | 零值同 Tick 不恢复；最大值在 119,999 us 恢复 |
| C12 | explicit / inherited 与 policy identity | 最终值相同则 JudgementIdentity 相同；ContentIdentity 来源不同；policy 变化导致 JudgementIdentity 变化 |
| C13 | prepare 后将运行中 Hook 改为 0 | 已准备的 60 ms 不被追溯修改 |
| C14 | Slider 尾部 `max(W.max.late, grace)` | `20 ms` 尾窗与 `60 ms` grace 得到 `deadline = t1 + 60 ms`，尾部未提前结算 |

五项全部通过。连续性专用章节和既有 profile 摘要在两个编译器之间逐行一致；仅运行耗时不同。

### 10.4 代表性研究切片与预算测量

为补齐进入 I 前的测量证据，本轮增加一条确定性的**代表性研究切片**：96 条
Hold / Slider requirement，8 条 lane，显式 `grace` 取 20/60/100 ms，包含每条连续音符
一次宽限内断连、Slider 段进度恢复、尾部恢复和 24 个快照恢复点。它不是正式作者谱面，
不进入产品 fixture，也不改变任何 ABI 或生产预算。

| 编译器 | requirements | input events | activity peak | Gap timer peak | max snapshot bytes | seek p95 ms | seek max ms | lossless |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | --- |
| GCC 16.1.0 `-O2` | 96 | 672 | 3 | 2 | 4,777 | 0.014 | 0.107 | yes |
| clang 22.1.8 MSVC target `-O2` | 96 | 672 | 3 | 2 | 4,777 | 0.015 | 0.119 | yes |

该切片的 Gap 区间在同一时刻最多重叠 2 个；它用于验证计算路径和快照无损性，不能代表
高密度真实谱面的最坏 activity。测量值只作为候选预算的补充证据，不冻结 `activityPeak`、
`maxSeekLatency` 或任何 ABI 限制。

### 10.5 结论与边界

这次压测支持“复用 `handoff + Gap + holdGrace` 是可行的最小实现”：不需要新增 Hook、Pattern
算子或 `reconnect` Fact；Slider 只需在 Gap 中保留已有的段号和路径进度。严格 `<` 边界、一次性
`Break`、普通仲裁、Gap 快照、逐音符 prepared grace、identity policy 和 Slider deadline 均有
研究性 spike 证据。

这不是产品实现，也不是 Stage 7A 验收：模型没有接入 `engine/`，没有验证真实几何路径、设备
事件采样丢失、音频时钟或完整判定/计分折叠。连续 Slider 的实际区域判定仍需在后续实现阶段
接入现有输入与几何模型后复测。
