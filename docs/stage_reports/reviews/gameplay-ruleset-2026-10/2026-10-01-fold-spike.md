# Gameplay Fold Spike：预算实测与确定性检查

状态：dated evidence（研究性 spike，不是实施；2026-10-01 快照）

更新日期：2026-10-01

本报告记录对 [Gameplay 预算与规模上界草案](../../../proposals/GAMEPLAY_BUDGET_AND_SCALE_DRAFT.md)
的第一次实测。被测对象是一个**独立的研究性 spike**，位于 `tools/research/gameplay_fold_spike/`：
不进产品构建、无 CMake target、不链接任何 Cuexis 库，也不是 Stage 7A 的实施。它的唯一用途是
给候选预算表填上第一批数字，并检验设计中的三条确定性声明。

当前状态仍以 [CURRENT_STATUS.md](../../../CURRENT_STATUS.md) 为准；本报告不改变任何阶段状态。

## 1. 被测内容与边界

```text
pattern.*   Pattern -> NFA -> 子集构造 -> 最小化；补在完整 DFA 上取；状态预算指出失败子表达式
runtime.*   Tap / Hold / Bomb / Roll 四种标准条目
            同 Tick 四阶段顺序（激活 / 定时器 / 输入 / 折叠）
            按 claimKey 仲裁、fanout 1、bomb 走 observe 边
            every(period) 采样，格点锚定在 arm（D1 的修法）
            派生 Hook windowScale，只在折叠阶段写，t+1 生效
            L3 折叠 + 一个限时模块（每 100 连击窗口放宽 10%，持续 5 s）
            规范化快照 / Seek
main.cpp    合成谱面与合成玩家，五个 profile
```

**不覆盖**：多接触点、几何与 frame、Controller、输入重采样、内联 Pattern 的运行时执行
（运行时按标准条目直接实现，Pattern 编译只用于测状态规模）。这些需要后续 spike。

**合成数据的局限**：谱面与玩家都是程序生成的。数字代表"这套执行模型在这些负载形状下的
代价"，不代表任何真实游戏的谱面分布。

## 4. 发现

### 4.1 新缺陷 D11：同 Tick 内 Fact 的折叠顺序依赖实例枚举顺序

**现象**：mixed-40k 在正向与反向枚举实例时结果摘要不同。定位到第一处差异：同一次按下在
同一 Tick 内引爆了同一轨道上的两个炸弹（requirement 32 与 40），两条 `Detonated` Fact 的
发出顺序随枚举顺序互换。

```text
正向   2280405 req=32 Detonated / 2280405 req=40 Detonated
反向   2280405 req=40 Detonated / 2280405 req=32 Detonated
```

**根因**：[Ruleset Fold Language 草案](../../../proposals/GAMEPLAY_RULESET_FOLD_DRAFT.md) §2.1
第 4 步规定"按发出顺序折叠本 Tick 产生的 Fact"。L7 的结构性保证只覆盖 **Hook 读取**
（同 Tick 内所有实例读到同一份 Hook），不覆盖 **Fact 发出顺序**——后者在 observe 边会让
一次输入同时结算多条 requirement 时，取决于实现遍历实例的顺序。

**后果**：本例中计分是可交换的，最终分数相同，只是 Fact 流（以及 Replay 可见的事件序列）
不同。但 L3 是可分发内容，任何对顺序敏感的处理器（"本 Tick 第一条 Fact 触发技能"、
按序累计的状态机）都会让同一输入得到不同结果。这与 D4 是同一类错误：一条没写死的顺序规则。

**修法（spike 已验证）**：折叠前把本 Tick 的 Fact 按 `(requirementId, phase, outcome)` 排序。
`requirementId` 已随 Fact 暴露（讨论记录第 47 条），因此这条规则不需要新字段。开启后五个
profile 正反枚举全部一致；关闭时 mixed-40k 复现差异。D11 的这一对照在 spike 报告的 B2 节
自动重跑。

**为什么之前没发现**：34 项案例与封闭性验证都是**逐条 requirement** 检查的，而 D11 只在
"一次输入、多条结算"时出现——它是跨实体的，正落在 Fold Calculus §2.1 说的核心边界之外。
这再一次说明跨实体语义需要按类检查，而不是逐案例检查。

### 4.2 预算草案 §7.5 的签名要求得到证实，且后果比预计更具体

预算草案只说"扫描线必须接收 Loadout 的窗口缩放取值"。实测表明后果不是"活动度估低"，而是
**判定结果改变**：若 `arm` 用基础缩放计算，实例在放宽窗口的前沿尚未激活，提前按下找不到
候选，变成 stray，音符随后 Miss。结论应写得更直接：**`arm` 是判定语义，不只是预算输入。**

### 4.3 活动度与 40,000 的关系：数量级成立

预算草案 §3.1 估计 40,000 条要求的平均活动度约 27。实测：

```text
tap-40k     实测最大存活 27，静态扫描峰值 36
mixed-40k   33 / 50
burst-40k   52 / 91（327 音符/s，远超常规谱面）
```

"整曲计数与瞬时计数相差约两个数量级"成立。静态扫描峰值是实测值的 1.3–1.8 倍，作为
保守上界可用。

### 4.4 稳态代价不是瓶颈

在本模型的计数下，最重的 profile（burst-40k）单 Tick 最多 94 次运算，每秒 14,021 次；
完整五分钟曲目单线程 11–30 ms 跑完。**以本 spike 的执行模型，L2 + L3 的稳态代价比渲染
低数个数量级**，`eventBudget` 的瓶颈不会在判定侧。

### 4.5 周期采样是稳态里唯一随长条线性增长的项

`samples/s` 列显示：Tap-only 为 0，长条比例越高越大（long-hold-4k 达 3,324/s，是该 profile
运算量的主要来源）。与压测 L3 的判断一致，但量级比"1.2e10"那个最坏估计低得多，
因为同时处于采样态的实例数实测只有 10–20 个。

### 4.6 快照极小，Seek 延迟与间隔近似线性

单快照约 1.2 KiB（只存存活实例、待触发定时器与折叠状态）。60 s 间隔下最坏 Seek 6 ms。
预算草案 §4.4 的不等式在本规模下**远未逼近边界**，因此"第一版只做全量快照"的裁决
（预算草案 §7.3）得到支持。

### 4.7 补的规模：常规条目远离预算，对抗输入被正确拒绝

标准条目的最小 DFA 在 8–122 状态之间；补出现在 Hold 与 Bomb 中，操作数最大 32。
对抗性 `¬(any* · press · any{n})` 在 n=10 处超过 4,096 预算，被拒绝且诊断指向子表达式。
这证实"补进预算、不进 capability"（预算草案 §3.3）在实践中可行：规模门能挡住指数爆炸，
同时不误伤常规条目。

**一处次要发现**：Tap 的 NFA 规模随窗口线性增长（窗口 120 时 2,166），主要来自
`repeat(any, 0, w)` 的展开。最小化后只剩 122。编译器若在构造中途检查规模，应检查
**确定化后**的状态数，而不是 NFA 规模，否则会误伤宽窗口条目。

## 6. 局限

1. 合成谱面与合成玩家，不代表真实分布。
2. 只测了四种标准条目；内联 Pattern 的运行时执行、多接触点、几何与 Controller 未覆盖。
3. 运行时按条目手写，而不是执行编译出的自动机。§8 的差分测试部分补上了这一项：短轨迹上
   编译产物与参考谓词一致，但运行时仍然不执行自动机，因此"运行时行为"与"编译产物"之间
   仍是两套实现。
4. 两个编译器都在 Windows x86-64 上；跨 OS 与跨架构的逐位一致尚未验证。
5. 耗时为单次运行，仅作量级参考。

## 7. 多接触点场景（第二轮）

第一轮只覆盖单轨道的单次按下，因此 §4.5 的归属、可见性与换手规则没有被测。第二轮补上：
多接触点模型 + 十一个定向场景，每个场景先写下设计文档的预期，不一致即失败。

| 场景 | 预期来源 | 结果 |
| --- | --- | --- |
| S1 同轨两个 Tap，相隔 30 ms | 仲裁取 `claimKey` 最近者 | 两个分别被就近的按下命中 |
| S2 一次按下、两条同锚点 Tap | 默认 fanout 1 | 只结算一条，另一条 Miss |
| S2b 同上，fanout = all on equal anchor | Ruleset 声明 | 两条都结算 |
| S3 sticky Hold 被第二个接触点中途按下 | §4.5 第 3 条 | 不换手，主体 `Broken` |
| S3b 同上，`strayWhen = noCandidate` | D10 精化后的定义 | 该按下被考虑过并拒绝，不是 stray |
| S4 handoff Hold 在宽限内换手 | §4.5 第 3 条 | 换手成功，主体 `Hit` |
| S5 炸弹（observe）与 Hold（claim）同按 | §4.5 第 2 条 | 都看见，只有 Hold 拥有 |
| S6 比 good 窗口晚 130 ms 按下 | 无候选 | Miss + stray |
| S6b 同上，`strayWhen = noCandidate` | D10 | 没有任何实例考虑过，是 stray |
| S7 槽位复用，原持有者接触点已终止 | D9 的修法 | 隐式替换，两个都命中 |
| S7b 同槽位，原持有者接触点未终止 | D9 的修法 | 活着的归属挡住第二个 |

### 7.1 由这批场景精化的两条规则

**D10 的 `noCandidate` 定义。** 原写法是"完全没有任何实例监听该输入"，实测发现它与
`consumeEmpty` 的区别不在"监听"，而在"**考虑过但拒绝**"。三种拒绝原因（接触点被独占、
窗口不匹配、实例已结算）都算考虑过。S3 正是第一种：sticky Hold 的边看过第二支手并因归属
拒绝，所以它不该算 stray。定义已改为"没有任何实例考虑过"，并写回压测文档。

**换手是一次消费。** spike 最初把 handoff 写成边上的无条件接管，S4 通过但 S3 失败——
因为"接管"绕过了候选集，于是 `sticky` 与 `handoff` 的差别被实现成了别的东西。正确形式是：
换手的边与同一按下上的其他 `consume` 边一起参加 `claimKey` 比较。这条已写回 Program IR
§4.5：`handoff` 的宽限窗口是**边上的谓词**，进候选集计算，而不是先于候选集判断。

### 7.2 Hold 的头部与主体是两条独立 Fact

S3 与 S5 的输出显示：中途断开时头部已经发出 `Hit(head)`，主体再发 `Broken(body)`，
两条事实同时存在。这不是 bug，而是 V2 修补（允许多分量 Measure）的直接结果，但原文档
没有说明它们的关系。裁决是**不做互相撤销**：是否把断开的 Hold 的头部命中计入连击由 L3 的
折叠规则决定。已写回 Program IR §4.5。

## 8. 差分测试：编译产物与手写条目是否同义（第二轮）

第一轮局限 3 指出：运行时按条目手写，没有证明"编译后的 Pattern 与手写语义等价"。
第二轮补上：为四种条目各写一个**独立于 Pattern 构造的参考谓词**，在字母表
{press, release, held, not-held, idle} 上枚举长度 0–5 的全部 3,906 条轨迹逐一比对。

| 条目 | 轨迹数 | 结果 |
| --- | --- | --- |
| Tap，窗口 3 | 3,906 | 一致 |
| Hold 主体，grace 0 / 1 / 2 | 3,906 × 3 | 一致 |
| Bomb，窗口 3 / 1 | 3,906 × 2 | 一致 |
| Roll，2 / 3 次 | 3,906 × 2 | 一致 |

八项全部一致，即 **31,248 条轨迹零反例**。这不能证明对所有长度成立（枚举只到 5 步），
但它排除了最常见的构造错误：`hole` 与 `gap` 的混淆、补的方向、`repeat` 的边界偏移。
grace=0/1/2 三档覆盖了"阈值为 0"这个容易出错的边界。

**仍未证明的**：长轨迹上的等价（需要随机化或符号方法），以及 Tap 的 120 ms 窗口在真实
采样率下的行为。这两项属后续 spike。

## 9. 几何、frame 与量化（第三轮）

补上 §4.3 的几何原语、§5.4 的 frame 与 §5.5 的数值模型。裁决侧的算术全部是整数；
报告里唯一的浮点用于算参考值以量误差。

| 项目 | 结果 |
| --- | --- |
| 定点表误差（1/65536 圈，Q16 值） | 0 单位（表本身就是"最接近的整数"这一语义） |
| 四分之一圈 ×4 回到原点 | 精确，零漂移 |
| 一次旋转的误差（1/1024 px 单位） | 1.489 |
| 串联两次旋转的误差 | 2.305，即一次旋转的 1.5 倍 |
| frame 求值（64 分段） | 每次 7 次比较，log₂64 = 6，符合 O(log N) |
| 区域命中代价 | Disc 5 次运算 / Rect 4 / Strip 9 / Segment 8，均为常数 |
| 反变换往返 | 误差 ≤ 1 单位 |

### 9.1 D6 的取整规则得到验证

**"仿射变换是单次量化运算"这条规则有实测依据。** 串联两次旋转的误差是一次旋转的 1.5 倍
（1.489 → 2.305 个 1/1024 px 单位），而且误差方向不可预测。这与 §5.5 的"禁止在同一表达式里
串联多次旋转"一致：串联不只是"多一点误差"，而是让误差随串联层数累积并失去简单上界。

**四分之一圈可精确表示**这一点值得单独记录。它是四类常见角度（0、90、180、270 度）中的全部，
因此**标准正交的判定线旋转不产生任何漂移**，只有任意角度才产生上表中的 1.5 单位误差。

### 9.2 区域形状的边界约定

四种形状的边界都是**含**的（`<=`），包括半宽为 0 的 Segment。这必须写进规范，否则
"正好在边界上"会在实现之间分叉。命中代价是常数，`contains` 不进 O(log N)，只有 frame
求值是 O(log N)。

### 9.3 输入重采样的样本量（回应预算草案 §5.2 的附带成本）

| 接触点 | 周期 | 域时长 | 样本数 | 每秒 |
| --- | --- | --- | --- | --- |
| 1 | 4 ms | 300 s | 75,000 | 250 |
| 10 | 4 ms | 300 s | 750,000 | 2,500 |
| 10 | 8 ms | 300 s | 375,000 | 1,250 |
| 10 | 4 ms | 600 s | 1,500,000 | 2,500 |

预算草案 §5.2 原估"5 分钟、4 ms、10 个接触点约 750,000 个样本"——实测完全一致。
**每秒 2,500 个样本与每秒 14,021 次运算的最重 profile 相比是同一量级**，因此重采样样本
必须计入每事件代价，不能当成免费的归一化。一小时 @1 ms 无溢出。

### 9.4 D1 的格点相位

格点锚定在 requirement 自己的 `arm`：同一 requirement 两次求值给出同一组采样时刻，
锚点平移 1 ms 则时刻集合改变。这正是 D1 的修法，且它使"采样时刻与前序输入无关"可测。

**一处仍未验的交叉**：重采样格点（L1，按域声明的 `inputRate`）与 `every` 格点（按 `arm`）
是两套相位。压测 L1 已要求"两者的相位关系必须一并定死"，本次只验证了后者。前者需要
真正的 L1 实现才能测，登记在后续。
