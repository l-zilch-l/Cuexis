## 问题 1：仓库版本号更新落后，需增加强制更新约束

状态：open

### 现象

当前仓库构建版本仍为 `26.08.01-1`（`cmake/CuexisVersion.cmake` 与 `vcpkg.json` 的
`version-string` 一致），但后续多个合并门禁未伴随版本更新：

- Stage 5 已于 2026-08-28 经 PR #20 合并至 `master`（合并提交 `d380fc9`）。
- `260829-full-review` 已于 2026-08-30 经 PR #21 合并至 `master`。
- `260830-followup` 已于 2026-09-01 经 PR #22 合并至 `master`。

即至少三次 merge/release 门禁未执行 [VERSIONING.md](../../../guides/VERSIONING.md) 规定的
“日期构建版本只在 merge/release 门禁更新”，版本号与实际合并历史脱节。

### 影响

- 显示版本 `26.08.01-1` 无法区分上述合并点，窗口标题与启动日志不能反映最新合并，版本身份失去
  追溯意义。
- 与版本政策的执行约定不一致，形成门禁缺口。

### 后续约束（待补充并落地）

增加**强制更新约束**：每次合并至 `master` 的发行门禁必须伴随一次
`python -B tools/update_version.py yy.mm.dd-v` 版本递增（日期变化则 build=1，同日期再次发布
则 build+1），并把“版本已更新”作为门禁的显式检查项，未更新则门禁失败。具体措辞与落点
（`VERSIONING.md` 或相应阶段计划/门禁）待与项目所有者确认后写入权威文档。

## 提案 1：分期退出 Chart v1–v3 谱面支持

状态：candidate（待项目所有者决策）

### 背景

当前 `cuexis_chart` 同时维护 v1/v2/v3（`canonical_chart_loader`）与 v4（`chart_v4_loader`）两条
Reader 路径，且 v3 仍是默认写出口（`chart_writer.cpp` 默认写 `version: 3`）。维护 4 个版本的
读取、迁移、测试与 golden 矩阵会随新字段持续扩大，形成可预见的长期负担。Simple Chart 的先例
（[ADR 0035](../../../adr/0035-retire-simple-chart-format.md)）已证明：当并行格式迫使每个新字段
同时设计多套语义时，收敛到单一格式是正确方向。

### 提案

长期收敛到 Chart v4，按 [ADR 0041](../../../adr/0041-legacy-format-exit-policy.md) 的版本化退出
节奏分两步退出 v1–v3，而非一次删除：

#### 第一步：冻结前进方向（不破坏兼容）

- 把默认 Writer 切到 v4（`--target 4` 成为默认），v3 写出口仅保留为显式 opt-in。
- 在格式能力矩阵与文档中把 v1/v2/v3 标记为 legacy，不再是默认前进格式。

#### 第二步：版本化退出（需新 ADR + SDK minor 提升）

- 先做一次性迁移窗口：仓库内 v1–v3 fixture 用现有 migrator 转 v4 并提交；仓库外资产盘点由
  项目所有者确认。
- 一次性转换物冻结在最后支持 v1–v3 的版本，不进入长期公共 API。
- 然后在新 ADR 中删除：旧 Reader 路由、旧 Schema 产物、旧迁移入口、旧 fixture/golden。
- 每项删除带 characterization、稳定拒绝测试、diagnostics fingerprint 与 hosted consumer 证据。

### 拒绝的方案

- 直接删除 v1–v3 而不先切默认 Writer：会删除自己默认产出的格式，自相矛盾。
- 保留 v1–v3 只读 Importer：等同长期维护第二套 Reader、预算、诊断与测试矩阵。

### 影响范围（爆炸半径）

- `chart_migrator` 的 v1/v2→v3 与 v1/v2/v3→v4 迁移入口。
- 源树内 v1×5、v2×1、v3×4 的示例/fixture/golden。
- `schemas/cuexis.chart.v1..v3.schema.json`。
- 外部 consumer 持有的 v1–v3 谱面（需盘点）。
- SDK/API 版本目标：移除公开兼容行为需 minor 提升（如 0.7.0 → 0.8.0）。

### 前提与验收

- 一份新 ADR（背景/取舍/迁移说明/拒绝方案）+ 项目所有者接受。
- external-consumer 门禁、稳定拒绝回归、diagnostics fingerprint、hosted 证据（ADR 0041 验收条款）。

### 待决策

- 是否接受本提案方向；是否启动第一步（默认 Writer 切 v4）。
- 是否将本提案升级为正式 ADR。

## 问题 2：渲染后端抽象过薄，阻碍 Vulkan 接入

状态：open

### 现象

当前渲染兼容层“隔离”了 OpenGL，但未“抽象”它。代码证据：

- `engine/render/include/cuexis/render/render_backend.hpp` 的 `RenderBackend` 唯一虚函数是
  legacy 的 `renderFrame(RenderFrame)`（只画 DebugLine，诊断用途）。
- 当前正式路径 `OpenGlBackend::renderPresentationFrame(FrameSnapshot, ...)` 是
  `engine/render_opengl/include/cuexis/render_opengl/open_gl_backend.hpp` 上的**具体方法**，
  不进任何虚接口；Player 直接持有 `OpenGlBackend` 调用它。
- 后端创建绑定 SDL+GL：`configureOpenGlContext(SdlRuntime&, ...)` 与
  `OpenGlBackend::create(SdlWindow&, OpenGlContextConfiguration&&)` 把创建流程焊死在 GL context
  与 SDL runtime 上。
- `OpenGlBackend` 直接持有 `SdlWindowLease window_` 与 `void* context_`，窗口表面所有权与渲染器
  未分离。
- `OpenGlDrawCommand` / `OpenGlDrawSummary` / `OpenGlPixelProbe` 都位于 `render_opengl`
  命名空间，前端无法共享这些大半是后端中立的 draw 状态。
- `RenderScene` 只有 `DebugLine` 一种命令，内容渲染完全绕过它走 `FrameSnapshot`，形成
  legacy DebugLine 与 portable Presentation 两条平行路径。

### 影响

- Stage 10（Vulkan adapter）接入时需要新增一套 `VkInstance/VkDevice/VkQueue/VkSurface/VkSwapchain`
  的创建与呈现生命周期，当前 `RenderBackend` 没有后端中立工厂或呈现接口可复用。
- 若不强抽象，Vulkan 会形成第三条渲染路径，或迫使前端反向依赖 `render_opengl` 类型，违反
  “adapters consume portable/public values” 的架构边界。
- Shader 绑定布局（set/binding→texture unit）在 OpenGL 适配器内实现，Vulkan 需要的
  set/binding→descriptor set 映射无共享层可复用（SPIR-V 是规范 IR，此点非致命）。

### 后续约束（待补充并落地）

在 Stage 10 启动前应补齐三件事：

1. 把 `renderPresentationFrame` 提升为后端中立的 `IPresentationRenderer` 虚接口，OpenGL 与
   Vulkan 各自实现。
2. 抽出后端中立的创建/所有权契约，分离“窗口表面”与“渲染器”两个生命周期。
3. 把 `OpenGlDrawCommand`/`OpenGlDrawSummary` 这类可移植 draw 状态下沉到 `cuexis_render`，
   让多后端共享命令生成。

具体接口形状与落点（Stage 10 计划或 ADR）待与项目所有者确认后写入权威文档。

### 已友好的部分（不构成问题）

- 可移植表现值（`FrameSnapshot`/`PresentationResourceRef`）后端中立，Vulkan 可直接消费。
- SPIR-V 是规范 IR（ADR 0021），ShaderAsset 源对 Vulkan 现成。
- 三层 capability 模型（Portable / Built-in Renderer / Host extension）已预设多后端。
- OpenGL/GLAD 类型已正确私有隔离在 `render_opengl`。

## 问题 3：当前无法直接使用常见图片/音频，Stage 6 需增加常用媒体格式支持

状态：open

### 现象

**图片**：引擎没有任何图片解码器：在 `engine/` 全树搜索 `jpg`/`jpeg`/`png`/`stb_image` 零匹配。
纹理必须是便携 `CXPRES01` 的 `.texture.bin`（24 字节 envelope + 宽/高/色彩空间 + 裸 RGBA8 像素），
网格/材质同理是 `.mesh.bin`/`.material.bin`。用户提供的 `test.jpg` 需手动解码成 RGBA8 再包成
`.texture.bin` 才能被 Player 消费。

**音频**：Player 只支持无压缩 WAV（`audio_sdl::WavDecoder`）：PCM 整数 8/16/24/32 位或 IEEE F32，
单/双声道，8000–192000 Hz；不支持 mp3/ogg/aac/flac 等压缩格式。

### 影响

- 内容创作/宿主接入不便：无法直接用 jpg/png 等常见图片与 mp3/ogg 等常见音频，需要专用转换工具
  或解码器。
- demo 示例（`assets/projects/demo20s`）的纹理就是手动从 `test.jpg` 转成 `.texture.bin` 的结果。

### 后续约束（待补充并落地）

Stage 6 应增加常用媒体格式支持：在导入/打包路径把常见图片（jpg/png）解码为 `CXPRES01`
`.texture.bin`、把常见音频（mp3/ogg/flac 等）解码为可消费的 WAV/PCM，或引入对应解码器
（如 stb_image、miniaudio 等）并同步更新依赖政策
（[DEPENDENCY_POLICY.md](../../../guides/DEPENDENCY_POLICY.md)）与 `THIRD_PARTY_NOTICES.md`。
具体范围、解码器选型与落点（导入工具 vs 运行时）待与项目所有者确认后写入权威文档。
