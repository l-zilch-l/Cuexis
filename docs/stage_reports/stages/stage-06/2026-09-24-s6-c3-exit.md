## 2. 计划项对照

计划第 1 项（统一命令入口和状态转换表）：

- 应用状态 `PlayerAppState`：`Empty`、`Loaded`、`Playing`、`Paused`、`Stopped`、`Failed`。
  它没有扩张公共 `playback::SessionState`。
- `PlayerCommandKind`：`Load`、`Play`、`Pause`、`Stop`、`Seek`、`Reload`、`Rebuild`。
  `evaluatePlayerCommand` 是纯函数转换表，`PlayerCommandContext` 只带当前状态和
  `transactionInProgress`。
- loading/reloading 期间：`load`、`reload`、`rebuild` 由 `TransactionGuard` 独占，期间任何
  命令都返回 `player.command.transaction_in_progress`，不存在交错事务。
- 重复命令策略：稳定的拒绝码 `player.command.duplicate`，并带 `duplicate=true` 上下文，
  因此调用方可以区分「已经在该状态」和「非法转换」。`Load` 永远被接受；`Rebuild` 是
  `Failed` 的恢复入口。
- 拒绝码还有 `player.command.not_loaded`、`player.command.not_playing`、
  `player.command.failed`、`player.command.unknown`、`player.command.mode_required`、
  `player.command.mode_change_requires_load`、`player.command.seek_not_finite`、
  `player.command.seek_negative`、`player.command.seek_outside`。

计划第 2 项（正式用户入口）：

- 命令表在 `cuexis_player_support`（`player_command.hpp` / `player_command.cpp`），只依赖
  `cuexis_core`，不含 Playback、SDL、OpenGL 或 JSON DOM。
- 真正调用 `PlaybackSession` 和 `IPresentationRenderer` 的代码在
  `app/player/src/player_control.cpp`。`PlayerControlPorts` 把来源解析、clip 准备和设备打开
  交给装配层，控制层只按事务顺序调用。
- Player 的生命周期不再由 smoke 分支单独实现：`player_app.cpp` 用 `apply(Load)` 和
  `apply(Play)` 启动，`player_smoke.cpp` 的全部内容生命周期也走同一 `apply`。smoke 里剩下的
  直接调用只是不提交内容的负例探针和像素/digest 断言。
- 窗口输入已经接入同一命令层。`PlayerSurface::pollInput` 返回中立的 `PlayerInputAction`，
  SDL 按键到 action 的映射在 `player_assembly.cpp`，action 到 `PlayerCommand` 的映射是
  `playerCommandForInput` 纯函数。按键绑定：

  | 键 | action | 结果命令 |
  | --- | --- | --- |
  | 空格 | `PlayPause` | 播放中发 `Pause`，其他状态发 `Play` |
  | 左 | `SeekBackward` | `Seek{max(0, 当前 chart time - 5000 ms)}` |
  | 右 | `SeekForward` | `Seek{当前 chart time + 5000 ms}` |
  | R | `Reload` | `Reload{KeepChartTime}` |
  | S | `Stop` | `Stop` |
  | B | `Rebuild` | `Rebuild` |
  | Esc | `Quit` | 离开帧循环，不产生内容命令 |

  按键在 `WindowEvents` 里以 `WindowKey` 命名上报，`player_surface.hpp` 和
  `player_control.*` 仍然不含 SDL、OpenGL、GLAD 或 AudioSDL。被拒绝的输入只记一条
  `player.command` 警告，不终止播放器。

计划第 3 项（边界行为）：

| 行为 | 结果 |
| --- | --- |
| 负时间 Seek | `player.command.seek_negative`，不接触 transport |
| 超出可播放范围 | transport 返回 `audio.transport.seek_range`，带 `command=seek`，位置不动 |
| 暂停中 Seek | 合法，保持暂停状态，发布一个 discontinuity |
| 停止后 Play | 从 chart time 0 重新开始（ChartClock）或交给 transport（CuexisAudio） |
| 有音轨 EOF | 设备报告 `Ended` 时应用转 `Stopped`，位置保留；设备报告 `Error` 时转 `Failed` |
| 无音轨 | ChartClock 会话，`audio() == nullptr`，不因「长度未知」被停掉 |
| 空内容 | 结构与资源都合法但 `objects` 为空：`Load` 成功，`objectCount == 0`，记一条警告，帧仍然有效 |
| 切换有无音轨 | 显式 `Load`；`Reload` 遇到 mode 变化返回 `player.command.mode_change_requires_load` |
| 显式来源需要音频时钟 | `player.command.mode_required`，不从失败的文件猜 mode |

`ChartClock`、`HostClock` 和 `CuexisAudio` 共用同一 timeline/discontinuity 规则：事务只发布
一个 discontinuity，ChartClock 用 `pendingChartSeekMs_` 在下一帧 rebase，音频路径交给
transport。

计划第 4 项（事务顺序）：`commitBundle` 的固定顺序为

1. 校验 prepared、冻结 timing offset 与 `ResolvedSessionConfig`，准备/重置 `RuntimeTimeline`；
2. `renderer.prepare` 取候选，`prepareClip` 取 clip，同设备时再 `prepareReplacement`；
3. `renderer.accepts` 预检 owner、generation 和 token；
4. 激活音频（设备变化时 `openAudio`，否则 `activateReplacement`），这是最后一个允许在物理
   设备上失败的步骤；
5. `PlaybackSession::commit`，随后 `renderer.activate`（无失败）；
6. 发布 bundle、identity、discontinuity，并换掉 seat 和活动 clip。

软件准备失败（步骤 1-3）丢弃候选和 clip，旧内容、旧资源和旧播放都不变，命令被拒绝但应用
不进入 `Failed`。步骤 4 失败进入 `Failed` 并保留已发布的内容、identity、时间、GPU cache 和
音频句柄，但设备可能已经切换，因此报告不声称硬件可回滚。步骤 5 失败同样进入 `Failed` 并
丢弃候选。提交后的 `present` 失败由 `markFailed` 发布 `Failed`，不回滚内容。

计划第 5 项（同一帧提交）：

- 诊断轴经 `snapshot_scene.cpp` 追加到后端无关的 `RenderScene`，与正式内容在同一次
  `renderer.submit(snapshot, &scene)` 里提交。正式提交仍走 `IPresentationRenderer::submit`
  和 `present`。
- Timeline、renderer 和设备寿命都在应用层。`PlaybackSession` 没有拿到 renderer，也没有
  Player 私有 Runtime。

### 4.1 真实窗口验证发现的缺陷

第一次真实窗口按键验证在按下 `R`（Reload）后立刻让播放器以
`runtime.frame.discontinuity_delta_nonzero` 退出。原因是输入路径在**该帧采样时钟之前**执行
事务：

1. 事务发布新 bundle，重置 timeline 并把 chart clock 的目标设成保留时间；
2. 该帧第一次 advance 消费目标，产生新的 discontinuity id 和零 delta；
3. `consumeBundleReplaced()` 让循环再 advance 一次，这一帧的 discontinuity id 不变但 delta
   变成两次采样之差，非零；
4. `PlaybackSession::update` 收到的正是这个再采样帧，而它上一次收到的帧还是旧 bundle 的
   discontinuity id，于是判定「新的 discontinuity 帧 delta 非零」。

smoke 没有暴露它，因为 smoke 的事务跑在 `afterTimelineAdvance` 里，也就是该帧第一次 advance
之后，再采样帧本身携带新的 discontinuity 和零 delta。

修复有两处：事务发布时不再把 `lastFrame_` 清成默认帧（它必须继续表示「session 真正收到的
上一帧」，它同时是 reload 目标和 discontinuity 基准）；帧循环在再采样后，如果该帧的
discontinuity id 与上一次真正投递给 session 的 id 不同，就把它的 delta 归零。

回归覆盖：新增用例用脚本化 `PlayerSurface` 在输入路径上触发 `Reload`，然后跑完整的
`runPlayerFrameLoop`。修复前该用例以同一个错误码失败，修复后通过。

### 4.2 hosted MinGW 发现的缺陷

`793b451` 的 hosted Windows MinGW 在 `cuexis_platform_sdl` 上失败：

```
engine/platform/include/cuexis/platform_sdl/sdl_window.hpp:34:6:
  error: elaborated-type-specifier for a scoped enum must not use the 'class' keyword [-Werror]
```

原因是新加的 `enum class WindowKey : std::uint8_t` 使用了 `std::uint8_t`，而
`sdl_window.hpp` 只包含 `<memory>`、`<string>`、`<vector>`。MSVC 的标准库会间接带入
`std::uint8_t`，libstdc++ 不会，于是 GCC 把 `enum class WindowKey` 当成 elaborated-type
specifier 解析。修复：给 `sdl_window.hpp` 和同样引用 `std::uint32_t` 的
`player_smoke.hpp` 补上 `<cstdint>`。

本地复现与验证用 ucrt64 的 `g++`：

```powershell
g++ -std=c++20 -fsyntax-only -I engine/platform/include -I engine/core/include `
    -I engine/player_support/include -I out/build/debug/generated `
    -isystem out/build/debug/vcpkg_installed/x64-windows/include <包含这两个头文件的 TU>
```

一个只写 `enum class Foo : std::uint8_t { A = 0 };` 且不包含 `<cstdint>` 的对照 TU 会输出
同一条错误，因此这个本地检查确实覆盖了该失败模式。修复后同样的检查退出码 0，Debug 全量
CTest 仍是 `732/732`。

### 4.3 hosted MinGW 与 MSVC 发现的第二个缺陷

同一次 hosted 矩阵还暴露了两个问题，本机都因为环境不同而看不见。

其一，`PlayerCommand{.kind = ...}` 在 GCC 下触发
`-Werror=missing-field-initializers`：`source` 和 `mode` 没有默认成员初始化器，GCC 对
指定初始化器里被省略且无默认值的成员告警（MSVC 不告警，本机 GCC 也没被用来编译过）。修复：
给这两个成员补上 `{}`，与结构里其它成员一致。本机 `ucrt64` 的
`g++ -std=c++20 -Wall -Wextra -Wpedantic -Werror -fsyntax-only` 对三种调用形式都通过；
对照实验确认，被省略的成员没有默认值时才告警。

其二，`cuexis_player_reports_missing_chart` 和 `cuexis_player_reports_missing_project`
在 hosted 的 debug 与 release 都失败：runner 上创建 OpenGL context 失败
（`actual_version=0.0`），而 C3 把内容加载挪到了窗口和 backend 之后，于是设备错误掩盖了
内容错误。修复：`run` 在创建 runtime、窗口和 backend **之前**先用
`openConfiguredPlaybackSource` 解析一次配置内容。这是有意的预检，事务仍会自己再解析一次
配置来源，因此「配置来源需要音频时钟时重读并以 CuexisAudio 再准备」的路径不变。

本机验证：`--chart <missing>` 与 `--project <missing>` 现在都只打印 `player.startup`、
`player.config` 和 `player.failure`，不再出现 `player.sdl` 或 `player.opengl`，退出码 1，
错误码分别是 `player.chart.open_failed` 和 `player.project.load_failed`。这正是 hosted
runner 需要的顺序。修复后 Debug 全量 CTest `732/732`，两个 GPU smoke 仍通过。
