# PD-5 读取回归的有界归因实验（R0-b）

状态：诊断报告。证据只在独立临时 worktree 中产生，变体不进主树、不登记、不产生 A/B 结论；不构成性能、内存或阶段接受，也不改变任何已接受判据。门 G2 未通过，读取候选不提名。

日期：2026-10-23

归属：Stage 7-PD / PD-5。执行[读取候选与分域内存观测实施方案](../../../../../../../stage_plans/active/stage-07/04-pd/pd-5/pd5-read-candidate-and-memory-domains-plan.md) §2.2 的 R0-b 有界归因实验，并按 §2.2 的门 G2 判定是否提名读取候选。上游为[静态指令归因（R0-a）](../r0-a/2026-10-23-read-regression-static-attribution.md)的灰区判定与[C2 结果](../../read-candidate/2026-10-21-c2-read-result-candidate.md)的 1.0214（未采用）。

结论摘要：边界批量物化（RB 的机制与其真实消费者采用方式）**不能**把读取回归压到 1.10 以内。5 个可执行、3 轮交错、18 次运行全部通过，有效性门成立（`V0/A` = 1.4140，相对存储的 1.3742 偏差 +2.90%，在 ±10% 内），候选上界直接取同机 `V1/A` = **1.3728，95% 区间 [1.3579, 1.3878]**：点估计、上界、乃至下界都高于 1.10，按 G2 记“上界不足”，进入 R3 未通过分支，R1（RB 实现）与 R2（A′ 对 RB 诊断）均不启动。归因上，批量只回收每帧 131.1 ns（N=64），占 F1 超出 A 的 1175.1 ns 的 11.2%；折成拟合量即边际 −1.92 ns/对象（目标 −12.32，完成 15.6%）与固定 −2.89 ns/次（目标 −6.01，完成 48.1%）。残余集中在逐对象提取块本身（组件检索 + 136 字节 DTO 重建 + 快照字段与矩阵写入），该块在 N=64 时占 V0 的 80.1%，且 F1 的该块是 A 的 1.58 倍。要够到 1.10，该块还须再降 24.7%；R0-b 的变体只做了“删除”而非“改写”，因此本报告只能断言边界批量化不可达，不能断言改写检索形态不可达。

## 1. 边界与不主张

R0-b 只回答一个问题：**在语义不变的前提下，把逐对象调用合并为窗口内批量物化，能把读取回归压到多少？** 它衡量的是候选的上界，不是候选本身，更不是正式测量。

不主张：正式性能接受、9 对登记、内存预算、ETW 覆盖、多线程/GPU 负载下的行为、跨机器可移植性；也不主张变体与插桩的绝对时间可用于验收（方案 §2.2 明确禁止）。

| 检查 | 结果 | 判定 |

## 6. 残余解释：到 1.10 的距离在哪里

以 V2 的“仅 id 与索引”为共同地板（N=64 时 795.3 ns），把每次 `extractFrame` 拆成地板与逐对象提取块：

| 项 | ns/帧 | 说明 |
| --- | --- | --- |
| V0 总成本 | 4003.3 | F1 原样 |
| V2 地板（仅 id 与索引） | 795.3 | 占 V0 的 19.9% |
| V0 提取块 | 3208.1 | 占 V0 的 80.1% |
| A 提取块 | 2033.0 | A 总成本 2828.3 减同一地板 |
| F1 提取块 / A 提取块 | 1.578 | 回归的可归因位置 |
| 批量回收（V0→V1） | 131.1 | 超额 1175.1 ns 的 11.2%，V0 的 3.3% |
| 防御检查（V2→V3） | 30.9 | V2 的 3.9%，V0 的 0.8%，约 0.48 ns/对象 |

要够到 1.10，N=64 时总成本须降到 3111.1 ns（比 V1 再少 761.1 ns，即 −19.7%）。扣除地板后，提取块的预算是 2315.8 ns，比现在的 3076.9 ns 低 24.7%，相当于 A 提取块的 1.139 倍。换句话说：**读取回归的量级与位置都不在窗口边界上**——那里只有一个窗口检查、一次调用和一次 `Result` 传递；它在每个对象的组件检索、136 字节 DTO 重建与快照字段/矩阵写入里，而 V1 把这些全部保留了下来。

V2/V3 是删除而非改写，所以这两个数只给出“该块的盘子有多大”，不给出“用另一种检索形态能省多少”。把它们当作可实现方案会重复 R0-a 的错误（见 §7）。

## 7. 与 R0-a 静态归因的差异

R0-a 在严格口径下把可移除项算成 118 / 147 条指令、13.18 ns/对象（投影 1.0824），并据此把候选判为灰区。R0-b 实测批量只拿到 1.92 ns/对象，静态口径高估约 6.9 倍。原因是该口径用“指令占比”近似“时间占比”：被批量真正拿掉的指令（窗口标志测试、`available()`、错误指针装配、`Result`/sret 与移动）处在无依赖、全部预测命中的短路径上，单条边际成本远低于均值；而每对象的 136 字节构造、字段与矩阵写入这些按规则被算作“必需”的部分，才是成本主体——实测与 R0-a 的“必需”划分一致，只是“可移除”部分的时间权重被高估了。

方向上的一个例外值得记录：批量对**固定项**的回收（−2.89 ns，目标的 48.1%）远好于对**边际项**（−1.92 ns/对象，目标的 15.6%）。R0-a 关于“调用与返回开销在固定项里”的判断成立，关于“每对象可移除量在 12 ns 以上”的判断不成立。

## 8. 协议偏差、局限与不可外推

1. V2/V3 不再写组件字段，`updated` 模式的 digest 不会变化，原断言 `REQUIRE(digest != prior)` 会失败；仅在 V2/V3 构建中用环境变量 `CUEXIS_R0B_VARIANT` 放宽该断言（A、V0p、V0、V1 保持原断言）。这是探针的布尔守卫，不触碰计时路径。
2. A 锚复用 2026-10-21 的冻结可执行，未在同机同次重建 A 树；因此用 `V0/A` 的有效性门（偏差 +2.90%）与其 1.3728/1.4140 的比值对齐来约束，而不是假设 A 与存储测量完全同源。
3. V0p 与 V0 是同一份源码的两次构建，差 1.0%；这是构建级噪声的实测下限，报告据此不给 1.37 以下的第二位小数赋意义。
4. 每块 0.45–0.52 s，满足协议；每变体 3 轮 × 3 块，全部交错。全部为相对值，绝对时间不作验收。
5. 单机、单次会话、单 content、单 viewport、无 GPU 负载、无并发消费者；`updated` 模式同批采到但只作交叉核对（`V0/A` = 1.0322 [1.0190, 1.0455]，说明回归只出现在 read 路径）。
6. 头文件宏变更对 ninja 不可见（MSVC `/showIncludes` 本地化导致依赖未跟踪），每次变体构建都显式删除变体翻译单元的 `.obj` 并设 `VSLANG=1033`；构建脚本与命令已入证据包。
