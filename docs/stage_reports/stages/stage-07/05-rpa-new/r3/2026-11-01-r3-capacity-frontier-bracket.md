## 为什么值得单独测一次

冻结的 2026-10-29 容量判定把 1800（仅渲染）与 1300（静态提帧）登记为“已确认的最高持续通过点”，
并明确留下三处空白：1900 仅渲染失败、1400/1500 静态失败、1800 静态**从未测过**。之后的
[40K 240 FPS 与预算判定](2026-10-31-r3-40k-240fps-and-budget-verdict.md)在同一份源码的**另一次会话**
（探针二进制 `91ed0d303c09ef92e6abab9e30b63c87da77322d1dc7132c6b45204c220578b9`）上记录到 1800 仅渲染
p99 中位 3.2105 ms、1800 静态 3.7251 ms、1300 静态 3.0710 ms，三点都在预算内：也就是说冻结的前缘现在
**严格低于**真实前缘，而那次判定只能给出“转移值”（把成本比折算成可承受实体数），给不出交叉点。

要把前缘变成区间，必须在一次会话里、一个二进制上把跨越点本身测出来——这就是本阶梯要做的事。它同时
要回答一个此前没有被量化的问题：同一份源码在不同会话上究竟差多少。本阶梯的 1800 锚点就是那把尺子：
预注册规定它与 `91ed0d30…` 的 3.2105 / 3.7251 ms 相差不得超过 ±10%，否则整条阶梯的同源前提不成立，
结论必须降级为“每个点属于它自己的构建与会话”。判定结果见“结果”一节的漂移条目。

预热登记的模型有两个，且互斥：

- `transfer_through_origin`：`p99(N) = k·N`，某点的成本比按 `1/r` 转移可承受实体数。这个模型产出
  仅渲染 2295、静态 1782；其中静态的 1782 已被“1800 静态现在通过”直接否证，所以该模型至少对静态
  是错的。
- `affine_p99_fit`：`p99(N) = a + b·N`，允许每帧固定成本 `a`。用同一会话（`91ed0d30…`）上的两个实测
  持续点（1300 与 1800）拟合，得到仅渲染 `0.897 + 0.001285·N`（交叉 2544）、静态 `1.371 + 0.001308·N`
  （交叉 2137）。

这两个模型都只是对那次会话数字的算术，不是测量；绝对值继承那次会话，所以只有“形状”与“交叉点相对
1800 的位置”能被本阶梯检验。阶梯的目的就是让实测来证伪它们，而不是让它们继续以“预测”身份被引用。

## 方法

- 每个实体数同时测 `render-only` 与 `static` 两种模式，各 3 个**新进程**、每进程 2 s 预热 + 20 s 测量，
  1920×1080、真实 OpenGL 可见窗口、显示器 240 Hz。
- 两种模式的每帧工作量不同，逐帧日志因此能把成本指认到相位：`render-only` 每帧只做一次
  `backend.submit` 加一次 `backend.present`，复用同一份快照，不更新、不提帧；`static` 每帧先做
  `session.update(+1/240 s)` 与 `session.extractFrame(viewport)`，再 `submit` / `present`。模式由环境变量
  `CUEXIS_GPU_MODE` 在 `tests/player/gpu_throughput_probe.cpp` 第 164 行读取并断言，第 268–274 行是
  `if (mode != "render-only")` 的守卫；`submit_us` 与 `present_us` 分别是两次调用的耗时，
  `cycle_us` 是“上次呈现→本次呈现”。两种模式提交的都是真实可见窗口的 OpenGL 帧，差别只在 CPU 侧
  每帧要不要重建快照。
- GPU 运行使用保存的 CPU 亲和掩码 65535；不与其他构建、测量并发。
- 每个点单独写 `registration.json`（head、worktree、探针源码哈希、运行器哈希、二进制哈希、计划），
  并在开跑前拒绝已存在的运行目录、在二进制哈希变化时中止整条阶梯。
- 中位数取“进程内中位数的中位数”，重复性用 `(max-min)/median` 的百分比，不重新采样、不挑选进程。
- 阶梯跑完后再做判定，判定脚本 `summarize_frontier.py` 只读预注册与实测，不改判据。
- 越过前缘之后的“形状”由 `analyze_stall_shape.py` 从同一批逐帧日志里读出（预算 4.166667 ms 与
  慢帧阈值 6 ms 都写在脚本里，不随结果调整）；慢帧的相位归因与 GPU 时间戳来自另一个运行器
  `run_stall_diagnosis.py` 的独立诊断。两者都归档在证据包的 `diagnosis/` 下，与阶梯的逐点记录分开。
- 预注册写于 `466ff76`，阶梯实际跑在 `8e275a59d6ff18d88a8193643254dc0d3fb9c034`：其间四个提交只改测试仪器、矩阵运行器、证据与文档，
  产品源码唯一的字节变化是 `engine/json_support/src/bounded_parse.cpp` 里一处注释换行（`9c392af`，
  不改变任何代码）。所以“同一份产品源码”可核，而**不是**“同一个提交”——每个点的 `registration.json`
  里记的探针源码哈希与 `binary_sha256` 才是被测量的那份字节。
- 前三次尝试都作废，判定只读 `frontier-bracket-4`：`frontier-bracket-1` 在六个测试仪器文件尚未提交
  时被“工作树必须干净”直接拒绝（一个进程都没起，只留下一个空目录）；`frontier-bracket-2` 跑到第 2
  点被运行器把“跑满 20 s 但低于登记速率”误判为“进程无效”而按停止规则中止，原因已修（截断仍算无效，
  跑满时长但低于速率算**预算失败**，与运行器自己登记的停止规则一致）；`frontier-bracket-3` 又跑到
  第 2 点被同一个干净树守卫拒绝，这次是因为本报告的作者在阶梯进行中修改了一份受版本控制的文档——
  守卫对**每个进程**都重新检查，这项设计是对的，错的是在阶梯期间动受控文件。第四次尝试
  （`frontier-bracket-4`）从干净树起跑，全程不碰任何受控文件。
- 前两次作废的尝试各自跑完了 1800 这个点，它们的文件整组归档在 `attempts/` 下，且**只在“同一个点
  三次独立观测”的意义上被引用**（见“边界”的重复性一条）；其余点（`frontier-bracket-2` 的 2400、
  `frontier-bracket-3` 的 2400 未开始）不参与任何判定。清单的 `superseded_attempts` 逐条记下每次的
  状态、作废原因与归档文件列表，`excluded` 为空是因为这次没有任何文件被丢掉。

**附加诊断：多出来的时间在 CPU 的 `submit` 里，GPU 几乎没有变**

上面只能把时间指认到 `backend.submit` 这一次调用，指不到调用内部。探针自带一个可选仪器正好能切开这
一点：`CUEXIS_GPU_TIMER` 打开后，它在 `backend.submit` 的前后各写一个 GL 时间戳
（`tests/player/gpu_throughput_probe.cpp` 第 275–284 行），于是同一帧同时有“CPU 在这段里花了多久”和
“GPU 自己的时间戳间隔有多长”。为了不污染阶梯，这个诊断用的是**另一个**运行器
`run_stall_diagnosis.py`（sha256 `30a34162c5ded51c06fbe01796349966f215e37554a2150f093dad5680000a01`），
它与阶梯运行器 `run_40k_refresh.py`（sha256 `16a3f57a…`）只差四处：把 `CUEXIS_GPU_TIMER` 置为 `1`、
把身份期望改成 `timer: true`、多一条“样本必须带 `gpu_interval_us`”的有效性检查、在登记里记下
`timer: true` 与仅诊断的 scope。探针二进制与 head 与阶梯完全相同。三个点：2300（3 进程 × 20 s）、
2800（3 进程 × 20 s）、40000（2 进程 × 120 帧）。

- 2300 静态的慢帧占 1.13% / 9.15% / 2.18%，这些帧的 CPU `submit` 比同进程快帧多
  3588.7 / 3180.3 / 3580.4 µs；同一批帧的 GPU 时间戳间隔只从 404.5 / 465.9 / 407.6 µs 变成
  436.7 / 496.6 / 436.2 µs，即 +28.6～+32.3 µs（约 +7%）。
- 2800 仅渲染同样是这个形状：`submit` 多 3404.6 / 3249.9 / 3139.1 µs，GPU 间隔 475 / 487 / 489 µs
  对 506 / 516 / 506 µs。2800 静态：`submit` 多 2279.6 / 2558.3 / 2508.1 µs，GPU 间隔
  572 / 505 / 511 µs 对 584 / 514 / 524 µs。
- 也就是说：多出来的约 2.3–3.6 ms 是 **CPU 停在 `submit` 调用里**，不是 GPU 在做更多工作；两者差两个
  数量级。同时，越过前缘的点上 GPU 远没有饱和：2300–2800 的 GPU 间隔中位数是 392–573 µs，而同一批
  帧的 `cycle` 是 3.0–4.9 ms，GPU 侧只占一帧的约 10–15%。
- 40K 的方向相反，但只能当上界读：40K 静态 `cycle` 中位数 56.5 / 56.7 ms（`update` 5.0、`extract` 7.0、
  `submit` 43.0 ms），同帧 GPU 间隔中位数 16.3 / 16.3 ms（p99 18.9–19.5 ms）；仅渲染是 44.3 / 45.6 ms
  对 16.3 / 17.6 ms。40K 的 40000 条绘制命令由 CPU 在 43 ms 内逐条发出，GPU 的两个时间戳之间必然夹着
  发令间隙，所以这个数**只能**证明“40K 的 GPU 侧并不便宜”，不能当作 GPU 侧的下界，也不能用来推断
  240 FPS 是否可行。
- 仪器自身开销与一致性：计时器打开后 `present_us` 从 31–119 µs 升到 307–380 µs（每帧多一次查询与
  排空），但 2800 仅渲染的 p99 是 7312.5 / 7327.7 / 7297.6 µs（阶梯）对 7350 / 7331.2 / 7359.6 µs
  （诊断），差 0.4–0.8%：停顿的幅度与频率没有被这个仪器改变。

这条诊断能确定的只有一句话：在越过前缘的点上，p99 由一段**发生在 `backend.submit` 调用内部的 CPU
停顿**决定，单次约 3.4 ms、周期约 5 帧，与实体数几乎无关。它为什么发生、为什么是 5 帧，本报告没有
回答——那需要把 `submit` 内部再分段，或者对提交路径做分配与上传计数，两者都不是本次阶梯的内容。

> **2026-11-01 追补（后见之明，原文不动）**：上面这句话里的三个估计后来被
> `2026-11-01-r3-submit-stall-wait-attribution.md` 的直接测量改写了，记录在此以免有人把它当结论引用：
> 那段停顿是**每帧一次**的匿名 Event 等待（A 组 2800 静态 1.25 次/帧、B 组 1800 静态 1.00 次/帧），
> 不是"每 5 帧一次"；它的**时长随负载增长**（每实体 +1.691 µs，中位片段 2800 静态 2.28 ms、1800 静态
> 0.94 ms），不是"与实体数几乎无关的固定值"——本报告自己记的 2800 静态 `submit` 多出 2.28 / 2.56 /
> 2.51 ms 也已经是这段时间，而不是一个跨点不变的 3.4 ms；而在 40 000 实体处它**完全消失**（40 个
> 样本 0 次命中），那里的代价换成了 40 000 次绘制调用的逐次提交成本（1.374 µs/实体）。"为什么这么长"
> 有一半答案（驱动在等，等的是 `nvoglv64+0xa1cd8a` 发起的同步），"为什么是 5 帧"当时的问题前提
> 本身不成立。

## 边界

- 这是**诊断区间**，不是容量接受。冻结的 1800（仅渲染）/ 1300（静态）继续是唯一登记过的容量值；
  本报告不把任何新通过点升级为容量值。要把容量值提高，需要按冻结组同样的登记方式（重复轮次与
  顺序控制）另立一次运行，不能引用本阶梯的通过点。
- 阶梯只覆盖 1080p、`CUEXIS_ENABLE_CHART_V5_CANDIDATE` 关闭时的发布探针与 40K v3 夹具；720P 与
  其他夹具的交叉点不同（HEAD 上 720P 与 1080p 的 40K p99 只差 1.4–7.0%，但这不构成对任意规模的
  分辨率不敏感结论）。
- 单点 3 进程 20 s 只够支撑“该点在预算内/外”的判定，不足以支撑亚百分比差异；因此本报告不给点与点
  之间的成本斜率置信区间，只给区间两端。
- 同一探针二进制、同一协议、同一台机器上，1800 这个点被独立测过三次；三次的中位数并不相同：
  - `仅渲染`：frontier-bracket-2、frontier-bracket-3、frontier-bracket-4 依次为 2.6697 / 2.7179 / 2.7479 ms，相对离散 (max−min)/median = **2.9%**。
  - `静态提帧`：frontier-bracket-2、frontier-bracket-3、frontier-bracket-4 依次为 3.1170 / 3.5755 / 3.5700 ms，相对离散 (max−min)/median = **12.8%**。
  这不是“取哪一次”的问题，而是该点本身的会话间离散度。凡是点间步长对应的 p99 变化小于该离散度的
  模式，表里的通过与失败仍按实测如实记录，但不能用来推断更细的交叉位置；反过来，离散度远小于步长
  的模式，其相邻点顺序才可用。
- 上一条也是 ±10% 漂移带为什么会失败的物理原因之一：它把两次会话的绝对水平当作可比的，而实测显示
  即便同一个二进制也不能这样比。本轮没有把漂移分解为“构建差异／GPU 状态／环境负载”，也不宣称
  HEAD 变快或变慢。
- 每点通过判据允许个别帧超出预算（运行器只看 p99 与 1 秒窗口内帧数），与冻结组口径一致；`over_budget`
  计数照原样留在逐帧日志里。
- “越过前缘的形状”与“附加诊断”两节是阶梯**之外**的追加分析：前者只重读阶梯自己的日志（没有新测量），
  后者是另一个运行器、开着 GL 时间戳的独立诊断。两者的数字都不进入任何阶梯点的通过与失败判定，也不
  改变区间端点；引用时必须带着“仅诊断”的标签。
- 停顿的**原因**未定。本报告能确定的只有“额外时间在 `backend.submit` 调用内部、单次约 3.4 ms、周期约
  5 帧、与实体数弱相关”。把它写成“GPU 慢”“驱动限制”或“某段代码的缺陷”都是超出证据的说法。
- 40K 那个诊断点是 **2 进程 × 120 帧**，与阶梯的 3 进程 × 20 s 不是同一口径，只用于读 GPU 时间戳间隔的
  上界；它不修正冻结的 40K 判定，也不构成对 40K 240 FPS 可行性的任何判断。

## 复现

```powershell
$probe = 'out/build/rpa-candidate-release/bin/cuexis_execution_device_probe.exe'   # 哈希见上方绑定
$refresh = 'out/verification-20261031/r3-40k-throughput-refresh-v1'
python -B $refresh/run_frontier_bracket.py `
  --exe $probe `
  --work $refresh/frontier-bracket-5 `
  --processes 3 --seconds 20
python -B $refresh/summarize_frontier.py `
  --summary $refresh/frontier-bracket-summary.json `
  --out $refresh/frontier-bracket-verdict.json
# 越过前缘的形状：只重读已录日志，不产生新测量
python -B $refresh/analyze_stall_shape.py `
  --run $refresh/frontier-bracket-4/entities-2300 --out $refresh/stall-shapes/ladder-2300.json
# 附加诊断：另一个运行器，开 GL 时间戳；输出目录必须不存在
python -B $refresh/run_stall_diagnosis.py --exe $probe `
  --out $refresh/stall-diagnosis-2/entities-2300 --entities 2300 --seconds 20 --processes 3
```

`--work` 必须是一个**不存在**的目录（运行器拒绝覆盖），并且从干净工作树起跑：它对每个进程都重新
检查工作树，阶梯进行中改任何受控文件都会让整条阶梯作废。`summarize_frontier.py` 的默认输入就是
`$refresh/frontier-bracket-summary.json`，这里写全是为了让读者看清判定与数据各在哪一个文件里。

复现要求同一份源码、同一构建配置与同一个 CPU 集合，并与本次 `registration.json` 的
`binary_sha256` 对照；哈希不同即属另一次构建，不能与本节数字并列。
