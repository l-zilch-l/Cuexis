## 2. 读取路径：假设、实验、证伪

**先定位量级。** 用同一个探针在 50 / 200 / 800 / 1800 实体上比较两臂，差距随实体数线性增长：

| 实体数 | A（pre-PD） | B（HEAD） | 每帧差 | 每实体差 |
| ---: | ---: | ---: | ---: | ---: |
| 50 | 4 641.8 ms | 5 250.7 ms | 0.30 µs/次 | 6.1 ns |
| 200 | 16 891.8 | 19 128.2 | 1.12 µs/次 | 5.6 ns |
| 800 | 68 462.7 | 78 666.6 | 5.10 µs/次 | 6.4 ns |
| 1800 | 175 878.4 | 206 681.6 | 15.4 µs/次 | 8.6 ns |

所以它是**逐对象**成本，不是每次调用的固定开销。

**假设。** HEAD 的逐对象读取走 `PresentationRead::readSnapshotObject`，每次调用都要重新验证读窗口
（`available()`：shared_ptr 解引用、owner 线程比较、serial 比较），并返回 144 字节的
`Result<ObjectVisualRead>`（见 `presentation_materializer.hpp` 的静态断言）。pre-PD 的循环全部内联在
`playback_session.cpp` 里，两者都不存在。

**实验。** 把这条路径改成"每帧验证一次 + 逐对象就地填充"：新增
`PresentationRead::objectCount()` 与 `readSnapshotObjectInto(index, out)`，物化器在循环外验证一次、
循环内只做索引读取，不再构造 per-object `Result`，并把 `snapshotReadScratchBytes` 从 256 改为 136。
在 `rpa-candidate-release` 增量重建后与保存的原二进制作三对交替比较（1800 实体、2000 次读取/块）：

| 对 | 原二进制 | 补丁二进制 | 比值 |
| ---: | ---: | ---: | ---: |
| 1 | 207 004.6 µs | 207 969.7 | 1.0047 |
| 2 | 239 582.0 | 247 021.7 | 1.0311 |
| 3 | 202 787.5 | 206 219.2 | 1.0169 |

几何平均 **1.0175**——补丁没有变快，略有变慢。假设被证伪，改动已回滚，工作树恢复为 `6256af8` 的
内容；保存的原二进制仍是
`out/verification-20261101/r3-repair-v1/bin/baseline-B.exe`（sha256 `5d5829a6…`）。

**这一条同时给出了一个有用的对照。** 同一次运行里，"update+extract" 块的耗时是 A 794.1 ms、B
350.1 ms——B **快 2.27 倍**；而纯 extract 块 B 慢 16 %。也就是说 R3/PD 的收益在 update 侧，
回归只在 extract 侧，且不能用"运行时状态整体变慢"解释。

**下一步（未做）**：逐对象的 6–8 ns 需要带符号的采样归因（仓库里已有 RIP 采样器
`out/verification-20261101/r3-stall-mechanism-v1/sample_rip.py`，但对 100 µs 级调用需要配套的符号
解析与低扰动采样设计），或对 `ObjectEntityMap` 间接层做一次针对性的布局实验。本轮不猜第三个补丁。

## 3. 首次 Pause：已经拆到具体位置

控制组的第一次 pause 读数可拆成两段（日志里有 `start_us` / `confirmed_us` / `first_present_us`）：

| 段 | 耗时 |
| --- | ---: |
| `host->pause(clock)` 本身（start → confirmed） | 258 µs |
| 随后的冻结帧 `sample` + `present`（confirmed → first_present） | **178 445 µs** |
| 之后的 pause（合计，中位） | 0.4–0.9 ms |

所以超界的 179 ms 全部在**第一次冻结绘制**里，控制命令本身只要 258 µs。

**为什么本轮不修。** 最自然的修法是在 load 末尾预热一张冻结帧，但那会多一次 present：
`first_frame_presented` 正是初次 load 门的边界，提前 present 会把那条读数改写成预热帧；
player 的 smoke 序列与 golden 摘要也可能因此移动。没有先做归因就动这条路径，风险大于收益。
**下一步（未做）**：在控制绘制上挂 GPU timer（探针已有 `CUEXIS_PD5_GPU_TIMER` 通道），先确认
178 ms 落在 submit 的 CPU 段、GPU 段还是首次 present，再决定预热放在 backend 创建、首次 submit 还是
`load` 末尾。
