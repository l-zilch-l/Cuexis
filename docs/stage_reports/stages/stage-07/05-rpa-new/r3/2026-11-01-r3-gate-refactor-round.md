## 1. Pause：用五个判别实验封死，结论是没有代码可修

问题陈述：首次 pause 超界 175–190 ms，判据 50 ms。先确认钱花在哪（`present` 里，GPU 只有 1 µs），
再逐个排除可能的机制。

| 判别 | 读数 | 排除了什么 |
| --- | --- | --- |
| 该帧 GPU timer | 1.024 µs | 不是 GPU 工作 |
| 拆分绘制 | pause() 258 µs / sample 49 µs / present 175 836 µs | 锁定在 `SwapWindow` |
| 隐藏 vs 可见窗口 | 178.7 ms vs 182.8 ms | 不是窗口可见性 |
| vsync 开 vs 关 | 176.4 ms vs 177.6 ms | 不是 vblank 等待 |
| 首帧前泵 32 ms 事件 | 182.9 ms vs 178.1 ms | 不是窗口就绪 |
| 首帧与次帧之间加延迟 | 20 ms→155 ms，50 ms→128 ms，**200 ms→0.25 ms**，400 ms→0.28 ms | 是"合成器追赶"，纯时间可溶解 |
| 先画 1 帧 live 再 pause | 停顿转移到那帧 live（174.9 ms），首次冻结 present 0.71 ms | 与冻结无关，是本进程第二次 present |

**结论**：这是本机环境下"窗口/上下文创建后的第二次 swap"的固有停顿。代码只能把它**推迟**（把首帧与
次帧拉开 ≥200 ms），不能消除——而拉开 200 ms 对用户可见的启动代价与现在的 175 ms 停顿等价。

所以 Pause 这一项**没有可保留的代码改动**。要让门反映产品语义，只有两条路，都需要 owner 决定：

1. **另登记一个"预热后"的控制负载**：先 present N 帧（间隔 ≥200 ms）再执行控制，同时保留冷启动读数；
2. 接受"冷启动第二次 present"是环境属性，在报告里把 Pause 门的读数标注为启动期一次性停顿。

4. 若成立，还要证明成本没有偷偷转移给 update（同一批里同时报 update 块）。


## 5. 方向 1 实做：紧凑展示行（已回滚）

设计：`publishPresentation` 每次发布变更后刷新一条紧凑的 `PresentationRow` 数组（矩阵值 + 可见性 +
材质 + 不透明度 + tint），`extract` 扫这条数组而不是逐对象碰 registry；行数组缺失或长度不符时逐对象回退，
正确性不押在优化上。

五个交替对，1800 实体、每块 2000 次操作，每帧成本：

| 模式 | 基线 | 紧凑行 | 变化 |
| --- | ---: | ---: | ---: |
| extract（纯读块） | 103.49 µs | 84.78 µs | **−18.1 %** |
| update（updated 减 read） | 76.91 µs | 114.68 µs | **+49.0 %** |
| 整帧（update+extract） | 180.40 µs | 199.46 µs | **+10.5 %** |

读取块比值 0.7968 看起来很好，但它是**成本转移**：行数组是数据从 pool 到快照之间多出来的一趟内存遍历，
extract 变快的 18 µs 在 update 里以 38 µs 还了回去。按"整帧不能变差"的标准，这个方向**回滚**。

剩下的方向只有一个真的：降低**源**的读取成本，而不是加中间层。可选的两条都在数据模型层面——
把 transform 与 appearance 合并成一次读取，或让 extract 直接消费 world 已有的 `transformCache_`
（它已经是按实体排序的连续数组，但目前每对象仍要一次查找）。两者都会改变组件/读取的内部结构，
需要先做一次受控实验，且属于需要 owner 知情的改动。


## 6. 方向 2：把两次组件读取拆开（E4/E5）

紧凑行失败之后，先问一个更基本的问题：那 17 % 到底是 transform 贵还是 appearance 贵？两个消融，各三轮
交替，同一基线二进制：

| 变体 | extract | update+extract | 隐含 update | 读取比 |
| --- | ---: | ---: | ---: | ---: |
| 基线 | 103.21 µs | 187.56 µs | 84.35 µs | — |
| E4（不读 transform） | 96.46 | 167.72 | 71.26 | **0.9346** |
| E5（不读 appearance） | 96.19 | 172.72 | 76.53 | **0.9320** |

两个组件读取各占约 6.5 % 与 6.8 %，基本等分、可以相加（与之前"完全不读 registry"的 0.8247 一致）。
**没有单一热点可以优化**：剩下的 13 % 只能靠改变数据放在哪里。

单独去掉任何一侧都只能把 1.1732 降到约 1.096，落在 1.10 边缘以内、但不足以让区间上界也过线。所以下一步
必须是"一次读取拿到两样东西"，而不是再调循环写法。

## 7. 下一个方向（未执行，需先验证前置）

**把 world 矩阵与 appearance 合并成一个展示组件，并按池顺序顺序读。**

- 上限有实测支撑：两次读取合计是当前读取块的 0.8247，是唯一量级够把 1.1732 拉回 1.10 以内的方向。
- 前置条件：**池的迭代顺序必须等于快照布局顺序**。快照对象顺序是公开合同（digest 绑定其上），不能重排；
  如果池顺序与布局顺序不一致，这个方案就要额外维护一张映射，收益会被吃掉一半。
- 代价：动 world 组件以及所有写它的系统（行为、动画、覆盖、回放），属于数据模型改动，不是局部优化。

在动它之前应先做一个只读检查：把 `registry.view<Transform>()` 的实体顺序与 `layout.entities[i]` 的实体
顺序逐项比较，确认两者一致（这一条本轮没做）。


## 8. 前置检查结果：池顺序不等于对象顺序（该方向关闭）

"合并组件 + 按池顺序顺序读"依赖一个前提：`registry.view<WorldTransformComponent>()` 的迭代顺序与对象表
（也就是快照布局）一致。用一次临时诊断直接比对同一偏移上的实体：

```
DIAG_POOL_ORDER compared=1800 mismatches=1799
```

1800 个对象里 1799 个不一致。所以这个方案要按对象顺序输出就得引入一张映射或置换，那会吃掉"少读一个
组件"挣来的 6.5–6.8 %。**该方向关闭**，诊断已回滚。

## 9. 读取相对门：本轮能得出的结论

在不动公开合同的前提下，本地可及的方向已经全部测过：

| 方向 | 结果 |
| --- | --- |
| 逐对象 `Result` + 重复窗口验证 | 1.0175，无效 |
| 调用边界/内联（运行时内批量读） | 1.0392，无效 |
| 紧凑展示行（发布时刷新） | 读取 −18.1 %，但整帧 +10.5 %，否决 |
| 只读 transform / 只读 appearance | 0.9346 / 0.9320，各占约 6.5 % |
| 按池顺序顺序读 | 前提不成立（1799/1800 顺序不一致） |

结论：这 17 % 是两次组件读取本身，任何"绕开它们"的改动要么无效、要么把成本搬进 update。要真正闭合，
只有两条路，都需要 owner 决定：

1. **改快照对象顺序合同**，让布局可以按池顺序排——这会改动公开顺序语义并让所有既有 digest/golden 失效；
2. **把两个组件合并成一个**，每帧只付一次稀疏查找与一条密集流——大约只有所需余量的一半，而代价是动所有
   写这两个组件的系统。


### 追加判别：窗口存在多久无关

在窗口创建之后、首帧 present 之前插入 100 / 200 / 400 ms 等待，首次 pause 仍是 173.8 / 175.7 / 176.6 ms。
所以停顿既不是"窗口可见性"、也不是"上下文创建后经过的时间"，只与**前两次 present 的间隔**有关。这一条把
可用的缓解手段收窄到"把首两次 present 拉开"，而那对用户可见代价与现状等价。
