## 1. Pause：用五个判别实验封死，结论是没有代码可修

问题陈述：首次 pause 超界 175–190 ms，判据 50 ms。先确认钱花在哪（`present` 里，GPU 只有 1 µs），
再逐个排除可能的机制。

| 判别 | 读数 | 排除了什么 |
| --- | --- | --- |
| 该帧 GPU timer | 1.024 µs | 不是 GPU 工作 |
| 拆分绘制 | pause() 258 µs / sample 49 µs / present 175 836 µs | 锁定在 `SwapWindow` |
| 隐藏 vs 可见窗口 | 178.7 ms vs 182.8 ms | 不是窗口可见性 |
| vsync 开 vs 关 | 176.4 ms vs 177.6 ms | 不是 vblank 等待 |
| 首帧前泵 32 ms 事件 | 182.9 ms vs 178.1 ms | 不是窗口就绪 |
| 首帧与次帧之间加延迟 | 20 ms→155 ms，50 ms→128 ms，**200 ms→0.25 ms**，400 ms→0.28 ms | 是"合成器追赶"，纯时间可溶解 |
| 先画 1 帧 live 再 pause | 停顿转移到那帧 live（174.9 ms），首次冻结 present 0.71 ms | 与冻结无关，是本进程第二次 present |

**结论**：这是本机环境下"窗口/上下文创建后的第二次 swap"的固有停顿。代码只能把它**推迟**（把首帧与
次帧拉开 ≥200 ms），不能消除——而拉开 200 ms 对用户可见的启动代价与现在的 175 ms 停顿等价。

所以 Pause 这一项**没有可保留的代码改动**。要让门反映产品语义，只有两条路，都需要 owner 决定：

1. **另登记一个"预热后"的控制负载**：先 present N 帧（间隔 ≥200 ms）再执行控制，同时保留冷启动读数；
2. 接受"冷启动第二次 present"是环境属性，在报告里把 Pause 门的读数标注为启动期一次性停顿。

## 2. 读取：四次消融把范围压到"每对象读 registry"

| # | 改了什么 | 比值 | 结论 |
| --- | --- | ---: | --- |
| E0 | 去掉逐对象 `Result<ObjectVisualRead>` 与重复窗口验证 | 1.0175 | 不是包装与校验 |
| E1 | 完全不读 registry（写入路径不变） | **0.8247** | 差距全部来自逐对象组件读取 |
| E2 | 只去掉 `registry.valid()` | 1.0068 | 不是有效性校验 |
| E3 | 运行时内部批量读（32 行/块） | 1.0392 | 不是调用边界或内联 |
| E4/E5 | 分别只读 transform / 只读 appearance | 未测 | 变体生成代码编译失败，本轮放弃而不是带病继续 |

E1 把 B 拉回 170–180 ms，正好是 pre-PD 臂的 175.9 ms。所以剩下的唯一方向是**数据布局**：让 extract 扫
一条每帧的紧凑展示行数组，而不是每对象去 registry 里抓 transform 与 appearance。这会动读取合同
（谁在什么时候填充这条数组、纯读场景如何保证新鲜），属于 owner 范围的改动。
