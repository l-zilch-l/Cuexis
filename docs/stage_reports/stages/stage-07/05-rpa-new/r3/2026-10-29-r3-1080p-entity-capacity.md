# 1080P 入镜实体容量与 240 FPS 边界

状态：有限本地容量诊断；不是 R3/R4 或生产接受

日期：2026-10-29

返回 [RPA 报告索引](../README.md)。当前接受状态只见
[CURRENT_STATUS](../../../../../CURRENT_STATUS.md)。前轮固定 40K 的 720P 测量见
[真实 GPU 吞吐核验](2026-10-29-r3-40k-physical-gpu-throughput.md)。

## 范围与判据

owner 要求在 1920×1080 下，从 10 个入镜实体增加至 40K，确定稳定帧率对应的实体容量。
根据前文目标，本轮以稳定 240 FPS 为判据，分别测试复用快照的 submit / present，以及
每帧静态 update / extractFrame / submit / present。没有引入优化或减少提交工作。

实际设备为 Ryzen 7 8845H / RTX 4060 Laptop，OpenGL 3.3、NVIDIA 616.64、AC 电源。
可见窗口实测 framebuffer 为 1920×1080，VSync 读回 0，不限帧、无音频。
普通分配器，PD metrics / RPA observation / lifetime observer OFF；实测使用默认 16 逻辑 CPU
集合、BelowNormal、执行节流关闭。每个进程至少 8 帧且至少 2 秒 warmup。

实体共享一个不透明无光照三角形 mesh / material，网格间距和 0.06 缩放保持不变。
修正小规模网格布局，始终让一个真实实体覆盖中心像素。逐进程核验全部实体中心在裁剪空间内，
逐帧核验 opaque 命令数，末帧材质像素须为 `[255,204,51,255]`；没有以背景或被裁掉的实体充数。

本轮新增完整 `cycle_us`：相邻两次 present 返回之间的周期，包含事件 pump 和循环开销；
`total_us` 仍保留 update 开始至 present 返回的较窄区间。稳定判据采用完整周期：

- 平均 wall FPS 至少 240，cycle p99 不超过 `1000000 / 240` µs，约 4.167 ms。
- 候选点三次独立短测均通过后，另登记三次、每次 20 秒的持续验证；每次均须通过上述预算，
  且每个完整 1 秒窗口至少完成 240 帧。
- 不将平均 FPS 达标或单次通过称为稳定。这里的稳定按 p99 定义，不承诺每一帧都无超时。

GPU timestamp 在本轮全部关闭，减少观察器对容量的影响；测量仍走真实 OpenGL 后端的正常
同步像素回读路径。不是纯 GPU shader busy 测试，也未计入完整 Player、Gameplay 或复杂材质负载。

## 登记与查找过程

证据根为 `out/verification-20261029/gpu-1080p-scale-v1/`，起点 `f90c2e1`。
只重新编译探针 translation unit，用原 MSVC Release 编译参数和只读已核验运行库独立链接，
原 720P 绑定构建、对象、库、二进制和原始证据均未覆盖。构建继续单任务、BelowNormal、affinity 3。

| 组 | 固定范围与用途 |
| --- | --- |
| `pilot` | 10 / 40000 × 两路径，各 8 测量帧，检查 1080P 实体及像素证明 |
| `duration-pilot` | 10 实体 × 两路径，各 1 秒，检查 duration、cycle 总和和秒窗口计数 |
| `coarse` | 16 个数量档位 × 两路径，共 32 新进程；10–5000 各 360 帧，7500 / 10000 各 240 帧，20000 / 40000 各 120 帧 |
| `fine` | render-only 1500 / 2000 / 2200 / 2400 / 2600 / 2800 / 3000；static 1000 / 1500 / 1600 / 1700 / 1800 / 1900 / 2000；每点三新进程、各 600 帧 |
| `gap` | 补测尚未测量的 render-only 1600 / 1700 / 1800 / 1900，每点三新进程、各 600 帧；将临界区间细化到 100 实体 |
| `sustain` | 最高全短测通过点 render-only 1900 / static 1500，每路径三次 20 秒 |
| `sustain-lower` | 上组未全通过，分别下调 100 至 render-only 1800 / static 1400；独立固定三次 20 秒，不替换原样本 |
| `sustain-static-1300` | 1400 static 两次 p99 超门，再登记未持续测试过的 1300 static，固定三次 20 秒；没有重跑 1400 或改判原组 |

各组在运行前固定计划；非法输出立即停止，不替换、不延长；预算失败作为有效容量点完整保留。
细化的是不同实体数量，不是重跑同一个失败窗口直到通过。短测与持续验证保持独立。

## 已确认的稳定容量

以本次 100 实体档位和预定判据，已确认的最高持续通过测试点如下。每条路径均为三次独立 20 秒，
不是把一次短测或平均 FPS 当作稳定结果，也不宣称这是所有环境下的精确数学极限。

| 路径 | 已确认实体数 | 三次平均 FPS 范围 | 三次 cycle p99 范围 | 60 个完整秒窗口中的最低 FPS |
| --- | --- | --- | --- | --- |
| 复用快照，仅 submit / present | **1800** | 341.27–353.06 | 3.680–4.094 ms | 319 |
| 每帧静态 update / extract / submit / present | **1300** | 370.95–407.86 | 3.154–3.779 ms | 344 |

相邻更高持续档位的完整结果保留：

| 路径 / 实体数 | 三次 cycle p99（ms） | 预算通过数 |
| --- | --- | --- |
| render-only / 1900 | 4.377 / 4.020 / 4.265 | 1 / 3 |
| static / 1500 | 4.202 / 3.609 / 4.032 | 2 / 3 |
| static / 1400 | 4.172 / 4.320 / 3.899 | 1 / 3 |

这些进程的平均 FPS 和每秒完成数仍都超过 240，失败点在 p99 尾部预算，不能删除慢点后重判。
1300 static 是一次额外下调：原计划的一次下调仍有两次超门，因此注册新的更低容量点，而非重跑
1400 直到通过；原登记与失败全部保留。更高数量有部分单次通过，故不把整体容量视为严格单调函数。
在已测范围内，保守稳定量与相邻失败档位分别是 1800 / 1900、1300 / 1400；中间数量未逐个枚举。

## 复核与交付

总计 **107 个有效进程、150171 个测量帧**，包括功能 pilot、粗扫、细测、补点及所有持续失败。
`audit_study.py` 对所有 log SHA-256、ordinal、帧数、分段合计、cycle 合计、p99、秒窗口、
实际 GPU / viewport / VSync / 像素证明和源 / 二进制绑定进行独立重算，见 `audit.json`。

`measurements.csv` 保存全部组和每进程结果；`coarse-table.md` 保存粗扫表；
`capacity-1080p.png` / `.svg` 为完整曲线图，`final-manifest.json` 封存源码、运行库、工具、
控制器、原始结果和图表。原 720P 的已封存 build / artifacts 哈希逐项复核仍相符，旧 probe 源副本保留。

本轮仅扩展显式设备探针的布局、viewport、duration、warmup 和计时输出，没有修改产品算法、
公共 API 或正式 profile。独立 MSVC 编译 / 链接、实体 / 材质像素验证、架构门、文档检查、
clang-format 和差异检查通过。未重跑全量矩阵、安装消费者或进行正式 R3/R4 接受。

上述容量只对应本机、本夹具和无锁帧测试，不包含完整 Player、音频、Gameplay 或全量动画；
真实内容须按其实际负载另测。原 4.167 ms p99、15% 正式重复性和其他阶段门限没有放宽。
