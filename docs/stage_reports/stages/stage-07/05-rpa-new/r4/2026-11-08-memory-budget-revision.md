# 内存上限修订提案 v2（待 owner 选择与签署）

状态：proposal；不含已接受数值，不改变现行 O1 接受记录

日期：2026-11-08

返回 [内存归因报告](2026-11-08-memory-attribution.md)与
[New RPA 报告索引](../README.md)。本文把 2026-11-08 归因批次的观测转成可审核的修订选项；
数值选择与接受仍属 owner。

## 1. 观测事实（不含推断）

| 尺度 | `state.current` 观测 | 现行 proposed 上限 | `command.session` 观测 | 现行上限 |
| --- | ---: | ---: | ---: | ---: |
| n64 | 427,015 B | 196,608 B（2048·N + 64 KiB） | 20,024,965 B | 21,854,208 B |
| n2048 | 13,249,941 B | 4,259,840 B | 27,049,016 B | 21,854,208 B |

分区是精确的（`exact=true`、`untagged=0`、域和等于全局），因此这些是**整域全部已链接 C++ 字节**，
不是下界。high 与 low 在 n64 上完全一致，说明不是采样噪声。

## 2. 双轴结构（2026-11-10 实测修正）

把 n64、n2048、n40000+4096 三次归因按两种归一化比较（判定标准：三次的每单位值极差 ≤10%），
域并不都随实体数增长：

| 域 | 随实体 | 随内容行 | 判定 |
| --- | ---: | ---: | --- |
| `state.world` | 3,168 → 892 → **828 B/实体** | 8,087（40K 行） | 实体轴 |
| `state.candidate` | 533 → 516 → **516 B/实体** | 5,039（40K 行） | 实体轴 |
| `delivery.payload` | 376 → 368 → **368 B/实体** | 3,594 | 实体轴 |
| `state.current` | 661（被摊薄） | 6,672 → 6,470 → **6,456 B/行** | 内容行轴 |
| `content.decoded` | 979（被摊薄） | 9,596 → 9,632 → **9,563 B/行** | 内容行轴 |
| `codec.buffers` | 232（被摊薄） | 2,297 → 2,261 → **2,262 B/行** | 内容行轴 |
| `owning.results` | 346（被摊薄） | 3,616 → 3,380 → **3,382 B/行** | 内容行轴 |
| `steps` / `journal` | 三次完全相同（7,529,781 / 2,458,821） | — | 固定，不缩放 |

含 40K 的第三次运行是唯一能把两条轴分开的样本：`state.current` 在 40K 实体下每实体只有 661 B，
但每内容行仍是 6,456 B，与 n64/n2048 一致。因此上限必须同时声明两个计数，单轴系数会同时低估
行缩放域、高估实体缩放域。

## 3. 为什么不能直接把观测值当系数

固定部分必须先扣掉，否则小 N 样本会把固定开销摊成“每实体系数”。`command.session` 是明确的例子：
逐分配追踪给出固定 19,766,750 B（128 个命令槽 5,077,031 B + 65,536 条保留前进记录 14,680,103 B
+ 9,616 B）与每实体 3,524 B（执行内核状态的七个连续数组），两者相加对 40K 的复现误差小于 0.1%。
只用两点拟合会得到 3,525 B/实体与高约 66 KB 的截距——数值可用，但解释是错的。

## 4. 需要 owner 签署的内容

1. **归属修正（推荐先决定）**：本批已在代码上把采样/前进期间物化的执行内核状态改记到
   `execution.retained`（见 §6），同一运行 21 个域全部在声明内。是否接受这份归属修正属 owner 签署范围。
2. **若修正归属**：`command.session` 维持 21,854,208 B 不变即可（实测固定 19.77 MB），只需确认
   65,536 条保留前进记录的 14,680,103 B 确实属于命令信封。
3. **若不做归属修正**：把 `command.session` 的声明改成“固定 19.77 MB + 3,524 B/实体”，
   根序列即变为解析值而非拟合值。
4. **双轴声明**：是否把 profile 的上限改成 `f(实体数, 内容行数)`（§2/§3），并相应声明 P8 的两个计数。
5. **落地方式**：把修订写回 `budget-proposal.v1.json` 的 `status`，或另出一份 `v2` 并把
   `2026-11-05-o1-budget-acceptance.json` 的引用改到 v2（两者都需新的接受记录）。

在签署前，现行 O1 接受记录与 `budget-proposal.v1.json` 保持不变；归因结果照原样保留，
不因提案修订而改写。

## 5. 2026-11-10 的 40K 实体数据（补充）

在 `2c4e1274` 上以 40,000 实体 + 4,096 内容行跑通后（见
[P8 报告](2026-11-10-p8-40k-entity-memory.md)），`command.session` 的观测是
160,834,198 B，是 proposed 上限 21,854,208 B 的 7.36×；`state.world`（33.1 MB / 163.9 MB）与
`state.current`（26.4 MB / 82.0 MB）都在声明内。

`command.session` 的超出已在 2026-11-10 用逐分配追踪解构（见
[P8 报告 §4](2026-11-10-p8-40k-entity-memory.md)）：固定 19,766,750 B + 每实体 3,524 B 的执行内核数组。
早先把它归因为“交付缓冲按 `frameByteBound` 分配”是错的——`FrameStorage` 只记账不分配，
`frameByteBound` 从未作为缓冲大小使用。

## 6. 归属问题（已定位并修正）

`command.session` 的 160.8 MB 里约 141 MB 是采样/前进期间物化的执行内核状态。它被记到“命令信封”名下，
是因为 `session_worker_dispatch.cpp` 的 `dispatch()` 用**一个**命令级作用域包住所有命令。

定位方式是检查点二分 + 逐分支验证：`after-seek` 时该域 19.8 MB，`after-sample` 时 145.7 MB；给
`SessionUpdatePresentation` 与 `SessionSeek` 各加一个 `ExecutionDomainScope{domainAdvance}` 后，
两者分别迁出 125,951,111 B 与 15,129,424 B。修正后同一运行（总字节不变，仍 365,084,102 B）：

| 域 | 修正前 | 修正后 | 声明上限 | 修正后倍率 |
| --- | ---: | ---: | ---: | ---: |
| `command.session` | 160,834,198 B | 19,762,486 B | 21,854,208 B | 0.90，在声明内 |
| `execution.retained` | 8,823 B | 141,080,535 B | 1,327,497,216 B | 0.11，在声明内 |

`over_declared` 从 `["command.session"]` 变为空。字节没有被移动或减少，只是记到了它所属的域。

因此待签内容从“给命令信封加 k·N”变成“是否接受这份归属修正”。若不接受，再回到按 3,524 B/实体
给 `command.session` 加项；两种选择都要求同样的双轴声明（§2/§3）。

## 7. 边界

- 本文不改变任何已测字节、不重跑样本、不把观测写成上限。
- GPU/驱动、prepare 峰值、直接 malloc/SDL/OS 堆仍未测量；本修订只涉及已归因的两个域。
