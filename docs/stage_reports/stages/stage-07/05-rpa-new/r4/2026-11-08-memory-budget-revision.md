## 1. 观测事实（不含推断）

| 尺度 | `state.current` 观测 | 现行 proposed 上限 | `command.session` 观测 | 现行上限 |
| --- | ---: | ---: | ---: | ---: |
| n64 | 427,015 B | 196,608 B（2048·N + 64 KiB） | 20,024,965 B | 21,854,208 B |
| n2048 | 13,249,941 B | 4,259,840 B | 27,049,016 B | 21,854,208 B |

分区是精确的（`exact=true`、`untagged=0`、域和等于全局），因此这些是**整域全部已链接 C++ 字节**，
不是下界。high 与 low 在 n64 上完全一致，说明不是采样噪声。

## 2. 为什么不能直接把观测值当系数

计划 §3.4 的规则：有限诊断“只核对覆盖、计数与观察开销，不从测得高水位反填 caps”。所以
“把 2 KiB/实体改成 6.5 KiB/实体”不能写成“因为测到了 6.5 KiB”。可选的两条解析路径如下。

### 路径 A：按 128 槽页结构解析（推荐）

事实：七个非空 World 组件声明了 `page_size = 128`（`NoteTag`/`ElementTag` 为空组件、无负载页）。
于是 `state.current` 的已分配字节 = `Σ_组件 ceil(N/128) × 128 × sizeof(组件)` 加上每页的容量表
与容器头。n64 时每个组件仍分配 128 槽（约 2 倍于实体数），n2048 时恰好 16 页 × 128 槽 = 2048 槽，
这解释了为什么小尺度的“每实体成本”看起来更低。

这条路要求先把七个组件的 `sizeof` 与其页内附加开销登记成一张表（约 20 个字段），再由公式生成
上限；它天然产生 `ceil(N/128)` 的阶梯项，不会在小 N 上过紧。

### 路径 B：固定项 + 线性项（保守）

`state.current = C × N + F`，其中 C、F 取自路径 A 的页表合计（C = Σsizeof，F = 页容量表与
容器的固定开销，并向上取整到 64 KiB）。`command.session` 同理改成分段式：
`128 × SessionChannelSlot + 16 MiB + D × N`，D 来自命令负载随内容增长的实测分解（n64 与
n2048 的差值即可给出 D 的量级，但需用布局字段而不是观测高水位来确认）。

## 3. 需要 owner 签署的内容

1. 选定路径（A 或 B）与最终系数；
2. 是否把 `command.session` 的 16 MiB 固定嵌套额度改为“固定 + 随 N 增长”；
3. 是否把修订后的表写回 `budget-proposal.v1.json` 的 `status`，或另出一份 `v2` 并把
   `2026-11-05-o1-budget-acceptance.json` 的引用改到 v2（两者都需新的接受记录）。

在签署前，现行 O1 接受记录与 `budget-proposal.v1.json` 保持不变；归因结果照原样保留，
不因提案修订而改写。

## 4. 边界

- 本文不改变任何已测字节、不重跑样本、不把观测写成上限。
- GPU/驱动、prepare 峰值、直接 malloc/SDL/OS 堆仍未测量；本修订只涉及已归因的两个域。
- P8/40K 的阻断（冻结的 `maxPackedStrings=100000`）与本文无关，见归因报告 §4。
