### 1C-R02：PlaybackSession 未实现 owner-thread 契约

**状态：已修复**

**证据**

- Playback State 没有 ThreadChecker 或 owner identity：
  [playback_session.cpp:66](../../engine/playback/src/playback_session.cpp#L66)。
- `state()` 直接读取 State：
  [playback_session.cpp:88](../../engine/playback/src/playback_session.cpp#L88)。
- `loadChart()` 在无任何线程检查时清空、追加和排序 Diagnostics，并在调用线程创建 RuntimeSession：
  [playback_session.cpp:92](../../engine/playback/src/playback_session.cpp#L92)。
- `update()` 先读取 Playback State，之后才由内部 RuntimeSession 检查线程：
  [playback_session.cpp:138](../../engine/playback/src/playback_session.cpp#L138)。
- 阶段 1C 计划明确要求同一 Session 保持 owner-thread 规则：
  [stage_1c_implementation_plan.md:180](../stage_plans/stage_1c_implementation_plan.md#L180)。

**触发条件**

- Session 在 A 线程创建，在 B 线程首次加载。
- Session 在加载后移动到另一线程使用。
- 宿主在 update/reload/unload 同时读取 state、chartInfo 或 diagnostics。

**影响**

- Playback 自身字段在 Runtime 拒绝调用前就可能发生数据竞争。
- Session owner 实际由“首次创建内部 RuntimeSession 的线程”隐式决定，而不是由 PlaybackSession 契约决定。
- 外部宿主无法可靠判断哪些查询允许跨线程。

**修复方向**

- owner identity 放入 Playback State，并在每个 public API 接触任何状态前检查。
- 明确构造线程是否就是 owner；如需迁移，提供只能在 quiescent/Empty 状态使用的显式 `transferOwnership()`，不要依赖普通 move 隐式迁移。
- 为查询、销毁、move、load 失败和多 Session 增加 Debug/Release 线程测试。

### 1C-R03：OpenGL 错误线程销毁会泄漏，并可能错误线程释放 SDL Window

**状态：已修复**

**证据**

- `OpenGlBackend::release()` 在非 SDL main/owner thread 时记录日志、清零所有 GL 句柄并直接返回：
  [open_gl_backend.cpp:581](../../engine/render_opengl/src/open_gl_backend.cpp#L581)。
- 该分支没有销毁 Context、Program、VAO 或 VBO，也没有投递 deferred destruction。
- `window_` 在该分支没有清空；最后一个 Lease 释放时，`WindowState::~WindowState()` 会调用 `SDL_DestroyWindow`：
  [sdl_window.cpp:201](../../engine/platform/src/sdl_window.cpp#L201)。
- SDL owner 检查最终依赖仅在非 `NDEBUG` 生效的 `assertCurrent()`：
  [thread_checker.cpp:16](../../engine/core/src/thread_checker.cpp#L16)。

**影响**

- Context 和 GPU 对象确定性泄漏。
- Studio 预览重建、热重载、宿主切场景或异常退出路径可能持续积累 GPU 资源。
- Release 下最后一个 Window lease 可能在错误线程执行 SDL API。

**修复方向**

- 增加 owner-thread `close()`/`shutdown()`，返回 `Result` 并要求宿主在帧安全点调用。
- 后端析构只处理已经关闭的对象；未关闭对象通过 owner queue 延迟销毁，或以明确 fatal contract 终止，而不是静默泄漏。
- 对 Context、Window、Program、VAO、VBO 分别记录销毁计数并增加错误线程回归测试。

### 1C-R04：逐帧 Runtime 与 Snapshot 路径无法扩展到默认对象预算

**状态：已修复**

**证据**

- 默认 Chart 上限允许 100,000 个对象：
  [limits.hpp:19](../../engine/chart/include/cuexis/chart/limits.hpp#L19)。
- 每帧 `TransformPropertyResolver::prepare()` 重置全部 Transform baseline，并重新 compose/校验全部 Transform：
  [property.cpp:95](../../engine/world/src/property.cpp#L95)、
  [property.cpp:174](../../engine/world/src/property.cpp#L174)。
- commit 再验证并替换全部 Transform，即使本帧没有对应写入：
  [property.cpp:187](../../engine/world/src/property.cpp#L187)。
- `updateWorldTransforms()` 每帧重新创建实体数组、排序、创建节点数组和 unordered_map：
  [transform_system.cpp:61](../../engine/world/src/transform_system.cpp#L61)。
- Runtime 每次 update 都无条件执行上述完整路径：
  [runtime_session.cpp:482](../../engine/runtime/src/runtime_session.cpp#L482)。
- Snapshot 每帧逐对象执行二分 `findEntity()`、复制 ChartObjectId，再复制到 ObjectSnapshot：
  [playback_session.cpp:166](../../engine/playback/src/playback_session.cpp#L166)。

**影响**

- update 至少包含多次 O(N) 全量扫描和一次 O(N log N) 排序。
- extract 包含 N 次 O(log N) 查找、两轮 ID 字符串复制和新 vector 分配。
- 多 Session、Studio 高频 Seek 和未来 Animation/Particle 扩展会放大 CPU 与内存带宽压力。
- 当前 3 对象 demo 和功能单测无法暴露该问题。

**修复方向**

- prepare 阶段生成稳定的拓扑顺序、父索引、对象/Entity 对齐表和可直接复制的 Snapshot layout。
- Resolver 只重建存在动画绑定或被覆盖的属性；WorldTransform 只更新脏节点及后代。
- Snapshot 使用稳定 ID 表、索引或共享不可变身份，避免逐帧复制字符串。
- 提供调用方缓冲、双缓冲或 arena，并给出 1k/10k/100k 对象的 update/extract 基准和内存峰值。

### 1C-R05：文件系统 containment 存在 TOCTOU 竞争窗口

**状态：已修复**

**证据**

- Asset 读取先执行 `weakly_canonical`、root prefix 和 regular-file 检查：
  [asset_database.cpp:588](../../engine/assets/src/asset_database.cpp#L588)。
- 随后独立查询 `file_size()`，最后才以路径创建 `ifstream`：
  [asset_database.cpp:599](../../engine/assets/src/asset_database.cpp#L599)、
  [asset_database.cpp:617](../../engine/assets/src/asset_database.cpp#L617)。
- Project 和 Player 文件读取也采用路径检查与打开分离的模式：
  [project_loader.cpp:798](../../engine/project/src/project_loader.cpp#L798)、
  [player_app.cpp:148](../../app/player/src/player_app.cpp#L148)。

**触发条件**

有权限修改项目/资产根的并发进程，在 canonical/regular-file 检查与 open 之间把目标替换为 symlink、junction、reparse point 或另一文件。

**影响**

- 可能读取声明 root 之外的数据，违反 ADR 0025 的物理 containment 承诺。
- 即使替换目标仍在 root 内，也可能出现检查对象与实际读取对象身份不一致。
- 当前短读/增长检测不能发现“相同尺寸的替换文件”。

**修复方向**

- Windows 使用 `CreateFileW` 打开句柄后查询 final path/file identity、reparse 属性和大小，再从同一句柄读取。
- POSIX 使用可信 root dirfd、`openat`/`openat2`、`O_NOFOLLOW` 和 `fstat`，避免重新按路径解析。
- 在阶段 1E 集中到 FilesystemContentProvider，增加 symlink/junction swap 与相同尺寸替换测试。

## 4. P2 问题

### 1C-R06：对象级 Camera 校验会静默回退默认值

**状态：已修复（2026-07-27）**

Canonical Reader 现在对对象 Camera 的 type、FOV、near、far 和 `near < far` 输出与顶层
Camera 一致的字段级诊断，非法组件不再发布默认回退值。ChartCompiler 同时验证程序化
ChartDocument 的默认 Camera 与对象 Camera；Canonical 和 Compiler 回归分别覆盖文本输入与
绕过 Reader 的 typed 输入。

对象组件解析只在值有效时赋值，没有为非法 projection type、FOV、near/far 生成语义诊断，也没有检查 `near < far`：
[canonical_chart_loader.cpp:499](../../engine/chart/src/canonical_chart_loader.cpp#L499)。顶层 Camera 使用了完整诊断逻辑，两个入口行为不一致。Schema artifact 虽包含部分限制，但 Canonical loader 明确不调用 Schema validator，Compiler 的 `validateComponents()` 也没有补充 Camera 校验。

结果是非法 Chart 可能被静默改写为 `perspective/60/0.1/1000`，或带着反向裁剪面进入 Runtime，直到 extract 时才失败。应让 Reader 报字段级错误，并让 Compiler 对程序化 ChartDocument 再做一次完整语义校验。

### 1C-R07：FrameSnapshot 静默丢弃无 Transform 的合法对象

**状态：已修复（2026-07-27）**

`ObjectSnapshot` 新增 `hasTransform`。Snapshot 固定按稳定布局发布全部 Chart Object；无
Transform 对象使用 identity matrix 且 `hasTransform=false`，因此
`ChartInfo.objectCount == FrameSnapshot.objects.size()`。Playback 回归覆盖只含 Element 的合法对象。

Runtime 允许只含 Element、Note 或其他非空间组件的对象，并只在 Chart 声明 Transform 时创建 TransformComponent：
[chart_world_instantiator.cpp:276](../../engine/runtime/src/chart_world_instantiator.cpp#L276)。但 Snapshot 只有在 Entity 具有 WorldTransformComponent 时才创建 ObjectSnapshot：
[playback_session.cpp:191](../../engine/playback/src/playback_session.cpp#L191)。

因此 `ChartInfo.objectCount` 与 `FrameSnapshot.objects.size()` 可能不一致，宿主无法区分“对象不存在”和“对象存在但没有 Transform”。需要冻结以下方案之一：所有 Snapshot 对象强制 Transform；ObjectSnapshot 带 `hasTransform`；或明确将集合改名为 spatial/render objects。

### 1C-R08：CameraComponent 投影缓存固定为 aspect=1

**状态：已修复（2026-07-27）**

`render::CameraComponent` 已移除 `projectionMatrix`，只保存 viewport-independent 参数。
实例化和 FOV 更新不再计算 aspect=1 矩阵；viewport-aware projection 只在 Playback Snapshot
提取时构造。全仓搜索确认 Runtime/Render 不再保留该缓存。

实例化对象相机和默认相机时都以 `aspect=1.0` 写入 projectionMatrix：
[chart_world_instantiator.cpp:301](../../engine/runtime/src/chart_world_instantiator.cpp#L301)。FOV 动画更新同样以 `aspect=1.0` 重算：
[runtime_session.cpp:249](../../engine/runtime/src/runtime_session.cpp#L249)。真正的宿主视口只在 Snapshot 提取时参与计算。

当前 Snapshot 输出正确，但 CameraComponent 中的缓存始终可能与真实视口不一致。后续 Studio、RenderSystem 或调试代码一旦直接读取该字段就会得到错误投影。建议移除 ECS 中 viewport-dependent 矩阵，或将缓存放入 RenderFrame/Snapshot 并明确刷新 owner。

### 1C-R09：`core::makePerspective()` 缺少公共输入契约

**状态：已修复（2026-07-27）**

`makePerspective()` 现在返回 `Result<Mat4>`，集中验证有限性、`0 < fov < pi`、正 aspect、
`0 < near < far` 和最终矩阵有限性。Core 回归覆盖每类错误码，Playback 将失败包装为带 cause
的 `playback.snapshot.camera_invalid`，不再复制参数校验。

`makePerspective()` 返回 `Mat4` 且标记 `noexcept`，但不验证 FOV、aspect、near/far 的有限性、正值和顺序：
[math.cpp:171](../../engine/core/src/math.cpp#L171)。非法输入会直接生成 NaN/Inf 或奇异矩阵。

当前调用方存在重复且不一致的前置校验。建议将验证集中为 `Result<Mat4>`，或将未检查实现降为 internal helper，并提供经过验证的公共入口。

### 1C-R10：PlaybackSession moved-from 对象可空指针解引用

**状态：已修复（2026-07-27）**

PlaybackSession 的 move constructor/assignment 已删除，类保持不可移动；公共头和测试均以
`static_assert` 固定该契约，避免 moved-from 查询产生未定义行为。

move constructor/assignment 会使源对象 `state_ == nullptr`：
[playback_session.cpp:78](../../engine/playback/src/playback_session.cpp#L78)。但 `state()`、`diagnostics()`、`loadChart()`、`unload()` 等全部直接解引用 `state_`。

虽然 moved-from 对象不必保持原值，但无前置条件的 `state() noexcept` 不应产生未定义行为。可选择让 move 后源对象重新获得 Empty State，或删除 move；若保留受限语义，必须在 API 文档和测试中明确。

### 1C-R11：Playback 状态机包含不可到达状态

**状态：已修复（2026-07-27）**

PlaybackSession 公共 `SessionState` 已删除不可到达的 `Paused`；暂停由 1D 的
SourceClock/Transport 表达。`Failed` 保留给候选 Runtime 或 Snapshot 提交失败，并已有赋值路径；
更新/输入错误继续以 Result 返回，不伪装成音频 Transport 状态。

公开枚举包含 `Paused` 和 `Failed`：
[playback_session.hpp:71](../../engine/playback/include/cuexis/playback/playback_session.hpp#L71)。代码只把 Paused 当作允许输入状态，从未进入 Paused；Failed 没有任何赋值路径。Runtime invariant、update 或 extract 失败后 Session 仍保留旧状态。

这使宿主无法区分可重试的输入错误和不可恢复的 Runtime 失败。需要实现明确的 pause/resume 与 fatal classification，或在冻结前删除未实现状态。

### 1C-R12：公共 callback API 允许异常跨模块边界

**状态：已修复（2026-07-27）**

Core 新增统一 `invokeGuarded()`；World 和 Runtime callback API 均返回单层 Result，并把非 OOM
标准/非标准异常转换为 `world.callback.exception` 或
`runtime.session.callback_exception`。公共头和 CODE_POLICY 明确 callback 同步运行于 owner
thread、调用结束即失效、不得重入同一对象或保留 Registry/World 引用。World/Runtime 回归验证
异常 code 和 context，所有调用点显式处理 `[[nodiscard]] Result`。

`World::withRegistry()` 直接 `std::invoke`：
[world.hpp:28](../../engine/world/include/cuexis/world/world.hpp#L28)。`RuntimeSession::withWorld()` 虽返回 Result，也没有捕获 callback 异常：
[runtime_session.hpp:118](../../engine/runtime/include/cuexis/runtime/runtime_session.hpp#L118)。

这与 CODE_POLICY 中“异常不得跨 Cuexis 模块公共边界”的规则冲突。Runtime/World 若仅作为内部实现，应收窄 public surface；否则需要捕获非 OOM 异常并转换为稳定 Error，同时定义 callback 的重入、阻塞和生命周期规则。

### 1C-R13：Reload 批量失败诊断对宿主不可见

**状态：已修复（2026-07-27）**

Playback State 现在分离 active `diagnostics` 与 `lastOperationDiagnostics`，新增
`lastOperationDiagnostics()` 查询。load/reload 的完整有界诊断集合会在失败后保留，摘要只从
第一条 Error 生成；回归测试覆盖失败 reload 后旧 Running 状态与完整 operation diagnostics。

reload 的 Chart load/compile/Runtime diagnostics 保存在局部变量中，失败时 `operationError()` 只复制第一条诊断 code/path：
[playback_session.cpp:278](../../engine/playback/src/playback_session.cpp#L278)。活动 `state_->diagnostics` 必须保留旧 Session 的诊断，因此本次失败的完整集合在返回后丢失。

建议使用 `ReloadResult { reloaded, error, diagnostics }`，或分离 active diagnostics 与 last-operation diagnostics。选择“第一条诊断”时也应查找第一条 Error，而不是无条件使用 `items().front()`。

### 1C-R14：Chart/Behavior IR 存在重复持有和复制

**状态：已修复（2026-07-27）**

Playback State 不再持有第二份 ChartRuntime，只保留 ChartInfo 和稳定 Snapshot layout。Runtime

## 6. 架构评价

### 6.1 可保留的设计

- `cuexis_playback` 作为宿主门面、RuntimeSession/World/EnTT 作为内部实现的方向正确。
- Chart typed Reader 与 JSON DOM 隔离有效，外部输入具有大小、深度、字符串、对象、Key 和诊断预算。
- Chart compile、Runtime prepare/commit/reload 的候选发布与失败回滚结构清楚。
- Behavior 以绝对 chartTimeMs 求值，排序后的 IR 和 discontinuity 契约有利于 Seek 与确定性。
- Resource Handle 的 index/generation/manager token 和 Lease/Scope 生命周期设计整体合理。
- CMake target 依赖 allowlist、架构正则扫描和公共 Playback header 检查能阻止明显的依赖反转。

### 6.2 当前主要结构缺口

```text
Project/Chart source
-> AssetDatabase
-> ContentProvider
-> ResourceManager
-> PlaybackSession
-> RuntimeSession
-> FrameSnapshot
```

当前只实现了 `Chart JSON -> PlaybackSession -> 无资源 RuntimeSession -> FrameSnapshot`。Player 单独完成了 Project/AssetDatabase 的前半段，但没有把结果接入 Playback，导致职责边界在最关键的组合点断开。

Playback State 后续应成为以下对象的统一 owner：

```text
Session owner identity
Host/Memory/Filesystem ContentProvider
AssetDatabase / ResourceManager
RuntimeSession
稳定 Object identity table
active diagnostics / last-operation diagnostics
Snapshot buffer policy
```

Player 只应保留 CLI、Clock、Window、输入和可选 Render/Audio adapter。
