# Cuexis AI 协作规范

状态：强制执行

更新日期：2026-07-20

## 1. 适用范围

本文约束 AI 在 Cuexis 项目中的所有分析、讨论、文件操作、代码编写、依赖引入、测试、验证和文档维护行为。

AI 必须同时遵守：

```text
用户当前明确要求
docs/ 下已接受的规范与 ADR
ADR 0027 与 SDK 转型方案定义的产品和宿主边界
本文定义的协作流程
项目已有模块边界、代码风格和构建规则
```

发生冲突时，AI 必须指出冲突、说明影响并向用户确认，不得自行选择会改变项目方向的方案。

讨论、建议、评审和假设不等于修改授权。用户未明确要求保存、修改、创建、删除或实现时，AI 只能进行只读分析，不得改动文件。

## 2. 编写代码前的强制确认

在编写或修改任何代码前，AI 必须反复向用户提问，直到以下技术细节和实现思路得到明确确认：

```text
目标行为与使用场景
功能范围与明确非目标
输入、输出、错误和边界条件
涉及的模块、依赖方向和所有权
数据格式、版本和迁移要求
线程、生命周期、时间域和确定性要求
平台、编译器、渲染或音频后端限制
性能、内存和延迟目标
兼容性、安全性和测试要求
验收标准与允许延期的内容
```

提问必须围绕真实决策点，不得机械重复已经确认的信息。若答案可以从现有代码、文档或构建配置中可靠取得，AI 应先进行只读检查，再向用户确认仍存在歧义的部分。

未经用户确认，不得：

```text
冻结新的公共 API
改变模块依赖方向
修改持久化格式或版本语义
引入新的第三方依赖
扩大当前阶段范围
删除、迁移或批量重写现有代码
把远期预留实现为当前功能
```

## 3. 实现前检查清单

开始编写代码前，AI 必须逐项思考并确认：

### 3.1 需求与架构

```text
是否准确遵循用户已确认的要求？
是否遵循 docs/ 下相关规范和 ADR？
是否保持 Playback、Chart、Runtime、World、Judgement、Render、Audio、Platform、Adapter 和 App 的模块边界？
是否把 RuntimeSession/EnTT 保持为 SDK 内部实现，并由 PlaybackSession 提供宿主门面？
是否保持 headless 路径不依赖 SDL、OpenGL、窗口或物理音频设备？
是否把功能放在正确的所有者模块，而不是为了方便形成反向依赖？
是否只实现当前阶段所需的最小闭环？
```

### 3.2 API 与第三方依赖

```text
现有项目 API 是否已经可以直接实现该功能？
标准库、操作系统或现有依赖是否已提供成熟实现？
是否存在成熟、持续维护、许可证兼容的第三方依赖？
引入依赖能否显著降低正确性风险和长期维护成本？
依赖是否会导致构建时间、二进制体积、包体、升级成本或攻击面不合理增长？
第三方类型是否被封装，避免污染 Cuexis 公共 API、Component、Chart 和资产格式？
安装后的 SDK 公共头是否避免暴露 EnTT、SDL、OpenGL、JSON DOM 和实现依赖？
是否有清晰的替代方案和退出路径？
是否需要更新 vcpkg manifest、固定 baseline、ADR 和 THIRD_PARTY_NOTICES？
```

不得仅因为“可以使用库”就引入依赖，也不得为了减少依赖而自行重写复杂、已有成熟实现的通用系统。

### 3.3 安全与健壮性

```text
所有外部输入是否经过语法、结构、范围和语义校验？
宿主 ContentProvider、InputEvent、ReplayData 和回调输入是否按不可信边界校验？
整数、时间、有理数、索引、大小和资源预算是否检查溢出与上限？
错误是否通过 Result、Diagnostics 或明确状态传播，而不是被静默忽略？
资源、线程和对象生命周期是否明确？
音频实时路径是否避免分配、阻塞、文件 I/O、格式化日志和 ECS 操作？
Worker、Main、Render 和 Audio Thread 是否遵守所有权规则？
失败、取消、Reload、Seek 和部分资源缺失是否保持一致且可恢复的状态？
日志和诊断是否避免泄露敏感信息或不可控的大量数据？
```

### 3.4 扩展性与冗余

AI 必须为已确认的后续需求保留合理扩展边界，但不得进行没有现实需求的过度设计。

```text
公共接口是否能容纳文档中已经确认的后端、格式和平台扩展？
格式、Component、资源和缓存是否具有明确版本？
持久化 ID 与运行时句柄是否分离？
后端对象是否被限制在后端模块？
未来扩展能否通过新增实现、注册项或版本迁移完成，而无需破坏无关模块？
预留是否只是稳定边界，而不是提前实现远期系统？
```

“足够冗余”表示为已确认的变化保留替换点、版本和容量，不表示预先加入未使用字段、抽象层、动态插件 ABI 或通用框架。

## 4. 编码与操作规则

AI 编写代码时必须遵守 `docs/CODE_POLICY.md`、模块专项文档和相关 ADR，并执行以下规则：

```text
保持改动范围最小，不混入无关重构
优先复用现有模式、工具和公共类型
Component 只保存数据，System 负责逻辑
业务代码不得直接依赖 OpenGL、SDL 后端对象或其他后端专有类型
公共 API 必须明确所有权、错误和线程要求
新增数据格式、Component 和缓存格式必须具有版本
所有确定性逻辑不得依赖数组顺序、哈希遍历顺序、帧率或真实时间
复杂算法只添加说明关键约束的必要注释
不得删除或覆盖用户已有改动，除非用户明确授权
```

每次准备修改文件前，AI 必须先说明将修改哪些内容以及原因。遇到用户在讨论中纠正方向时，应先确认新方案；用户未要求保存时不得直接写入文件。

## 5. 阶段完成后的强制重审

功能、子阶段或阶段完成后，AI 必须重新审查全部相关改动，而不能只确认代码能够编译。

重审至少包含：

```text
逐项对照用户要求和验收标准
重新检查相关 docs/ 规范与 ADR
检查模块依赖、公共 API、所有权和线程边界
检查异常、错误恢复、资源释放、Reload、Seek 和失败回滚
检查输入校验、溢出、越界、空值、失效句柄和生命周期问题
检查确定性、时间边界、排序冲突和跨帧状态
检查新增依赖、许可证、NOTICE、版本和退出路径
检查是否存在未使用代码、临时绕过、调试残留和隐式默认行为
```

## 6. 测试与验证要求

AI 必须根据改动风险执行严格且可重复的测试，并报告实际执行结果。

最低验证流程：

```text
配置项目
构建受影响 target
运行相关单元测试
运行 CTest 对应 preset
检查失败输出和结构化诊断
检查格式、静态规则和文档一致性
```

涉及以下系统时必须增加专项验证：

```text
Chart：非法输入、版本、引用、模板、顺序无关和确定性编译
Timing：BPM、Stop、offset、负 Beat、边界和逆映射
Runtime：prepare/commit、失败回滚、Reload、Unload 和销毁顺序
Resource：generation、Lease/Scope、Required/Fallback/Optional 和热重载失败
Animation：冲突、权重、Additive、Quaternion、离散属性和任意时间采样
Particle：跨帧率、Checkpoint、Seek、倒放和 simulationVersion
Render/Shader：多目标编译、Reflection、Variant、缓存和失败保留旧 Pipeline
Audio/Input：实时线程限制、时钟不连续、延迟、时间戳映射和 underrun
SDK：headless、外部 consumer、多 Session、公共头泄漏、安装/导出和宿主回调生命周期
Judgement/Replay：startRecording/stopRecording API、loadReplay 拒绝同时实时输入、cuexis_judgement 不依赖 SDL/音频/渲染后端、输入顺序、时间戳、配置快照、实时/回放一致性和损坏格式
```

测试必须覆盖正常路径、边界路径和失败路径。不能用一次成功运行代替单元测试，也不能用“理论上正确”代替实际验证。

如果环境限制导致某项测试无法执行，AI 必须明确说明：

```text
未执行的测试
无法执行的具体原因
已经完成的替代检查
仍然存在的风险
用户可执行的准确命令
```

## 7. 完成报告

AI 只有在确认代码、测试、文档和验收标准一致后，才能声明功能或阶段完成。完成报告至少包含：

```text
实际完成的内容
修改的模块和公共行为
执行的测试与结果
未执行的验证和剩余风险
新增依赖及许可证影响，若有
后续仍需处理但不属于本次范围的事项
```

不得隐瞒失败、跳过的测试、安全风险或尚未实现的验收项。
