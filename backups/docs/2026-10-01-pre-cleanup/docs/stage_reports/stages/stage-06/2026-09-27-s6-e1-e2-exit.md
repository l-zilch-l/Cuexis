### 4.2 三种格式的完整导入/播放（E2 验收）

1. Python 写出确定性的 3 秒 48000 Hz 双声道 S16 源 `source.wav`（576044 字节）；ffmpeg 以固定
   选项编码出 `source.mp3`（libmp3lame 128k）、`source.ogg`（libvorbis q5）、`source.flac`
   （flac level 5）。
2. CLI 分别导入，三者都报告 `sampleRate=48000`、`channels=2`、`frames=144000`、
   `decodedBytes=576044`，decoder 分别为 `minimp3-2021-11-30-no-simd`、
   `libvorbis-1.3.7-libogg-1.3.6`、`libflac-1.5.0-native`。
3. FLAC 的 canonical WAV 与 `source.wav` 逐字节相同；MP3 与 Ogg 按各自的 delay/padding 与
   granule end 规则截断，因此与源不同。
4. 把产物换回 `stage1d_project` 副本的 `assets/audio/main.wav`，`--audio-smoke-test` 三种格式
   全部退出码 0、各 90 帧完成、reload 事务完成、`underruns: 0`。这同时说明 canonical WAV 布局
   （只有 `fmt ` 与 `data`、`byteRate`/`blockAlign` 自洽）被既有解码器接受，不需要运行时直解码
   路径。证据目录 `out/s6e_playback/`。

该链路的边界（本批次未把它当作已完成）：仓库里没有一条自动化测试把 importer 产出的 canonical
WAV 字节直接喂给 `cuexis::audio_sdl::WavDecoder`（`tests/audio_sdl/wav_decoder_tests.cpp` 只用
内存中合成的 WAV，`cuexis_playback_tests` 不链接 `cuexis::audio_sdl`）。本节是运行时端到端证据，
不是单元测试；把它固化成门禁需要另开测试项。

## 5. 缺陷

实现与四平台验证过程中发现并修复的六条缺陷，全部有具名复验：

1. minimp3 静默接受截断 MP3（`mp3dec_ex_read` 在残缺帧返回 0 且不报错，75% 截断被当作正常输入
   只产出 47 帧）。改为拿 Xing/Info 声明的样本数与实际解码样本数比较，不足即
   `media.audio.truncated`；在 50%/75%/90%/95% 四个截断点复验。
2. libFLAC 在非 seekable 回调下于最后一个帧边界误报 `lost sync`。改为提供
   seek/tell/length/eof 回调。
3. FLAC 截断与损坏原来都归到 `media.audio.decode_failed`。现按 STREAMINFO 声明样本数区分
   `media.audio.truncated` 与 `media.audio.container_invalid`。
4. MSVC C4611（libpng/libjpeg 的 setjmp 桥接）：桥接函数只保留 C 结构与裸指针并定点抑制；此前的
   C4324、C4244、C4189、C2665 也已消除。
5. 门禁的内存上限用例原来用 2x2 的 `rgb8.png` 加 1 MiB 上限，在 MinGW 上**通过**（运行时基线
   与分配量都低于 1 MiB，上限根本没被触发，用例什么都证明不了）。改用
   `image/budget_1024.png`（1024x1024 → 4 MiB RGBA8），四个平台都必须失败关闭。
6. POSIX `RLIMIT_AS` 与 AddressSanitizer 不兼容（ASan 在 `main` 之前 abort），导致 sanitized
   构建里每次 worker 调用都失败。现在 worker 检测到 sanitizer 时跳过地址空间上限并在 stderr
   说明 `--memory-limit` 被忽略，门禁在 sanitized 构建跳过该用例；上限本身仍由 MSVC、MinGW 与
   GCC media-tools 三个作业覆盖。
