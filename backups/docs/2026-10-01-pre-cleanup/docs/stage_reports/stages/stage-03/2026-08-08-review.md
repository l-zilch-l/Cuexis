### R01（P1）：OpenGL candidate 会被后续 prepare 静默作废

ADR 0037 和详细合同要求 adapter 在不修改 active cache 的前提下准备 candidate，并在 Playback commit
成功后以不可失败的 move/swap 激活同一个 candidate cache
（`docs/adr/0037-stage-3-portable-presentation-contracts.md:61-68`，
`docs/PORTABLE_PRESENTATION.md:498-522`）。公共注释也声明 valid candidate 不能激活失败
（`engine/render_opengl/include/cuexis/render_opengl/open_gl_backend.hpp:160-167`）。

实现没有让 `OpenGlPresentationCandidate` 拥有 cache 或 backend identity；它只保存 token、settings 和
一个数值 generation，`valid()` 也只检查 generation 非零
（`engine/render_opengl/include/cuexis/render_opengl/open_gl_backend.hpp:94-115`，
`engine/render_opengl/src/open_gl_presentation.cpp:940-956`）。backend 只有一个 `pending` 槽位
（`engine/render_opengl/src/open_gl_presentation_internal.hpp:98-104`），每次 prepare 都直接覆盖该槽位
并更新 generation（`engine/render_opengl/src/open_gl_presentation.cpp:1076-1080`）。旧 candidate 对象仍
返回 `valid() == true`，但 activation 遇到 generation 不匹配时只清空 candidate 并静默返回
（`engine/render_opengl/src/open_gl_presentation.cpp:1096-1117`）。

可复现顺序：

1. 为 Playback candidate A 调用 `preparePresentation()`，得到 OpenGL candidate A。
2. 在未提交 A 前，为同一 Session 的 Playback candidate B 调用 `preparePresentation()`。
3. 提交 A。Playback 允许多个同 generation 的 PreparedPlayback 存在，第一次 commit 可以成功
   （`engine/playback/src/playback_session.cpp:1026-1059`）。
4. 调用 `activatePresentation(A)`。该调用无错误返回，但不会切换 cache。

结果是 Playback A 已发布，GPU 仍使用旧 active cache，而 B 的 cache 留在 pending。若资源 identity
不同，后续帧会失败或继续显示旧内容；若 ID/identity 恰好兼容，则错误可能静默存在。candidate 还没有
backend identity，两个 backend 的 generation 碰撞时，跨 backend 传入 candidate 也可能激活或丢弃
目标 backend 自己的 pending cache，而不是调用者传入 candidate 对应的 cache。

原始缺失测试：同一 backend 同时准备两个 Playback/OpenGL candidate，提交并激活较早者，验证 active
token/cache 与已提交 Playback 一致；另需两个 backend 的交叉 candidate 测试。原始审查时 smoke 只有
单一 candidate 的失败/成功 reload 顺序，不能覆盖该状态空间。

整改（2026-08-09）：OpenGL backend 现在显式只允许一个 outstanding presentation candidate；在前一
candidate 激活或丢弃前再次 prepare，会返回
`render.opengl.presentation.candidate_outstanding`，且不覆盖 pending cache。candidate 同时记录唯一的
backend token；跨 backend 的 activate/discard 不修改 candidate 或目标 backend，而同 backend 的
generation、Playback token 或 pending 状态不变量失配会直接终止，避免无错误返回的静默分裂。

Player GPU smoke 新增“先准备 candidate A、拒绝 candidate B、再提交并激活 A”的回归路径，验证被拒绝
的第二次 prepare 不会作废第一个 candidate，且 reload 后原有 pixel/summary digest golden 保持不变。
由于当前 `SdlRuntime`/`SdlWindow` 合同只允许一个 active window，两个真实 OpenGL backend 的交叉
candidate 负例尚未自动化，继续记录为残余测试缺口，不阻止本次实现整改进入独立复审。

### R02（P2）：未绑定 Behavior 扩大表现资源闭包

合同要求 manifest 只包含播放期间可能被 Snapshot 引用的资源，并明确要求 Stage 3 使用“严格必需
资源”闭包（`docs/PORTABLE_PRESENTATION.md:440-453`，
`docs/stage_plans/stage_3_implementation_plan.md:383-390`）。

`collectRequiredResources()` 先遍历 Renderable object，但随后无条件遍历 `chartRuntime.behaviors` 中的
每个 RenderMaterial Step，把所有 Material 值加入 manifest，不检查该 Behavior 是否被任何 Renderable
object 绑定（`engine/playback/src/presentation.cpp:827-871`）。Runtime 的真实准备路径只在遍历到具有
Renderable 和 Behavior binding 的 object 时请求动态 Material
（`engine/runtime/src/runtime_session.cpp:777-833`）。

因此，一个完全未绑定、运行时不可能影响 Snapshot 的 Behavior，只要引用缺失、损坏或超预算
Material，就会让整个 candidate 在 commit 前失败；大量未绑定 Material 也会无故消耗 65,536 entry
和 512 MiB session budget。这既拒绝了本可播放的 Chart，也使 manifest 不再是规范定义的最小表现
闭包。

原始缺失测试：在合法 Chart 中加入未绑定 Behavior，并让其 RenderMaterial Step 引用不存在或超预算
的 Material；candidate 应按实际 object binding 准备成功，manifest 不应包含该资源。还应核对“绑定
到非 Renderable object”的阶段边界。

整改（2026-08-09）：`collectRequiredResources()` 现在在遍历每个 Renderable object 时，只查找该 object
实际绑定的 Behavior，并只收集其中的 RenderMaterial Step 候选值；不再全局遍历
`chartRuntime.behaviors`。新增回归在合法 Chart 中加入两个引用缺失 Material 的未绑定 Behavior，
candidate 仍成功准备并提交，manifest 保持原有 4 个严格必需资源且不包含两个缺失引用。

复核同时确认，RenderMaterial Behavior 绑定到非 Renderable object 并不是合法的可播放输入：
`RuntimeSession` 会在 presentation 构建前以 `runtime.chart.behavior_renderable_missing` 拒绝。因此新增测试
锁定该上游拒绝，不把它误判为应成功但 manifest 为空的 R02 路径。

### R03（P2）：Validation Sink 不是严格独立 oracle

详细合同把 Validation Sink 定义为只使用公共 API 的独立实现，并声明它独立验证 resource 语义、
manifest membership、依赖、预算和规范资源顺序，以便捕获 Playback producer 缺陷
（`docs/PORTABLE_PRESENTATION.md:719-724`）。当前实现有以下共同盲区：

- Mesh 只检查 finite、count 和 index 范围，没有检查 position `abs <= 1,000,000`、UV `[0,1]`，也
  没有拒绝重复 index/零面积三角形
  （`tests/presentation/validation_sink.cpp:355-407`；合同见
  `docs/PORTABLE_PRESENTATION.md:341-350`）。
- Material 只检查颜色位于 `[0,1]`，没有执行 Opaque alpha 必须精确为 `1` 的规则
  （`tests/presentation/validation_sink.cpp:431-458`；合同见
  `docs/PORTABLE_PRESENTATION.md:374-388`）。
- Frame validation 对 Stage 2 已冻结为 `[0,1]` 的 opacity/tint 只检查 finite，超范围值会进入
  effective color 和 pass 计算
  （`tests/presentation/validation_sink.cpp:1108-1125`；合同见
  `docs/adr/0036-stage-2-runtime-contracts.md:63-72` 和
  `docs/PORTABLE_PRESENTATION.md:403-416`）。
- Sink 复制并排序 manifest，而不是拒绝非规范顺序
  （`tests/presentation/validation_sink.cpp:467-482`）。现有测试甚至反转 manifest/resources 后要求验证
  成功（`tests/presentation/validation_sink_tests.cpp:226-240`），与 manifest 本身必须按稳定键排序的
  合同相反（`docs/PORTABLE_PRESENTATION.md:445-453`）。

Playback producer 当前会在解析时拒绝这些值，但独立 oracle 的目的正是发现 producer 回归。若
producer 同时生成与非法值一致的 identity，Sink 会重新计算同一 identity 并接受；OpenGL 也依赖已
验证资源，因此两者仍可能产生一致的错误 summary，使 parity/golden 门禁保持绿色。

原始缺失测试：独立构造并同步更新 ref identity 的非法 PortableResource，覆盖 position/UV 范围、
重复 index、零面积、Opaque alpha、opacity/tint 范围；非规范 manifest 顺序必须失败，而不是在 Sink
内部被修正。

整改（2026-08-09）：Validation Sink 不再排序 manifest 或重新配对 resources；manifest 必须按
`(AssetId raw bytes, resource type)` 严格递增，resource 数组必须与 manifest 同索引一致，否则返回
`playback.presentation.reference.invalid`。Mesh 校验现已覆盖 position 绝对值上限、UV `[0,1]`、重复
index 和零面积三角形；Material 校验增加 Opaque alpha 精确为 `1`；Frame 校验增加 opacity/tint
`[0,1]` 范围。

为有限但超范围的 Frame 值新增稳定 code `playback.presentation.frame.value_invalid`，并同步写入
`docs/PORTABLE_PRESENTATION.md`。测试先修改 owning public resource，再重新计算并同步 resource/manifest
identity，确保失败来自独立语义校验而不是旧 identity；反转 manifest 或 resource 顺序现在必须失败。

### R04（P2）：OpenGL 为 legacy candidate 激活空 cache

Playback 的兼容合同允许全 opaque Stage 1B closure 继续 prepare/commit，但不发布 portable manifest
（`docs/PORTABLE_PRESENTATION.md:320-325`，测试见
`tests/playback/presentation_tests.cpp:548-562`）。这只保留 Playback 历史路径；ADR 0037 同时规定 opaque
fallback 不得进入真实绘制路径，Stage 3 adapter 应在 commit 前完成或拒绝准备
（`docs/adr/0037-stage-3-portable-presentation-contracts.md:61-73`）。Validation Sink 按这一边界在
manifest 为空时拒绝 candidate（`tests/presentation/validation_sink.cpp:919-925`）。

OpenGL 的行为不同。`validatePresentation()` 对没有 `state_->presentation` 的 candidate 跳过全部
Portable capability/limit 检查并仍可返回 effective settings
（`engine/playback/src/playback_session.cpp:605-700`）；OpenGL 随后在 manifest 为空时跳过 acquisition 和
upload，却仍写入单一 pending 槽并返回 valid candidate
（`engine/render_opengl/src/open_gl_presentation.cpp:1021-1080`）。commit 后 activation 会发布这个空
cache；frame 构建看到空 manifest 立即成功返回，不检查 legacy Renderable，也不产生 presentation
command（`engine/render_opengl/src/open_gl_presentation.cpp:564-577`）。

这会让官方 adapter 把“无法消费的 candidate”报告为 prepare 成功，宿主随后完成 Playback commit，
却只能得到没有真实 Renderable 的 active cache。该失败发生在已越过可回滚的 adapter prepare 边界后，
与完成报告所称“成功 reload 只在完整 candidate 准备后切换”不一致
（`docs/stage_reports/stage_3_completion_report.md:24-36`）。

原始缺失测试：使用 `stage1b_project` 调用 OpenGL `preparePresentation()`，要求在 Playback commit 前
返回明确错误并保持旧 active cache；同时保留 Playback-only legacy prepare/commit 回归。

整改（2026-08-09）：OpenGL 在发布 pending cache 或 candidate generation 前强制要求非空 portable
manifest；legacy candidate 返回
`render.opengl.presentation.portable_candidate_required`。非空但零 entry 的 Portable v1 manifest 仍为
合法输入。Player 构建现在复制未修改的 `stage1b_project` fixture，GPU smoke 通过公开
`PlaybackSource`/`PlaybackSession` 路径验证 legacy candidate 在 Playback commit 前被拒绝，且旧 active
cache 保持有效；Playback-only legacy 兼容路径未被修改。

### R05（P2）：冻结的 dependency-cycle code 不可达

Stage 3 v1 把 `playback.presentation.dependency.cycle` 列为稳定诊断，并规定稳定 code 不得复用为其他
失败（`docs/PORTABLE_PRESENTATION.md:567-609`）。原实现中，AssetDatabase 在 Playback presentation
prepare 之前遍历完整依赖图，以 `assets.database.dependency_cycle` 拒绝 cycle，导致宿主无法观察冻结的
Playback code。

整改（2026-08-09）：`PlaybackSource::fromTypedProject()` 和 `fromFilesystemProject()` 现在在 Playback
公共 source 边界把该 Assets 层错误翻译为 `playback.presentation.dependency.cycle`，同时保留原始
`assets.database.dependency_cycle` 作为 cause，并复制 cycle context。Assets 层仍保留自己的内部错误
语义，避免修改通用 AssetDatabase 合同。

回归测试从公共 `PlaybackSource::fromTypedProject()` 构造闭环，断言宿主看到稳定 presentation code、
cycle context，以及底层 Assets cause；WSL GCC 与 Clang ASan/UBSan Playback 测试均通过。

### R06（P3）：Debug summary parity 取决于 scene 指针

Validation Sink 把 candidate 的 effective `debugPassEnabled` 直接写入 summary
（`tests/presentation/validation_sink.cpp:1018-1028`）。OpenGL 只有在该 setting 为 true 且调用者传入
非空 `debugScene` 时才把 summary 字段设为 true
（`engine/render_opengl/src/open_gl_presentation.cpp:1163-1175`），而公共调用默认参数正是
`debugScene = nullptr`
（`engine/render_opengl/include/cuexis/render_opengl/open_gl_backend.hpp:169-173`）。两个 summary digest 都
哈希该布尔值（`tests/presentation/validation_sink.cpp:800-824`，
`engine/render_opengl/src/open_gl_presentation.cpp:537-561`）。

所以相同 candidate settings 和 FrameSnapshot 在“Debug 已有效、但本帧没有 Debug scene”时产生不同
digest。当前 Player 总是传入 scene，golden 没有覆盖默认调用路径；该问题只影响 parity/诊断摘要，
不改变 Opaque/Transparent 绘制，故评为 P3。

缺失测试：启用 Debug capability/request，分别以 `nullptr`、空 scene 和非空 scene 调用 OpenGL，并与
ValidationSummary 比较 effective setting 和 digest。

整改（2026-08-09）：OpenGL summary 的 `debugPassEnabled` 现在只来自 active candidate 的 effective
setting，不再取决于调用者是否传入 Debug scene。`debugCommandCount` 仍只记录 Debug pass 启用时本次
实际传入的 scene command 数量，但不参与 Portable summary digest；因此省略、空和非空 scene 不再
改变同一 snapshot 的 effective setting 或 digest。

Player GPU smoke 在 Debug 已启用且具有固定 Validation Sink golden 的 Frame 1 上，依次以 `nullptr`、
空 `RenderScene` 和非空 `RenderScene` 渲染同一 snapshot，要求三者的 `debugPassEnabled` 和 digest
完全一致；非空 scene 的 digest 仍必须等于 `18316288860163381829`。Debug/Release smoke 均通过，
原有像素、六帧完成以及 R01/R04 reload 回归未漂移。

### R07（P3）：shared DLL 泄漏测试用 detail symbols

两个位于 `engine/playback/src/`、不安装给 consumer 的内部函数仍标记
`CUEXIS_PLAYBACK_API`：历史 digest 入口
`computeFrameDigestVersion()`（`engine/playback/src/frame_digest_internal.hpp:9-14`）和 common normalizer
`normalizePresentationFrame()`（`engine/playback/src/presentation_extraction.hpp:13-42`）。在 shared build
中它们进入 Playback DLL 导出表，扩大了实际二进制表面，并把 tests 所需的内部 C++ 类型暴露为可见
symbol。本地 `headless-shared-debug` 构建后使用 `llvm-readobj --coff-exports` 检查 DLL，两个
`cuexis::playback::detail` 符号均实际出现在导出表中。

`VerifySharedExports.cmake` 只用子串检查七个必需 symbol，并禁止 RuntimeSession、AssetDatabase、EnTT
和 World 四类名字，没有禁止 `cuexis::playback::detail` 或执行精确 allowlist
（`cmake/VerifySharedExports.cmake:24-39`）。因此 `cuexis_shared_export_surface` 通过并不能支持“仅有预期
Playback API”的更强结论。当前 C++ shared package 本来就是 matching-toolchain preview，所以该问题
评为 P3，而不是稳定 ABI 破坏。

缺失测试：对 demangled shared export 建立精确公共 allowlist，至少拒绝
`cuexis::playback::detail::computeFrameDigestVersion` 和
`cuexis::playback::detail::normalizePresentationFrame`。

整改（2026-08-09）：两个内部声明已移除 `CUEXIS_PLAYBACK_API`。`computeFrameDigest()` 的公共 wrapper
保留在 `frame_digest.cpp`，历史版本实现移入新的 `frame_digest_version.cpp`；shared 测试直接编译该实现
和 `presentation_extraction.cpp`，因此不再通过 Playback shared library 链接未安装的 detail 入口，同时
继续覆盖历史 digest 与 normalization 行为。

`VerifySharedExports.cmake` 现在显式禁止两个函数名和 Playback `detail` namespace，并对 Cuexis 自有
导出执行公共 owner allowlist：`ChartClock`、`PlaybackSession`、`PlaybackSource`、`PreparedPlayback`、
`RuntimeTimeline` 以及公共 free function `computeFrameDigest`。Windows `dumpbin` 对 DLL 的全部显式导出
执行 allowlist；Linux 使用 `nm -D` 的原始 Itanium symbol 判断顶层 owner 和执行 allowlist，另以
`nm -D -C` 检查必需公共名称。由 GCC/Clang/libstdc++ 生成、顶层 owner 为 `std`、`__gnu_cxx` 的弱模板
符号即使参数提到 Cuexis 私有类型也不会误判，而真正以 Cuexis namespace 为 owner 的 symbol 仍必须
满足 allowlist。MSVC、WSL GCC 和 WSL Clang shared export gate 均通过，导出表均不再包含两个 detail
函数。

## 3. 未升级为 finding 的测试缺口与残余风险

- 当前 2x2 texture fixture 是非对称内容，但 GPU smoke 只读取中心像素并允许较宽容差
  （`app/player/src/player_app.cpp:276-295`）。中心 bilinear 采样不能证明四个 corner、UV `(0,0)` 左上角
  约定和 clamp 边界；应补充 off-center/corner probe。代码审查未建立现有实现发生垂直翻转的充分
  证据，因此本项只记录为测试缺口。
- GPU 证据仍只覆盖 Windows/NVIDIA/OpenGL 3.3；AMD、Intel 和 native Linux GPU 是完成报告已列出的
